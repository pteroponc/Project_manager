# PM-003B3.2c — POST/PATCH ИБ-рисков

## Обязательное уточнение B3.3b: экземпляр паспорта

Паспорт возвращает серверный неизменяемый `instanceId` (UUID), техническая версия
нового паспорта остаётся 0, documentVersion=1.0. После удаления новый паспорт того
же проекта получает другой instanceId. Клиент не задаёт instanceId при POST и не
может менять его при PATCH.

**expectedPassportInstanceId обязателен** в JSON PATCH паспорта, POST компонента,
интеграции, риска и checks/initialize; в query DELETE паспорта и всех четырёх типов
дочерних записей. Он передаётся вместе с прежними числовыми версиями/confirmed.
POST самого паспорта сохраняет expectedProjectVersion; PATCH дочерней записи сохраняет
собственный UUID recordId и expectedVersion, без токена паспорта.

Отсутствующий/невалидный UUID — 400; после блокировок сначала проверяются наличие
и принадлежность ресурсов, затем instanceId, затем числовые версии. Несовпадение —
409 PASSPORT_INSTANCE_CONFLICT с реальной currentVersion и versionResource=PASSPORT,
без записей. Ресурс отсутствует — 404. Никакой подстановки токена текущего паспорта
для старой команды или автоматического повтора. Клиенту нужна новая карточка и
повторное подтверждение намерения. Числовые параметры и closed-list JSON/query
дополнены только этим полем. Это изменение контракта обязательно для клиентов.

Пример query дополнительно содержит
`expectedPassportInstanceId=11111111-1111-4111-8111-111111111111`;
в JSON-команде добавляется одноимённое строковое поле с UUID из актуального DTO.
Полная спецификация и ручная миграция: `docs/PM-003B3.3b-manual-V005.md`.

Backend-контракт. Существующие модель, каталоги, DTO и оценщик B2 используются без
изменения схемы, миграций и формулы. Пользовательская `passport.documentVersion=1.0`
отделена от технических `@Version`.

## Маршруты и поля

`POST /api/projects/{id}/architecture/risks` требует существующие проект и паспорт,
`expectedPassportVersion` и пять обязательных полей. Успех — **201 с полным архитектурным
агрегатом**, а не одной записью. Никакие другие дочерние записи автоматически не создаются.

```json
{
  "expectedPassportVersion": 0,"expectedPassportInstanceId":"11111111-1111-4111-8111-111111111111",
  "name": "Недоступность обмена",
  "category": "INTEGRATION",
  "probability": "MEDIUM",
  "impact": "HIGH",
  "status": "OPEN",
  "owner": "Ответственный",
  "treatmentDueDate": "2026-12-01",
  "treatmentPlan": "Согласовать резервный порядок обмена"
}
```

| Поле | Контракт |
|---|---|
| name | Обязательно, непустой однострочный текст, максимум 255 |
| category | ACCESS, DATA, AVAILABILITY, INTEGRATION, PROCESS, OTHER |
| probability, impact | LOW, MEDIUM, HIGH, CRITICAL |
| status | OPEN, IN_PROGRESS, ACCEPTED, MITIGATED, CLOSED |
| description, treatmentPlan, acceptanceJustification | Nullable, непустой при передаче текст, максимум 2000, разрешены переносы строк |
| owner | Nullable, непустой при передаче однострочный текст, максимум 255 |
| treatmentDueDate, closedDate | Nullable, реальная календарная дата YYYY-MM-DD |

При POST пропущенные nullable-поля сохраняются как null. UUID выдаёт сервер,
начальная техническая версия риска назначается Hibernate (0).

`PATCH /api/projects/{id}/architecture/risks/{recordId}` требует `expectedVersion`
риска и хотя бы одно изменяемое поле из таблицы. Успех — **200 с полным агрегатом**.
Пропущенное поле сохраняет прежнее значение; null очищает только nullable-поле.
Объект версии без изменяемых полей отклоняется. Чужой риск даёт безопасный 404.

```json
{
  "expectedVersion": 0,
  "status": "ACCEPTED",
  "acceptanceJustification": "Решение ответственного за риск"
}
```

## Проверка объединённого состояния

Проверяется отдельное итоговое состояние до изменения managed-сущности:

- ACCEPTED требует непустое `acceptanceJustification`.
- CLOSED требует `closedDate`; у всех остальных статусов дата закрытия отсутствует.
- `acceptanceJustification` допустимо при любом статусе; автоматического удаления
  обоснования при переходе из ACCEPTED нет.
- Переход из CLOSED требует явного `closedDate:null` в том же PATCH; изменение других
  полей CLOSED сохраняет дату. Очистка обоснования существующего ACCEPTED запрещена.
- Даты проверяются на формат и календарную корректность; ограничений относительно
  текущей даты, дат друг друга или сроков обработки не добавлено.

`level`, `acceptanceVerification`, ID, принадлежность, техническая версия записи,
даты/показатели паспорта не принимаются от клиента. `expectedVersion` и
`expectedPassportVersion` — отдельные параметры конкурентного контроля.

## Транзакции, версии и блокировки

POST: валидация команды → общий `ProjectWriteLock` → lock паспорта → сравнение
expectedPassportVersion → persist/flush риска → атомарное увеличение версии паспорта
ровно на 1 → refresh/flush → полный DTO и оценка внутри той же write-транзакции.
Версия проекта и даты паспорта не меняются. Этот порядок общий с POST компонентов,
интеграций и инициализацией проверок. При одной версии паспорта один конкурентный
POST успешен, другой после ожидания получает 409 с реальной текущей версией.

PATCH: проверка существования родителей → lock строки риска с условием принадлежности
проекту → сравнение expectedVersion → проверка объединённого состояния → запись/flush
→ полный DTO и оценка в той же write-транзакции. Только версия риска увеличивается
ровно на 1; если значения прежние, применяется CAS технической версии и refresh.
Версии родителей и даты паспорта не меняются. Разные риски не блокируют друг друга.
FK NO ACTION сохраняются; перенос риска в другой проект не разрешён.

Чтение ответа переиспользует `ArchitectureReadService.cardAfterWrite` с MANDATORY.
Отдельного GET после commit нет. Ошибка на любом шаге, включая сборку ответа после
flush, откатывает всю запись и версии. Существующие GET остаются read-only.

## Оценка и безопасность

`level` вычисляется существующим оценщиком по матрице B2 и не сохраняется.
OPEN/IN_PROGRESS CRITICAL → BLOCKED, HIGH → ATTENTION_REQUIRED.
ACCEPTED HIGH/CRITICAL → ATTENTION_REQUIRED и отдельный `acceptedHighRisks` с обоснованием.
ACCEPTED возвращается с `acceptanceVerification=UNVERIFIED`, что не удостоверяет
согласование. MITIGATED/CLOSED сами проблемных причин не создают. Все остальные
причины сохраняются; `officialGoLiveApproval=false` всегда. Бюджет в агрегате отсутствует.

Используется общий строгий JSON-разбор B3.1/B3.2: только объект, неизвестные и
повторяющиеся поля, неверные типы и trailing JSON отклоняются. Максимум тела **32 KiB**,
глубина JSON 4, строка парсера 10 000 символов, число 20 символов; массивов в контракте нет.
Версии — целые 0…Long.MAX_VALUE−1. Коды точные, без смены регистра/пробелов.
Текст обрезается по краям, приводится к NFC, CRLF/CR к LF; недопустимые управляющие
символы, HTML/исполняемые фрагменты и явные секреты/URL/IP отклоняются существующим
валидатором. Это фильтр явных признаков, а не гарантия отсутствия чувствительной информации.
Содержимое команд и обоснования не добавляются в логи. Ошибки не отражают входной текст,
SQL, пути, Java-классы и stack trace.

| HTTP | Код / смысл |
|---|---|
| 400 | BAD_REQUEST / VALIDATION_ERROR; безопасное имя поля |
| 404 | PROJECT_NOT_FOUND / PASSPORT_NOT_FOUND / RISK_NOT_FOUND; чужой риск не раскрывает версию |
| 409 | PASSPORT_VERSION_CONFLICT при POST, RISK_VERSION_CONFLICT при PATCH; реальная currentVersion и versionResource=PASSPORT или RISK |
| 500 | DATABASE_ERROR, безопасное общее сообщение |

DELETE, frontend, операции проверок, автоматические миграции и изменение схемы не входят
в этап. Рабочая файловая БД и её копии не используются; тесты только in-memory H2.
