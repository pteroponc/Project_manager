## Реализация и границы

Добавлен `ArchitectureReadinessAssessmentService`, принимающий неизменяемый
`ArchitectureReadinessSnapshot` и `ArchitectureAssessmentContext`. Снимок содержит только
сведения для расчёта: паспорт, классы данных, среды, проверки, интеграции и риски. Конструктор
защитно копирует коллекции; вложенные записи и даты неизменяемы. Вход не содержит JPA-сущностей,
компонентов или health/прогресса/сроков/статуса проекта. Сервис не импортирует репозитории,
не загружает сущности, не сохраняет данные и не изменяет входные коллекции.

`ArchitectureAssessmentClockConfiguration` предоставляет внедряемый именованный Clock.
`newContext()` получает московскую дату один раз. `assess(snapshot, context)` часы не читает;
будущий портфель должен создать один контекст на запрос и переиспользовать его для всех строк.

Результат содержит статус, согласованную подпись, все причины с приоритетом, машинным кодом,
типом сущности, ID и безопасным сообщением; ближайшие проверки; принятые высокие риски;
дату/часовой пояс и `officialGoLiveApproval=false`. Коллекции результата неизменяемы.
Порядок причин детерминирован: приоритет, тип сущности, тип проверки/уровень риска, дата,
ID, код, сообщение. Ближайшие проверки и принятые риски также имеют стабильную сортировку.

## Согласованные правила

- Приоритет: BLOCKED → ATTENTION_REQUIRED → NOT_ASSESSED → READY. Причины меньшего
  приоритета сохраняются.
- BLOCKED: открытый/обрабатываемый CRITICAL-риск, обязательная BLOCKED-проверка,
  обязательная PRODUCTION_ADMISSION в CHANGES_REQUIRED, HIGH/CRITICAL-интеграция BLOCKED.
- ATTENTION_REQUIRED: открытый/обрабатываемый HIGH-риск, принятый HIGH/CRITICAL-риск,
  просроченная обязательная незавершённая проверка, стадия CHANGES_REQUIRED и другие
  обязательные проверки CHANGES_REQUIRED.
- NOT_ASSESSED: отсутствие/неполнота паспорта, стадия не APPROVED, отсутствующие типы
  проверок, незавершённые или противоречивые проверки, значимые интеграции PLANNED/IN_PROGRESS.
- READY: полный утверждённый паспорт и все десять типов корректно завершены либо явно
  неприменимы, других причин нет. Подпись: «Архитектура и ИБ: проверки завершены».
- required=true завершается только PASSED с actualDate; required=false требует NOT_REQUIRED
  с обоснованием и без actualDate. Для остальных статусов actualDate отсутствует.
  Дубликаты типов, неизвестные коды и противоречия не могут дать READY.
- Просрочка строго plannedDate < calculationDate. Нет срока — причина неполноты, без
  просрочки. Ближайшие обязательные незавершённые проверки: сегодня…+14 включительно;
  +15 вне горизонта. Горизонт сам статус не ухудшает.
- Все 16 клеток матрицы реализованы без сохранённого level. Принятые HIGH/CRITICAL всегда
  требуют внимания, возвращаются с обоснованием и UNVERIFIED; READY при них невозможен.
  MITIGATED/CLOSED и LOW/MEDIUM-риски сами проблемной причины не создают.
- LOW/MEDIUM-интеграции не меняют результат. Критичность компонентов информативна.

В плане PM-003 заменены прежние правила рисков/интеграций и подпись READY, разделены
PM-003B2.1 (расчёт) и PM-003B2.2 (последующее read API). Убрано неверное утверждение, что
FK один закрывает гонку: закреплены общая блокировка проекта, повторный подсчёт зависимостей
после блокировки, стабильный порядок блокировок при переносе и проверка обоих порядков.

## Оставшиеся границы

API, загрузка снимков из репозиториев и портфельная агрегация относятся к PM-003B2.2.
Операции записи, frontend, схема и миграции в этом этапе не менялись. Уровень риска
не сохраняется. Верификации полномочий принятия риска и официального допуска нет.

Обоснование принятого риска возвращается как пользовательский текст; будущий API/UI
должен экранировать его в контексте вывода. Ошибки входных данных дают причины NOT_ASSESSED,
не исправляют данные. Создание отсутствующих проверок или паспорта расчётом исключено.
