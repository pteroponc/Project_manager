## Реализация и контракт клиента

В разделе «Риски ИБ» доступно добавление при существующем паспорте.
Редактор существующего риска открывается по UUID, независимо от позиции в списке.
В заголовке — название именно выбранной записи. UUID и технические версии
не выводятся в пользовательский текст; UUID используется только в служебном
атрибуте кнопки и адресе запроса.

| Поле | Контракт формы |
|---|---|
| name | Обязательно, до 255 символов |
| description | Nullable, многострочный текст до 2000 |
| category | ACCESS, DATA, AVAILABILITY, INTEGRATION, PROCESS, OTHER |
| probability, impact | LOW, MEDIUM, HIGH, CRITICAL |
| owner | Nullable, до 255 |
| treatmentDueDate | Nullable, реальная дата ГГГГ-ММ-ДД |
| treatmentPlan | Nullable, многострочный текст до 2000 |
| status | OPEN, IN_PROGRESS, ACCEPTED, MITIGATED, CLOSED |
| closedDate | Nullable по статусу, реальная дата ГГГГ-ММ-ДД |
| acceptanceJustification | Nullable по статусу, многострочный текст до 2000 |

Все пять обязательных полей выбираются/заполняются явно. Пропущенные nullable-поля
POST не передаёт. При PATCH очищенное поле превращается в null; пропущенное
поле сохраняется. Текст обрезается по краям, нормализуется NFC, CRLF/CR приводятся
к LF. Введённый текст не переписывается в форме при ошибке. Окончательную проверку
небезопасного текста и секретов выполняет существующий backend.

Общий модуль `architecture-editor-validation.js` содержит только нормализацию
текста и календарную проверку. Он переиспользуется проверками C.3c и рисками;
прежние календарные правила проверок сохранены. Матрицы риска и оценки в нём нет.

### POST

`POST /api/projects/{id}/architecture/risks`, `Content-Type: application/json`:

```json
{
  "expectedPassportVersion": 981238,
  "expectedPassportInstanceId": "f071002a-3da5-4bc6-b472-6ba147514ea2",
  "name": "Новый риск",
  "category": "DATA",
  "probability": "MEDIUM",
  "impact": "HIGH",
  "status": "OPEN"
}
```

Числа/UUID в примере — из тестовых данных. В приложении используются исходные
токены загруженного паспорта, зафиксированные при открытии формы. Сервер выдаёт
ID и техническую версию новой записи. Клиент их не назначает.

### PATCH

`PATCH /api/projects/{id}/architecture/risks/{recordId}` использует исходную
версию выбранного риска и только изменённые поля. Например, у принятого риска
с уже заполненным обоснованием:

```json
{
  "expectedVersion": 981242,
  "probability": "HIGH",
  "impact": "MEDIUM"
}
```

Версии и instanceId паспорта в PATCH нет. Без изменений запрос не отправляется.
Для разных рисков используются независимые версии записей.

Пример очистки реквизитов и перехода из CLOSED в OPEN (при исходно заполненных
nullable-полях, включая обоснование):

```json
{
  "expectedVersion": 17,
  "description": null,
  "owner": null,
  "treatmentDueDate": null,
  "treatmentPlan": null,
  "status": "OPEN",
  "closedDate": null,
  "acceptanceJustification": null
}
```

`level`, acceptanceVerification, ID, принадлежность, техническая версия записи
и вычисленные показатели не являются полями формы и не отправляются.
После успеха применяется полный агрегат ответа без дополнительного GET.
Серверные уровень, оценка, причины и documentVersion отображаются без пересчёта.

## Проверка итогового состояния

- Любой ACCEPTED требует непустое acceptanceJustification, при любых probability
  и impact. Уменьшение вероятности/влияния не отменяет требования обоснования.
- CLOSED требует closedDate; у всех остальных статусов closedDate отсутствует.
- Выход из CLOSED требует явной очистки даты в форме. Она не очищается автоматически.
- При переходе из ACCEPTED обоснование сохраняется, если пользователь его не меняет.
  Оно допускается при любом другом статусе. Автоматической очистки нет.
- Проверяется всё итоговое состояние, а не только изменённые поля. Например,
  очистить обоснование существующего ACCEPTED, меняя только вероятность, нельзя.
- Даты проверяются на точный формат и существование календарной даты, включая
  високосные годы и четырёхзначный год 0000, как в валидаторе API.
  Ограничений относительно сегодняшней даты или дат друг друга нет.
- Даты — обычные текстовые поля с подсказкой формата. Неверная дата сохраняется
  для исправления, а не сбрасывается браузером. Статусы, даты и текст автоматически
  не исправляются и не заполняются.

## Принятые риски и оценка

Существующие представления сводки и риска сохраняют серверные данные:
уровень, обоснование, все причины оценки и список acceptedHighRisks.
Для серверного UNVERIFIED отображается **«Согласование принятия не проверено»**.
ACCEPTED не выдаётся за подтверждённое согласование. HIGH/CRITICAL не скрываются
из причин и отдельного списка. Официальный допуск по-прежнему не заявляется:
используется серверный officialGoLiveApproval=false и соответствующее пояснение.

В тестах намеренно возвращены несовпадающие с матрицей probability/impact и level:
интерфейс сохраняет уровень ответа, что подтверждает отсутствие расчёта в браузере.
Это специальные тестовые данные, не новая формула.

## Ошибки и защита черновика

Переиспользуется общая оболочка C.3a–C.3c:

- 400 — безопасные сообщения у полей, весь ввод сохраняется.
- 409 — ввод сохраняется, повторная отправка блокируется. Явная сверка загружает
  актуальный агрегат, не меняя исходные expectedVersion/expectedPassportVersion/instanceId.
- POST с PASSPORT_INSTANCE_CONFLICT объясняет удаление и пересоздание паспорта.
- PATCH с RISK_NOT_FOUND объясняет удаление выбранного риска. Сверка отдельно
  отличает отсутствие записи от нового instanceId паспорта. Для отсутствующих
  проекта/паспорта сохранены безопасные общие сообщения 404.
- При сети, 5xx или непригодном успешном ответе результат считается неизвестным:
  сервер мог выполнить запись. Автоматических повторов POST/PATCH нет.
- Двойное нажатие отправляет один запрос, поля блокируются на время отправки.
- Закрытие и навигация требуют подтверждения потери изменённого/неопределённого
  черновика. Защита действует между паспортом, дочерними редакторами и проектами,
  а также для истории браузера и beforeunload.
- Поздние success/error/comparison не меняют новую форму, другой проект или
  более свежий снимок. Полный ответ записи применяется через существующий
  защищённый callback, без отдельного GET.
- Сравнение показывает актуальные сведения рядом с вводом. Переход к свежему
  агрегату требует явного закрытия формы; автоматического переноса правок нет.
- Текст формы, заголовка и сравнения экранируется. SQL, пути, stack trace и сырые
  сообщения исключений не отображаются. Логирование содержимого не добавлялось.

### Ограничения

поля; матрица риска в тестовом сервере не реализована. Это не проверка формулы B2.

VM-контекстах; серверные транзакции/блокировки не менялись и повторно не доказывались.
