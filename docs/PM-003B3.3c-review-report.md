## Реализация

Маршрут DELETE /api/projects/{id} и успех 204 без тела сохранены.
ProjectDependencyService — общий источник семи scalar COUNT, причин запрета и
выбора кода для GET/DELETE. Считаются задачи, контрольные точки, архитектурный
паспорт, компоненты, интеграции, проверки, ИБ-риски. Полный архитектурный агрегат,
тексты и дочерние сущности для подсчёта не загружаются.

GET остаётся readOnly=true/REPEATABLE_READ; сохранены прежние поля/счётчики,
architectureImpactPreliminary=false. Один запрос читает проект для наличия/имени,
семь COUNT — зависимости. DELETE получает ProjectWriteLock, затем заново считает
те же зависимости в этой write-транзакции. Любая зависимость запрещает удаление
до первой записи. Иначе удаляется только проект и выполняется flush.

Старые code/error для только задач/точек сохранены:
PROJECT_HAS_BOARD_CARDS / PROJECT_HAS_MILESTONES; их сочетание, любые архитектурные
и смешанные зависимости — PROJECT_HAS_DEPENDENCIES. В 409 добавлен актуальный
impact с теми же полями/причинами, что GET. Отсутствующий проект — безопасный
PROJECT_NOT_FOUND/404. Каскадов, очистки зависимостей и автоматических повторов нет.

Счётчики архитектурных детей учитываются отдельно от паспорта; физические FK
требуют паспорт при наличии ребёнка. Классы/среды паспорта и классификация интеграций
защищены наличием соответствующих родителей, новых полей project impact не добавлено.

Убрана зависимость логического запрета от перехвата FK-ошибки DELETE: все известные
зависимости отклоняются до удаления. Неожиданный технический сбой обрабатывается
существующим безопасным DATABASE_ERROR без SQL/классов/путей/stack trace, не выдаёт
выдуманный impact с нулевыми счётчиками. Для runtime-гонок CREATE/DELETE подтверждены
404/409 без HTTP 500 и без сирот. Нового логирования содержимого нет.

Контракт/пример 409: docs/PM-003B3.3c-project-deletion-api.md. Общий план актуализирован:
исправлены шапка, состояние B1/B2/B3, уже существующий FK V003 и описание project impact.

| PATCH паспорта/классов/сред | Lock паспорта; его существование всегда даёт architecturePassportCount>0, DELETE проекта запрещён; ownership не создаётся и не переносится |
| PATCH архитектурных детей | Lock только ребёнка, собственный UUID/version; принадлежность неизменна, существующий паспорт блокирует DELETE проекта; независимость разных строк сохранена |
| Старые create/update проекта и release train | Не создают/не переносят зависимостей проекта; дополнительные обходные пути записи карточек/точек/архитектурных детей в runtime не найдены |

При исходном создании контрольной точки CAS UPDATE projects.version уже получал
DB-lock проекта до commit; если DELETE выигрывал, CAS не проходил и currentVersion=null
давал 404 до вставки точки. Но явного общего lock в начале пути не было. Теперь
create/patch/delete точек явно берут ProjectWriteLock до проверки версии/CAS/записи,
что закрепляет общий порядок и повторную проверку существования. API не менялся.

## Изолированная схема и FK V003

Новый набор использует только
jdbc:h2:mem:pmtest_project_dependencies;MODE=PostgreSQL;DB_CLOSE_DELAY=-1.
Initializer до подключения проверяет memory-префикс, создаёт отдельную старую
тестовую схему, затем применяет V002→V003→V004→V005 **только к этой памяти**.
Приложение теста использует ddl-auto=validate. Метаданные отдельно доказывают
fk_board_cards_project с NO ACTION/RESTRICT, NOT NULL project_id, индекс project_id;
реальная вставка сироты отклоняется. Одного validate для доказательства FK не используется.

Все остальные проверки Maven также только на одноразовых in-memory H2 **2.3.232**
под PM-000/TestDatabaseGuard. Рабочая файловая БД и её копии не открывались,
V003/V004/V005 к ним не применялись. Автоматическая миграция приложения не добавлена.

### Покрытие и сохранность

1. Пустой проект удаляется с 204, повторный DELETE и GET impact — 404. Полные снимки
   всех полей 12 таблиц до/после отличаются только отсутствующей целевой строкой проекта.
   Другие проекты, их задачи/точки/архитектура, поезда, ID, даты, версии, нули и
   максимальный бюджет сохранены.
2. Для каждого из семи видов зависимостей, задач+точек и всех зависимостей вместе
   проверены точные отдельные счётчики, причины, прежние коды/error, предварительный
   флаг false. GET impact полностью равен impact отказа DELETE. Все строки/версии
   после 409 прежние, сирот нет. Архитектурные дети имеют необходимый FK-паспорт,
   его счётчик также 1 — не подменяет счётчик ребёнка.
3. GET impact проверяется внутри активной readOnly/REPEATABLE_READ транзакции по
   JDBC isolation. Hibernate статистика: ровно восемь statements и один загруженный
   ProjectEntity. Spy запрещает load архитектурного агрегата. Повторные GET сохраняют
   полный снимок и не создают строк/версий.
4. После фактического DELETE/flush artificial failure в beforeCommit подтверждает
   SQL count(project)=0 внутри той же write-транзакции и бросает DataAccess-ошибку.
   Безопасный 500 DATABASE_ERROR; после rollback проект и весь снимок восстановлены.
   Это не ошибка до DELETE, транзакция действительно видела удалённую строку.
5. Полный старый набор сохраняет instanceId-регрессии A→DELETE→B, restart/V005,
   удаление пустого паспорта, независимые PATCH детей, чтение без изменений и PM-001/PM-002.

второго запроса не завершён. Park только опрашивает состояние, не задаёт порядок.

require(r) в стабильном сортированном порядке вне зависимости от направления.
Для transfer нет HTTP endpoint: проверяется сервисный PROJECT_NOT_FOUND, который
имеет действующий структурированный 404-обработчик. HTTP CREATE/DELETE проверяются через MockMvc.

## Ограничения

Гарантия сериализации относится к перечисленным runtime-писателям, использующим
общий протокол. Прямые SQL/внешние писатели вне протокола не покрыты; один FK на
H2 2.3.232 его не заменяет. Непредвиденный технический DB-сбой остаётся безопасной
500, а не фиктивным бизнес-конфликтом. Прежний проектный DELETE не требует версии:
это сохранённый API, новой модели подтверждения/токена проекта не добавлено.
Другие СУБД отдельно не удостоверялись. Новые frontend/авторизация/роли/аудит,
формула B2 и схемные изменения не входят в этап.
