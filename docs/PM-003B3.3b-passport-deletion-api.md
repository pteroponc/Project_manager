# PM-003B3.3b — безопасное удаление пустого паспорта

## Обязательное уточнение B3.3b: экземпляр паспорта

Паспорт возвращает серверный неизменяемый `instanceId` (UUID), техническая версия
нового паспорта остаётся 0, documentVersion=1.0. После удаления новый паспорт того
же проекта получает другой instanceId. Клиент не задаёт instanceId при POST и не
может менять его при PATCH.

**expectedPassportInstanceId обязателен** в JSON PATCH паспорта, POST компонента,
интеграции, риска и checks/initialize; в query DELETE паспорта и всех четырёх типов
дочерних записей. Он передаётся вместе с прежними числовыми версиями/confirmed.
POST самого паспорта сохраняет expectedProjectVersion; PATCH дочерней записи сохраняет
собственный UUID recordId и expectedVersion, без токена паспорта.

Отсутствующий/невалидный UUID — 400; после блокировок сначала проверяются наличие
и принадлежность ресурсов, затем instanceId, затем числовые версии. Несовпадение —
409 PASSPORT_INSTANCE_CONFLICT с реальной currentVersion и versionResource=PASSPORT,
без записей. Ресурс отсутствует — 404. Никакой подстановки токена текущего паспорта
для старой команды или автоматического повтора. Клиенту нужна новая карточка и
повторное подтверждение намерения. Числовые параметры и closed-list JSON/query
дополнены только этим полем. Это изменение контракта обязательно для клиентов.

Пример query дополнительно содержит
`expectedPassportInstanceId=11111111-1111-4111-8111-111111111111`;
в JSON-команде добавляется одноимённое строковое поле с UUID из актуального DTO.
Полная спецификация и ручная миграция: `docs/PM-003B3.3b-manual-V005.md`.

## Контракт

```text
DELETE /api/projects/{id}/architecture?expectedVersion=7&confirmed=true&expectedPassportInstanceId=11111111-1111-4111-8111-111111111111
```

`expectedVersion` — техническая версия паспорта. `confirmed` — точная строка `true`.
Все три query-параметра обязательны и одиночные; неизвестные/повторные/невалидные — 400.
Как в B3.3a: версии — десятичные целые 0…Long.MAX_VALUE−1, без знаков, пробелов,
дробей, экспоненты и ведущих нулей кроме `0`. `TRUE`, `false`, `1` не подтверждают
удаление. JSON-тело не заменяет query-параметры.

Паспорт можно удалить только при нуле всех шести счётчиков:

- компоненты;
- интеграции (в том числе с классификацией);
- проверки;
- ИБ-риски;
- классы данных самого паспорта;
- среды паспорта.

Дочерние записи не удаляются автоматически. Классы/среды пользователь сначала
явно очищает существующим PATCH с `dataClasses:[]`, `environments:[]` и актуальной
версией паспорта. Статусы/содержимое зависимостей значения не имеют: даже завершённая
проверка или закрытый риск запрещают удаление паспорта.

## Транзакция и блокировки

Одна сервисная write-транзакция:

1. Проверить query-параметры до записей.
2. Взять общий ProjectWriteLock, затем PESSIMISTIC_WRITE на паспорт.
3. Проверить актуальную техническую версию паспорта.
4. Повторно посчитать все шесть видов зависимостей скалярными COUNT в этой же
   транзакции под блокировками. Используется шесть ограниченных запросов без
   загрузки текстов/сущностей. Общий чистый сборщик impact применяется и для GET,
   и для отказа DELETE; названия счётчиков и причины совпадают.
5. При любой зависимости вернуть 409 без записей и без очистки наборов.
6. Удалить только паспорт, flush. Атомарно увеличить техническую версию проекта
   ровно на 1 через существующий CAS, refresh/flush. Остальные поля проекта прежние.
7. После flush вызвать cardAfterWrite/MANDATORY, собрать полный DTO с существующей
   оценкой B2 внутри той же write-транзакции. Отдельного GET после commit нет.

При ошибке любой стадии откатываются паспорт и версия проекта. FK NO ACTION,
отсутствие CascadeType.REMOVE/orphanRemoval сохранены. Автоматических повторов нет.

POST дочерних записей/initialize тоже блокируют проект → паспорт. Если создание
выиграло, старая версия DELETE даёт 409 версии; повтор с актуальной версией даёт
409 с зависимостями. Если DELETE выиграл, создание получает PASSPORT_NOT_FOUND,
проект остаётся существующим, сирот нет. PATCH паспорта блокирует паспорт:
PATCH первым → DELETE после ожидания получает 409 версии; DELETE первым → PATCH
после ожидания получает 404. Два DELETE дают один 200 и один 404.

## Ответы

**200:** существующий полный архитектурный агрегат; `passport=null`, пустые
dataClasses/environments/components/integrations/checks/risks, оценка NOT_ASSESSED
с причиной PASSPORT_MISSING. `project.version` увеличена на 1; бюджет отсутствует,
officialGoLiveApproval=false. Пользовательская версия паспорта не перенумеровывается:
паспорт отсутствует. У других паспортов documentVersion=1.0 и даты/версии прежние.
Повторные GET паспорт или проверки не создают.

**409 версии:** существующий безопасный формат PASSPORT_VERSION_CONFLICT,
реальная currentVersion, versionResource=PASSPORT. Проверяется до зависимостей.

**409 зависимостей:**

```json
{
  "code": "PASSPORT_HAS_DEPENDENCIES",
  "error": "Passport has dependencies",
  "currentVersion": 7,
  "versionResource": "PASSPORT",
  "impact": {
    "projectId": "p",
    "passportPresent": true,
    "componentCount": 1,
    "integrationCount": 0,
    "checkCount": 0,
    "securityRiskCount": 0,
    "dataClassCount": 0,
    "environmentCount": 0,
    "deletionAllowed": false,
    "blockers": ["Компоненты: 1"]
  }
}
```

`impact` имеет тот же контракт, что GET `/api/projects/{id}/architecture/deletion-impact`,
но значения пересчитаны после locks внутри write-транзакции. Нет содержимого
паспорта/рисков и фиктивных версий.

**404:** PROJECT_NOT_FOUND или PASSPORT_NOT_FOUND. Повтор DELETE — 404.
**400:** BAD_REQUEST / VALIDATION_ERROR, безопасное имя поля без значения.
**500:** DATABASE_ERROR, общее сообщение без SQL, путей, Java-классов и stack trace.
Нового логирования содержимого или обоснований не добавлено.

Расширение DELETE проекта, frontend, схема/миграции и datasource-профили в этап
не входят. Формула готовности не меняется. Тесты только на отдельных одноразовых
in-memory H2; рабочая файловая БД и её копии не открываются.
