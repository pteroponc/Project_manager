## Реализация

| Метод | Маршрут | Результат |
|---|---|---|
| POST | `/api/projects/{id}/architecture/risks` | 201, полный архитектурный агрегат |
| PATCH | `/api/projects/{id}/architecture/risks/{recordId}` | 200, полный архитектурный агрегат |

Контракт и примеры команд: `docs/PM-003B3.2c-risks-api.md`.

POST проверяет обязательные name/category/probability/impact/status и бизнес-состояние,
берёт общий lock проекта, затем паспорта, сравнивает expectedPassportVersion,
создаёт риск с UUID сервера и версией Hibernate=0; увеличивает техническую версию
паспорта ровно на 1. Версия проекта и даты паспорта не меняются.
Компоненты, интеграции и проверки автоматически не создаются.

PATCH проверяет существование родителей, блокирует строку риска с условием
принадлежности проекту, сравнивает expectedVersion. Чужой риск — безопасный 404
RISK_NOT_FOUND без раскрытия версии. Итоговое состояние сначала собирается отдельно
от managed-сущности: ACCEPTED требует обоснование; CLOSED требует closedDate,
у остальных статусов closedDate=null. Обоснование разрешено и сохраняется при
других статусах. Пропущенные поля прежние, null очищает только nullable-реквизиты.
Только версия риска +1, включая PATCH прежних значений через CAS/refresh при no-op.
Разные риски редактируются независимо, без изменения версий родителей.

Запись, flush, загрузка полного DTO и оценка — одна write-транзакция с повторным
использованием `cardAfterWrite`/MANDATORY из B2/B3. GET после commit не выполняется.
Искусственный сбой после flush проверяет полный откат риска, полей и версий.

Строгий JSON parser и version/text/NFC/date validators переиспользованы без изменения
правил старых API. Запрещены клиентские id/projectId/version/level/acceptanceVerification
и прочие неизвестные поля. Ограничение тела 32 KiB и длины полей закреплены в контракте.
Ошибки 400/404/409/500 безопасны, входные значения не отражаются; 409 содержит
реальные currentVersion и versionResource=PASSPORT или RISK. Нового логирования нет.

Схема/сущности/миграции, DTO и формула B2 не менялись. level вычисляется при сборке
существующего read DTO, не хранится. Все причины сохраняются, ACCEPTED возвращается
как UNVERIFIED, acceptedHighRisks содержит принятые HIGH/CRITICAL с обоснованием;
officialGoLiveApproval=false, documentVersion=1.0. Бюджет в ответах отсутствует.

### Покрытие

1. Минимальный и полный POST: UUID, version=0, nullable-поля, нормализация NFC/CRLF,
   прошлые и будущие корректные даты, версия паспорта +1, полный ответ равен GET.
2. PATCH: сохранение пропущенных значений, очистка всех nullable-полей, ровно один
   прирост версии при изменениях и прежних значениях; родители и даты паспорта прежние.
3. ACCEPTED/CLOSED и обратные переходы: требуется объединённое непротиворечивое
   состояние, обоснование сохраняется вне ACCEPTED, дата CLOSED явно очищается при
   переходе. Неудачный PATCH с несколькими полями не меняет даже валидные поля.
4. Отсутствующие обязательные поля POST, null, неизвестные/неизменяемые поля,
   enum, типы, версии, дубликаты JSON-полей, trailing JSON и oversized body.
5. Длины 255/2000 и превышение, пустые/опасные строки, nullable-типы, некорректные
   календарные даты и форматы. NFC до проверки длины, 2024-02-29 принимается.
6. Отсутствующие проект/паспорт/риск, чужой риск и устаревшие версии: безопасные
   коды и действительные currentVersion/versionResource; полный снимок без изменений.
7. Все **16 клеток матрицы** проверены через POST и полный API-ответ, включая level
   и итоговый статус при полном утверждённом паспорте с завершёнными проверками.
8. OPEN/IN_PROGRESS CRITICAL блокируют; HIGH требуют внимания; ACCEPTED HIGH/CRITICAL
   остаются в acceptedHighRisks с обоснованием/UNVERIFIED и требуют внимания.
   MITIGATED/CLOSED возвращают READY при отсутствии других причин. Совмещение
   принятого риска, открытого CRITICAL, незавершённых проверок и стадии паспорта
   сохраняет все причины. officialGoLiveApproval=false, documentVersion=1.0.
9. Сбой на загрузке DTO после flush POST подтверждает внутри активной write-транзакции
   новую строку риска и увеличенную версию паспорта, затем JPA-ошибка откатывает всё.
   Повторный POST после снятия сбоя успешен. После flush PATCH подтверждены новая
   версия и CLOSED; DataAccess-ошибка откатывает все поля, дату и версию. Ответы 500
   не раскрывают текст искусственного внутреннего исключения.
10. Ответ видит свою незакоммиченную запись; GET из другого соединения одновременно
    видит прежнее состояние. После commit JSON полностью совпадает с write DTO.
11. Полные снимки 12 таблиц до/после повторных GET совпадают по всем полям, датам и
    версиям. Проекты без паспорта/пустые наборы не дополняются. После POST/PATCH
    изменены только целевой риск и техническая версия его паспорта при создании.
    Остальные риски, проекты, задачи, поезда, контрольные точки, компоненты,
    интеграции/классы, проверки, классы/среды паспорта сохранены; нули и максимальный
    существующий бюджет также сохранены.
12. Полный прежний набор B3.2b/B3.2a/B3.1/B2/B1/PM-001/PM-002 прошёл без регрессий.

### Конкурентность

| Сценарий | Подтверждённый результат |
|---|---|
| POST риск / POST риск с одной версией паспорта | Один 201, один 409 PASSPORT_VERSION_CONFLICT/currentVersion=1, один риск |
| Риск первым / компонент вторым | 201 риск, 409 компонент; только риск создан |
| Компонент первым / риск вторым | 201 компонент, 409 риск; риск не создан |
| Риск первым / интеграция вторым | 201 риск, 409 интеграция; интеграция/классы не созданы |
| Интеграция первой / риск вторым | 201 интеграция, 409 риск; риск не создан |
| Риск первым / initialize вторым | 201 риск, 409 initialize; проверки не созданы |
| Initialize первым / риск вторым | 201 initialize, 409 риск; ровно десять проверок, риска нет |
| PATCH одной версии одного риска | Второй ждёт lock строки; один 200, один 409 RISK_VERSION_CONFLICT/currentVersion=1, данные Winner сохранены |
| PATCH разных рисков | Второй завершает 200 до освобождения первого; оба риска version=1, версии родителей прежние |

Используются отдельные соединения/транзакции и CountDownLatch. До освобождения первой
транзакции проверяются реальные H2 INFORMATION_SCHEMA.SESSIONS: BLOCKED, BLOCKER_ID,
SQL ожидаемой таблицы, Future второго запроса ещё не завершён. Короткий park только
опрашивает состояние ожидания, порядок не основан на случайных задержках.
После сценариев проверено отсутствие сирот рисков и паспортов.
