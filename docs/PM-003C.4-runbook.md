# PM-003C.4 — воспроизводимый сквозной запуск

## Изоляция

Запускать из корня репозитория, Java 21 и Maven 3.9.9. Это **тестовый** запуск,
не `java -jar`, не обычный профиль и не `architecture-preview.cjs`.
Рабочую БД, её копии и URL файлового H2 не использовать.

`ArchitectureBrowserServerTest` включается только явным `pm.c4.browser=true`.
До первого JDBC он проверяет сгенерированный `jdbc:h2:mem:pmtest_c4_<UUID>` через
существующий `TestDatabaseGuard`. Подготовка использует существующий
`ArchitectureSchemaMigrationIntegrationTest.setup`: старую тестовую схему,
V002 → V003, затем оригинальные V004 → V005. Всё — в одном JVM и только в памяти.
Добавлены исключительно вымышленные названия. Схема и выпущенные миграции не меняются.

Spring запускается с явно активным `smoke`, собственным URL и обязательными
параметрами `ddl-auto=validate`, `sql.init.mode=never`, H2 Console выключена,
`server.address=127.0.0.1`, `server.port=4184`. Конфигурация smoke `create-drop`
перекрыта явным аргументом `validate`, проверенным после старта. Обе существующие
PM-000 защиты остаются активны на тестовом classpath. Сервер не попадает в рабочий JAR.

Тестовый servlet filter только записывает **реальные** ответы API в
`tmp/PM-003C.4-http.jsonl`; он не генерирует и не подменяет ответы. Файл содержит
вымышленные сведения этой памяти. Не переносить механизм на рабочие данные.

## Команды

Порт 4184 должен быть свободен. Первая консоль:

```powershell
mvn.cmd -Dtest=ArchitectureBrowserServerTest -Dpm.c4.browser=true test
```

В фактической среде Maven расположен здесь (эквивалент первой команды):

```powershell
& 'C:\Users\Polina\Documents\Codex\2026-04-28-new-chat\tools\apache-maven-3.9.9\bin\mvn.cmd' '-Dtest=ArchitectureBrowserServerTest' '-Dpm.c4.browser=true' test
```

Дождаться `C4_REAL_SERVER_READY`. Открыть:

```text
http://127.0.0.1:4184/?view=projects&query=Atlas&quarter=Q1
```

Сервер привязан только к IPv4 loopback. Для независимого второго origin можно
открыть `http://localhost:4184/?view=project-architecture&project=zero`:
браузерные origin/storage различны, backend и тестовая память общие.
Это не разные процессы/профили браузера; аутентификационных сессий в приложении нет.

## Последовательность основного прогона

1. Открыть `C4 Fictional Atlas`, архитектуру, вернуться в карточку и реестр.
   Проверить `query=Atlas&quarter=Q1` и Back. Снова открыть архитектуру.
2. Создать паспорт HIGH / NOT_STARTED / NEW_SOLUTION, без архитектора и наборов.
   Проверить `1.0`. Редактировать: архитектор `Fictional Architect`, PUBLIC и TEST;
   сохранить, затем очистить архитектора, PUBLIC и TEST и сохранить ещё раз.
3. Создать `Atlas backend`: BACKEND, LOW, false, 0. Создать `Atlas queue`: QUEUE,
   MEDIUM, true, 5. Открыть именно queue и изменить на false, 0, назначение
   `Fictional queue processing`. Проверять UUID по реальному PATCH, а не позиции.
4. Создать `Atlas exchange`: Fictional source → Fictional destination, OUTBOUND,
   API, NONE, HIGH, PLANNED, PUBLIC. Отредактировать READY, заменить PUBLIC на INTERNAL.
5. Явно подтвердить создание десяти проверок. Согласование архитектуры: PASSED без
   даты должно оставить ошибку и ввод; добавить `2026-10-24`, сохранить.
   Требования ИБ: required=false / NOT_REQUIRED без комментария — ошибка;
   добавить `Fictional scope excludes this check`, сохранить. Набор не создаётся при GET.
6. Создать `Atlas accepted risk`: DATA, HIGH, CRITICAL, ACCEPTED. Без обоснования
   получить ошибку формы; добавить `Fictional review evidence pending`, сохранить.
   Сводка: CRITICAL, ATTENTION_REQUIRED, acceptedHighRisks/UNVERIFIED, все причины,
   officialGoLiveApproval=false. Перевести CLOSED: без даты ошибка; добавить
   `2026-10-24`, сохранить; обоснование не очищается автоматически.
7. Два документа открывают один риск до изменений. В первом owner=`First session saved`,
   во втором owner=`Second session draft`. Сохранить первый, затем второй:
   настоящий 409, второй ввод сохранён, кнопка записи заблокирована. Во втором
   коротком прогоне аналогичный конфликт проверен через раздельные origin
   127.0.0.1 и localhost (owner `Origin one saved` / `Origin two retained draft`).
8. В первой форме паспорта снова добавить PUBLIC и TEST. Открыть удаление паспорта:
   все шесть счётчиков ненулевые, шесть причин, подтвердить нельзя. Отменить.
   Явным PATCH убрать PUBLIC и TEST.
9. Создать вторую интеграцию `Atlas retained exchange`: Fictional left → Fictional right,
   INBOUND, EVENT, NONE, LOW, READY, PERSONAL. Удалить **Atlas exchange**, подтвердив
   её название; другая интеграция и PERSONAL должны сохраниться.
10. Удалить первую проверку отдельным подтверждением, перезагрузить страницу:
    девять проверок, нет кнопки дополнения. Дополнительный HTTP-запрос ниже
    подтверждает серверный 409 для непустого набора, не заменяет UI-проверку.
11. Отдельными подтверждениями удалить оставшиеся девять проверок, два компонента,
    оставшуюся интеграцию и риск. Не использовать каскады или массовое удаление.
12. Во втором документе открыть PATCH пустого паспорта, ввести
    `Stale passport draft`, не сохранять. В первом удалить пустой паспорт:
    шесть нулей, проект остаётся. Создать новый LOW / NOT_STARTED / NEW_SOLUTION.
    Сохранение старой формы должно получить PASSPORT_INSTANCE_CONFLICT, ввод сохранён.
    Перезагрузка первого документа показывает новый пустой паспорт, не старый ввод.

Для сценария 10 дополнительная проверка сервера в другой PowerShell-консоли:

```powershell
$root = 'http://127.0.0.1:4184/api/projects/zero/architecture'
$before = Invoke-RestMethod $root
$body = @{expectedPassportVersion=$before.passport.version;expectedPassportInstanceId=$before.passport.instanceId} | ConvertTo-Json
$result = Invoke-WebRequest "$root/checks/initialize" -Method Post -ContentType application/json -Body $body -SkipHttpErrorCheck
$result.StatusCode # 409, CHECKS_ALREADY_EXIST
$after = Invoke-RestMethod $root
if (($before | ConvertTo-Json -Depth 30 -Compress) -ne ($after | ConvertTo-Json -Depth 30 -Compress)) { throw 'Unexpected change' }
```

Команда `-SkipHttpErrorCheck` требует PowerShell 7. Вся проверяемая запись, кроме
этого явно отмеченного отрицательного HTTP-запроса, в основном прогоне — через UI.

После основного прогона, **до нового запуска**, сохранить проверяемую выжимку:

```powershell
node src/test/js/architecture-e2e-evidence.cjs
```

Анализатор проверяет реальные ответы, UUID, версии, сохранённые состояния,
классификацию другой интеграции, причины, конфликты и старые проекты/поезда;
он не управляет браузером и не делает запросы/подключения к БД. Выход:
`docs/review/PM-003C.4/http-evidence.json`. UUID/время будут новыми при каждом прогоне.
Если планировать второй запуск для скриншотов, сохранить исходный JSONL под новым
именем и передать его анализатору аргументом. Уже выполнено:

```powershell
node src/test/js/architecture-e2e-evidence.cjs tmp/PM-003C.4-main-http.jsonl
```

## Остановка и общие проверки

Во второй консоли, из корня репозитория:

```powershell
Set-Content -LiteralPath tmp/PM-003C.4-stop.txt -Value stop
```

Дождаться `C4_REAL_SERVER_STOPPED` и BUILD SUCCESS. Контекст закрывается, затем
выполняется SHUTDOWN **этой же памяти**. Стоп-маркер удаляется. Есть предел 45 минут:
при забытом сервере тест завершается с ошибкой и закрывает контекст/память.
При аварийном завершении JVM память также исчезает.

Только после остановки (не запускать clean при работающем тесте):

```powershell
mvn.cmd clean verify
node --test src/test/js/*.test.cjs
node --check src/test/js/architecture-e2e-evidence.cjs
git diff --check
```

Обычный полный Maven-прогон пропускает только интерактивный метод этого класса;
негативная проверка unsafe URL выполняется всегда. Существующие тесты используют
свою PM-000 in-memory изоляцию. Изменений рабочего datasource и автозапуска миграций нет.
