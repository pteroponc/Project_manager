## Что реализовано

- «Создать паспорт» при отсутствии и «Редактировать паспорт» при наличии.
- Все редактируемые реквизиты: criticality, stage, solutionType, architect, solutionSummary,
  availabilityRequirement, recoveryRequirement, lastReviewDate, dataClasses, environments.
- Неполный черновик: архитектор и остальные необязательные поля могут быть пустыми;
  оба набора могут быть пустыми. В новой форме стадия по умолчанию NOT_STARTED,
  тип решения NEW_SOLUTION; критичность пользователь выбирает явно.
- При редактировании заполняются реальные значения загруженного снимка. Технические версии
  и instanceId не являются полями формы и не показываются пользователю.
- Пользовательская версия берётся из `documentVersion` ответа; после создания отображается 1.0.
- После POST/PATCH применяется полный агрегат ответа, включая серверную оценку и коллекции.
  Дополнительный GET автоматически не выполняется.
- Удаления паспорта и записей дочерних сущностей нет. Их разделы остаются для чтения.
- Использованы существующие классы форм, кнопок, панелей и диалогов; CSS дополнен только
  раскладкой полей/наборов и переносами текста. Дизайн приложения не перерабатывался.

## Точный контракт запросов

Путь: `/api/projects/{id}/architecture`, `Content-Type: application/json`.

Минимальная форма отправляет POST:

```json
{
  "expectedProjectVersion": 981237,
  "criticality": "HIGH",
  "stage": "NOT_STARTED",
  "solutionType": "NEW_SOLUTION",
  "dataClasses": [],
  "environments": []
}
```

Число выше — значение из изолированной тестовой фикстуры. В приложении берётся
`project.version` исходного загруженного агрегата. Пустые nullable-поля POST пропускает.
Ни documentVersion, ни техническую версию новой записи клиент не назначает.

Пример PATCH при очистке архитектора, даты и наборов:

```json
{
  "expectedVersion": 981238,
  "expectedPassportInstanceId": "f071002a-3da5-4bc6-b472-6ba147514ea2",
  "architect": null,
  "lastReviewDate": null,
  "dataClasses": [],
  "environments": []
}
```

Токены берутся из **исходного паспорта этой формы**. PATCH включает только изменённые поля.
Пропущенное поле не очищается. Пустое необязательное поле преобразуется в `null`, пустой набор
— в `[]`. Порядок кодов при сравнении наборов незначим. «Не указано» не подставляется в ввод.
При отсутствии изменений PATCH не отправляется, пользователь видит соответствующее сообщение.

Текст нормализуется NFC, крайние пробелы убираются, CRLF/CR переводятся в LF без схлопывания
внутренних переносов. Отправка не меняет сам ввод формы: при ошибке он остаётся в исходном виде.
maxlength: architect 255, solutionSummary 2000, availabilityRequirement/recoveryRequirement 1000.
Дата — необязательное поле `type=date`, без ограничений относительно сегодняшней даты.
Закрытые наборы имеют 6/5 чекбоксов и не создают дубликатов кодов.
Полные проверки текста и данных выполняет действующий backend; клиент не дублирует его фильтр секретов.

Числовые версии, не представимые как безопасные целые JavaScript, блокируют отправку с понятным
сообщением. Клиент не отправляет округлённый технический счётчик. Это ограничение текущего JSON/JS-клиента;
контракт Long backend не менялся.

## Ошибки и конфликты

- 400: известные fieldErrors отмечаются рядом с полями, весь ввод и выбранные наборы сохраняются.
  Технический текст исключений в страницу не попадает. После исправления разрешена новая явная отправка.
- 409: сохраняется ввод, блокируется повторное сохранение этой формы, объясняется конфликт.
  PASSPORT_INSTANCE_CONFLICT явно обозначает удаление и повторное создание паспорта.
- «Загрузить актуальные сведения для сверки» выполняет только GET. Рядом показываются актуальные
  деловые поля и ввод пользователя. Изменения ввода после загрузки также отражаются в сравнении.
  Технические токены исходной формы не заменяются.
- Различаются отсутствие паспорта, тот же экземпляр и новый instanceId. Для перехода на свежие
  сведения нужна отдельная кнопка и подтверждение потери черновика. После этого пользователь
  может **явно** открыть новую форму; автоматического переноса правок/повтора записи нет.
- 404 сохраняет ввод и предлагает сверку существования ресурса.
- Сеть, 5xx или некорректный успешный ответ считаются неподтверждённым результатом записи:
  сервер мог её выполнить. Ввод сохраняется, POST/PATCH не повторяется автоматически и повторное
  сохранение блокируется до осознанного перехода на свежие сведения.

## Навигация и конкурентные ответы

На время запроса форма блокирует поля и кнопку сохранения; повторный submit игнорируется.
Существование отдельной сессии формы проверяется в success/error/finally и сверке. Ответ старой
формы не может изменить новый редактор или другой проект. Архитектурный экран дополнительно
проверяет поколение запроса и проект перед применением агрегата; открытие формы инвалидирует
старые чтения, более новое чтение инвалидирует прежний callback записи.

Закрытие, меню, возврат и открытие другого проекта требуют подтверждения при несохранённых
изменениях. Пока форма остаётся открытой, переключение разделов сохраняет её поля.
При Back/Forward текущая запись истории временно восстанавливается; переход выполняется
после подтверждения. Учтён случай подтверждения до завершения возврата истории.
Перезагрузка/закрытие страницы защищены `beforeunload`.

При уходе во время запроса предупреждение прямо говорит, что закрытие не отменяет запись.
Её поздний результат игнорируется в покинутой форме. Отмены/повторной записи в фоне нет.
