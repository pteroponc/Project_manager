# PM-003B3.2a — компоненты и интеграции: POST/PATCH

База: `codex-dev`, `3cc8a2a61a0b0c1a72f987789e7c2703f47cfb95`.
Используются модель B1b, актуальный расчёт B2, полный DTO B2.2, правила JSON/текста B3.1.

## Маршруты

| Метод | Путь | Успех |
|---|---|---|
| POST | `/api/projects/{id}/architecture/components` | 201, полный архитектурный агрегат |
| PATCH | `/api/projects/{id}/architecture/components/{recordId}` | 200, полный агрегат |
| POST | `/api/projects/{id}/architecture/integrations` | 201, полный агрегат |
| PATCH | `/api/projects/{id}/architecture/integrations/{recordId}` | 200, полный агрегат |

Content-Type `application/json`; ID новой записи — UUID, выдаётся сервером.
Полный ответ имеет прежние `project`, `passport`, `dataClasses`, `environments`, `components`,
`integrations`, `checks`, `risks`, `assessment`. Каждая интеграция содержит свой `dataClasses`.
Бюджет не возвращается. Формула не меняется: все причины, принятые HIGH/CRITICAL-риски
с обоснованием/UNVERIFIED и `officialGoLiveApproval=false` сохраняются.
Критичность компонентов информативна; LOW/MEDIUM-интеграции оценку не ухудшают.

## Техническая версия и пользовательская версия

Новый паспорт имеет пользовательскую версию **1.0**. В JSON это отдельное read-only
`passport.documentVersion: "1.0"`; значение не вычисляется из `version` и не изменяется
этими операциями. Действующая модель не хранит историю редакций: поле возвращается как
постоянные метаданные DTO без изменения схемы. Правила будущего изменения номера документа
в этом задании не вводятся.

`passport.version` — прежний технический целочисленный счётчик. Паспорт после B3.1 POST
имеет техническую версию 0. Каждый успешный POST дочерней записи увеличивает её ровно на 1.
Для POST передаётся **expectedPassportVersion**, а не пользовательское `1.0`.
Новая дочерняя запись получает техническую версию 0 при persist/flush через Hibernate.

PATCH принимает **expectedVersion самой записи** и увеличивает только её техническую
версию ровно на 1, в том числе при прежних значениях или замене набора на прежний набор.
Версия паспорта и версия проекта не меняются. POST дочерней записи не меняет версию
проекта. Даты/реквизиты самого паспорта этими операциями не меняются: POST изменяет
только технический счётчик состава, PATCH — только дочернюю запись/её классификацию.

## Поля компонента

| Поле | Тип / допустимые значения | POST | PATCH/null |
|---|---|---|---|
| `name` | Текст до 255 | Обязательно | Можно менять, null запрещён |
| `componentType` | FRONTEND, BACKEND, DATABASE, QUEUE, EXTERNAL_SERVICE, INFRASTRUCTURE | Обязательно | null запрещён |
| `criticality` | LOW, MEDIUM, HIGH, CRITICAL | Обязательно | null запрещён |
| `externalComponent` | JSON boolean | Обязательно, false — допустимое значение | null запрещён |
| `position` | JSON integer 0…2147483647 | Обязательно, 0 — допустимое значение | null запрещён |
| `purpose` | Многострочный управленческий текст до 1000 | Можно пропустить/null | null очищает |
| `platform` | Однострочный текст до 255 | Можно пропустить/null | null очищает |

Одинаковые position разрешены моделью; порядок ответа — position, затем ID. Сервер не
вводит новый алгоритм автонумерации/перестановки компонентов.

Пример POST:

```json
{
  "expectedPassportVersion": 0,
  "name": "Сервис обработки заявок",
  "componentType": "BACKEND",
  "criticality": "HIGH",
  "externalComponent": false,
  "position": 0,
  "purpose": "Обработка заявок.\nПодготовка управленческой отчётности.",
  "platform": null
}
```

## Поля интеграции

| Поле | Тип / допустимые значения | POST | PATCH/null |
|---|---|---|---|
| `name` | Текст до 255 | Обязательно | null запрещён |
| `sourceSystem` | Деловое наименование системы до 255 | Обязательно | null запрещён |
| `targetSystem` | Деловое наименование системы до 255 | Обязательно | null запрещён |
| `direction` | INBOUND, OUTBOUND, BIDIRECTIONAL | Обязательно | null запрещён |
| `interactionType` | API, EVENT, FILE_EXCHANGE, BATCH, OTHER | Обязательно | null запрещён |
| `authCategory` | NONE, SERVICE_ACCOUNT, OAUTH2, MTLS, CERTIFICATE, OTHER | Обязательно | null запрещён |
| `criticality` | LOW, MEDIUM, HIGH, CRITICAL | Обязательно | null запрещён |
| `readiness` | PLANNED, IN_PROGRESS, READY, BLOCKED | Обязательно | null запрещён |
| `dataClasses` | Набор закрытых кодов | Обязательно, минимум 1 | Замена целиком, минимум 1; null запрещён |
| `responsibleParty` | Однострочный текст до 255 | Можно пропустить/null | null очищает |
| `comment` | Многострочный управленческий текст до 1000 | Можно пропустить/null | null очищает |

Классы: PUBLIC, INTERNAL, CONFIDENTIAL, PERSONAL, PAYMENT, COMMERCIAL_SECRET.
Дубликаты запрещены, максимум 6 кодов. Классы интеграции не подменяют классы паспорта.
При PATCH отсутствие `dataClasses` сохраняет прежний набор, переданный массив заменяет
его целиком. `[]` и null отклоняются до записи. Ответ содержит отсортированные коды.
Строки классификации других интеграций не затрагиваются.

Пример POST:

```json
{
  "expectedPassportVersion": 1,
  "name": "Передача управленческой отчётности",
  "sourceSystem": "Система заявок",
  "targetSystem": "Управленческий контур",
  "direction": "OUTBOUND",
  "interactionType": "API",
  "authCategory": "OAUTH2",
  "criticality": "HIGH",
  "readiness": "PLANNED",
  "dataClasses": ["INTERNAL", "PERSONAL"],
  "responsibleParty": null,
  "comment": null
}
```

Пример PATCH интеграции:

```json
{"expectedVersion":0,"comment":null,"dataClasses":["INTERNAL"]}
```

## PATCH и валидация

Пропущенное поле сохраняется, явный null допустим только для nullable-поля.
PATCH только с expectedVersion без изменяемых полей — 400. Поля ID, projectId/passport,
version, documentVersion, createdAt/updatedAt, вычисленные показатели и чужие коллекции
клиент не задаёт. Переноса записи в другой проект нет.

Переиспользуются B3.1: строгие JSON-типы, коды в точном верхнем регистре, версии integer
0…9223372036854775806, trim/NFC для текста и длина после нормализации в UTF-16 единицах.
Пустые строки запрещены; nullable-значение очищается через null. CRLF/CR в описаниях
приводятся к LF, внутренняя многострочность и пробелы сохраняются. Запрещённые
управляющие/FORMAT-символы, HTML/исполняемые фрагменты и явные URL/IP/секреты отклоняются.
Имена систем — деловые названия без адресов и конфигураций. Фильтр явных шаблонов не
заменяет ручной контроль содержания и будущие контекстное экранирование/контур доступа.

Строгий JSON parser теперь общий для архитектурных write-маршрутов; старые API не
меняются. Корень — объект; неизвестные и повторяющиеся JSON-поля, trailing JSON,
неверные типы и невалидный JSON — 400. Максимум тела 32 KiB (32768 байт), чтение
ограничено 32769 байт; глубина 4, строка парсера 10000 символов, число 20 символов.
Каталоги и отдельные длины полей ограничены строже. Превышение — безопасный 400.

## Транзакции и блокировки

Все четыре операции — одна сервисная write-транзакция от проверки версий до полного DTO:

- POST: validate → общий ProjectWriteLock → lock паспорта → проверка expectedPassportVersion →
  persist/flush новой записи → CAS версии паспорта и refresh → для интеграции запись классов →
  flush → общий `cardAfterWrite` (MANDATORY), оценка → commit.
- PATCH: validate → проверка существования проекта/паспорта → lock строки записи с условием
  принадлежности проекту → проверка expectedVersion → поля/flush → @Version (либо CAS и
  refresh для прежних полей) → классификация/flush → полный DTO и оценка → commit.

POST берёт блокировки в общем порядке **проект → паспорт → новая дочерняя запись**,
совместимом с B3.1 и текущим DELETE проекта. После ожидания проверяется актуальное
состояние. Два POST с одной ожидаемой версией состава дают один успех и один 409.
Ошибки после flush откатывают новую строку, классификацию и техническую версию паспорта.

PATCH не переносит зависимость и не создаёт родителя, блокирует существующую строку,
не берёт write-lock общего проекта/паспорта. Поэтому другая запись может успешно
завершить PATCH до commit первой. Набор классов защищён lock своей интеграции.
Существующие FK NO ACTION сохраняются; каскады и orphanRemoval не добавлены.
Будущие DELETE должны соблюдать общий протокол и повторные проверки; здесь они не реализуются.

При текущем DELETE проекта уже существующий паспорт сам запрещает удаление по FK.
В обоих порядках POST ребёнка/DELETE проекта проект и паспорт сохраняются, DELETE
получает 409, POST — 201. Если DELETE взял lock первым, POST ждёт отката DELETE,
после чего повторно проверяет проект/паспорт. Сценарий успешного DELETE проекта,
содержащего паспорт, этим этапом не вводится.

DTO/оценка строятся после flush в той же write-транзакции и видят собственные записи;
отдельного GET после commit нет. GET остаются read-only REPEATABLE_READ и не меняют
даты/версии/строки. Ответ write относится к состоянию его транзакции и не обещает видеть
параллельную ещё не зафиксированную правку другой записи.

## Ошибки

Сохраняется формат B3.1: code, error, опциональные fieldErrors/currentVersion/versionResource.
Валидация использует те же безопасные сообщения B3.1 про поля/запрос паспорта как агрегата.

| HTTP | code |
|---|---|
| 400 | BAD_REQUEST / VALIDATION_ERROR |
| 404 | PROJECT_NOT_FOUND / PASSPORT_NOT_FOUND / COMPONENT_NOT_FOUND / INTEGRATION_NOT_FOUND |
| 409 | PASSPORT_VERSION_CONFLICT при POST, COMPONENT_VERSION_CONFLICT / INTEGRATION_VERSION_CONFLICT при PATCH |
| 500 | DATABASE_ERROR, безопасное Database operation failed для технических DataAccess/transaction/JPA ошибок |

Чужая запись возвращает тот же 404, что отсутствующая; её версия не раскрывается.
409 возвращает реальную текущую техническую версию и ресурс PASSPORT/COMPONENT/INTEGRATION.

```json
{"code":"INTEGRATION_VERSION_CONFLICT","error":"Version does not match","currentVersion":1,"versionResource":"INTEGRATION"}
```

Ошибки не отражают текст запроса, SQL, пути или внутренние исключения. Новое логирование
содержимого не добавлено. Авторизация и роли этим этапом не реализуются.

## Границы

DELETE, операции проверок/рисков и frontend не реализованы. Сущности/схема/ручные миграции
и datasource-профили не менялись; startup-мигратора нет, защита PM-000 сохранена.
Рабочая файловая БД и её копии не открываются. Все автоматические подключения — к
одноразовым in-memory H2. Коммит и push до ревью не выполняются.
