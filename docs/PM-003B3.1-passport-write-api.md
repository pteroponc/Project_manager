# PM-003B3.1 — создание и PATCH архитектурного паспорта

База: `codex-dev`, `7fa0a2340b3ebcd31ca04d67fa044843f2b444f5`.
Модель хранения B1b, оценка B2.1 и полный DTO B2.2 переиспользуются без изменения формулы.

## Маршруты

| Метод | Путь | Успех |
|---|---|---|
| POST | `/api/projects/{id}/architecture` | 201, полный `ArchitectureReadDtos.Card` |
| PATCH | `/api/projects/{id}/architecture` | 200, тот же полный DTO |

Content-Type: `application/json`. Проект определяется только ID в пути.
Полный ответ включает проект, паспорт, классы/среды, компоненты, интеграции с классификацией,
проверки, риски с версиями и оценку. Бюджета нет. Все причины и принятые высокие риски
сохраняются; `officialGoLiveApproval=false`, принятие риска — `UNVERIFIED`.

### POST

Обязательны `expectedProjectVersion`, `criticality`, `stage`, `solutionType`.
Остальные реквизиты разрешают черновик: пропущенные nullable-поля сохраняются как SQL NULL,
пропущенные наборы — пустыми. Массивы могут быть пустыми.
Паспорт, оба набора и увеличение версии проекта записываются одной транзакцией.
Компоненты, интеграции, риски и десять проверок не создаются автоматически.

Пример минимального черновика:

```json
{
  "expectedProjectVersion": 0,
  "criticality": "HIGH",
  "stage": "NOT_STARTED",
  "solutionType": "NEW_SOLUTION",
  "dataClasses": [],
  "environments": []
}
```

Новый паспорт имеет версию 0; проект — прежнюю версию +1.
`createdAt=updatedAt` — один серверный `Clock.instant()`, хранение/ответ в UTC.
Неполные сведения разрешены, готовность рассчитывается прежней формулой: отсутствие
проверок не становится READY, даже если клиент указал стадию APPROVED.

### PATCH

Обязателен `expectedVersion` **паспорта**, плюс хотя бы одно изменяемое поле.

| Вход | Действие |
|---|---|
| Поле пропущено | Сохранить прежнее значение |
| Nullable-реквизит равен `null` | Очистить реквизит |
| Ненулевой реквизит равен `null` | 400 |
| `dataClasses`/`environments` — массив | Полностью заменить соответствующий набор |
| Набор равен `[]` | Очистить набор |
| Набор равен `null` | 400 |
| Только `expectedVersion` | 400 |

Пример:

```json
{
  "expectedVersion": 0,
  "architect": null,
  "solutionSummary": "Изменены границы решения.\nНужно повторное согласование.",
  "dataClasses": ["INTERNAL", "PERSONAL"],
  "environments": []
}
```

Успешный PATCH увеличивает версию паспорта **ровно на 1**, даже при прежних значениях
и при том же моменте тестового Clock. Версия проекта не меняется.
`createdAt` сохраняется, `updatedAt` получает серверный момент Clock; если Clock возвращает
тот же момент, дата может совпасть с прежней, но версия всё равно увеличится.

## Разрешённые поля и ограничения

| Поле | Тип / каталог | Nullable | Максимум |
|---|---|---|---|
| `criticality` | LOW, MEDIUM, HIGH, CRITICAL | нет | Каталог |
| `stage` | NOT_STARTED, IN_DESIGN, IN_REVIEW, APPROVED, CHANGES_REQUIRED | нет | Каталог |
| `solutionType` | NEW_SOLUTION, EXISTING_SOLUTION_CHANGE, INTEGRATION, MIGRATION | нет | Каталог |
| `architect` | Свободный текст, одна строка | да | 255 |
| `solutionSummary` | Управленческое описание, несколько строк | да | 2000 |
| `availabilityRequirement` | Управленческое требование, несколько строк | да | 1000 |
| `recoveryRequirement` | Управленческое требование, несколько строк | да | 1000 |
| `lastReviewDate` | Строка даты YYYY-MM-DD с реально существующей датой | да | 10 |
| `dataClasses` | Массив: PUBLIC, INTERNAL, CONFIDENTIAL, PERSONAL, PAYMENT, COMMERCIAL_SECRET | нет | 6 элементов |
| `environments` | Массив: DEV, TEST, PREPROD, PROD, OTHER | нет | 5 элементов |

Коды принимаются строго в каноническом верхнем регистре, без пробелов и неявного приведения.
Дубликаты запрещены. Порядок массивов незначим, ответ содержит отсортированные коды.
Версии — JSON integer от 0 до `9223372036854775806` включительно; строки, boolean,
дробные числа и числа вне диапазона запрещены. Верхняя граница оставляет место для +1.

Свободный текст обрезается по краям, нормализуется NFC; длина проверяется после
нормализации (в единицах UTF-16 Java String). Внутренние пробелы не схлопываются.
CRLF/CR в многострочных описаниях приводятся к LF, разбиение на строки сохраняется.
Пустые строки не заменяются на null: они дают 400. Управляющие символы запрещены,
кроме CR/LF в многострочных полях; Unicode FORMAT, включая невидимые/bidi-маркеры,
и одиночные суррогаты запрещены.

Отклоняются HTML-маркеры/экранированные угловые скобки, явные исполняемые фрагменты,
URL/типовые домены, IPv4/IPv6, JDBC/URI строк подключения, ключевые шаблоны секретов,
Bearer/Basic, приватные ключи, узнаваемые токены/JWT и присваивания вроде
`password=…`, `DB_PASSWORD=…`, `apiKey=…`. Ошибка не возвращает отклонённое значение.
Это фильтр явных шаблонов, а не доказательство отсутствия произвольной чувствительной
информации: сохраняется требование PM-003 к управленческому содержанию и ручному контролю.
При будущей реализации frontend по-прежнему необходимо контекстное экранирование.

### JSON и тело запроса

Отдельный mapper обслуживает только эти два маршрута: правила старых API не меняются.
Корень должен быть объектом. Неизвестные поля, дубликаты полей (в том числе совпадающие
значения), лишний JSON после объекта, некорректный JSON и неправильные типы дают 400.
Клиент не может задать `id`, `projectId`, `version`, `createdAt`, `updatedAt`, оценку,
компоненты/интеграции/проверки/риски. Единственное поле версии — ожидаемая версия для
соответствующего метода.

Тело ограничено **32 KiB (32768 байт)**: читается не более 32769 байт и превышение
отклоняется до JSON-разбора и записи. Дополнительно ограничены глубина JSON до 4,
строка парсера до 10000 символов и число до 20 символов. Каталог/длины полей и размер
массивов ограничиваются валидатором строже. Ошибка превышения размера — безопасный 400.

## Транзакции, версии и ответ

POST: validate → общий `ProjectWriteLock` → наличие проекта → отсутствие паспорта →
ожидаемая версия проекта → persist/flush паспорта → увеличение версии проекта с CAS →
refresh проекта → явная запись наборов → flush → полный DTO и оценка → commit.
Все шаги записи входят в одну `@Transactional`-операцию.
Конкурентный POST ждёт ту же строку проекта, затем проверяет состояние заново.

PATCH: validate → наличие проекта → `PESSIMISTIC_WRITE` строки паспорта → ожидаемая
версия паспорта → поля/updatedAt → flush → явная замена переданных наборов → flush →
полный DTO и оценка → commit. Конкурентный PATCH после ожидания получает актуальную версию.
Обычно версия увеличивается Hibernate через `@Version`; если при фиксированном Clock
поля остались прежними, CAS повышает её ровно один раз и refresh обновляет managed-состояние.
Проверка конфликта при CAS использует скалярную актуальную версию, а не кеш сущности.

Замена наборов удаляет только строки выбранного набора и явно вставляет новые;
каскадов и orphanRemoval нет. Любая ошибка откатывает поля, наборы, версии и даты целиком.
Сборщик B2.2 вызывается через `cardAfterWrite` с `Propagation.MANDATORY`: ответ видит
собственные записи после flush в текущей write-транзакции. Отдельного GET после её
завершения нет. Один контекст оценки на ответ, зона расчёта Europe/Moscow.
Существующие GET остаются read-only REPEATABLE_READ, без write-lock и изменений.

Существующий DELETE проекта не расширен. POST паспорта и DELETE используют общий lock
проекта; после создания удалению также препятствует существующий FK паспорта NO ACTION.
Расширенные проверки удаления относятся к следующему этапу.

## Безопасные ошибки

| HTTP / code | Значение |
|---|---|
| 400 BAD_REQUEST | Неверная структура/поля/JSON/размер или PATCH без изменений |
| 400 VALIDATION_ERROR | Неверное значение известного поля; безопасный `fieldErrors` |
| 404 PROJECT_NOT_FOUND | Проект отсутствует |
| 404 PASSPORT_NOT_FOUND | PATCH существующего проекта без паспорта |
| 409 PASSPORT_ALREADY_EXISTS | POST существующего паспорта; currentVersion и PASSPORT |
| 409 PROJECT_VERSION_CONFLICT | POST с устаревшей версией проекта; реальная currentVersion и PROJECT |
| 409 PASSPORT_VERSION_CONFLICT | PATCH с устаревшей версией паспорта; реальная currentVersion и PASSPORT |
| 500 DATABASE_ERROR | Техническая ошибка БД, безопасное общее сообщение |

Пример 409:

```json
{"code":"PASSPORT_VERSION_CONFLICT","error":"Version does not match","currentVersion":2,"versionResource":"PASSPORT"}
```

Сообщения не раскрывают текст запроса, SQL, пути, Java-классы или stack trace.
Новое логирование запросов/полей/обоснований не добавлено. Старый обработчик ошибок БД
сохраняет безопасный `Database operation failed`.

## Границы

DELETE паспорта, операции с дочерними записями и инициализация проверок не реализованы.
Frontend, схема, ручные миграции и datasource-профили не изменены. Авторизация/роли
этим этапом не добавляются; ограничения доверенного развёртывания из PM-003 сохраняются.
Рабочая файловая БД и её копии не открываются, миграции к ним не применяются.
Проверки выполняются только на одноразовых in-memory H2 с защитой PM-000.
