# PM-003D.2 — портфельная сводка архитектуры и ИБ

`GET /api/architecture/portfolio/summary` — отдельный read-only маршрут. Прежние
`GET /api/architecture/portfolio`, `/api/projects/registry` и карточка проекта сохраняют
свои контракты. Рабочая схема и datasource не меняются.

## Параметры

| Параметр | Значение по умолчанию | Правило |
|---|---|---|
| `query` | пустая строка | Буквальная подстрока в названии или описании проекта, без учёта регистра; пробелы запроса по краям обрезаются. |
| `quarter`, `status` | `all` | Точное сравнение без учёта регистра; пробелы в сохранённом значении не удаляются. Неизвестное значение даёт пустую выборку. |
| `readiness` | `all` | `all`, `BLOCKED`, `ATTENTION_REQUIRED`, `NOT_ASSESSED`, `READY`, без учёта регистра. |
| `sort` | `name` | `name`, `deadline`, `health` как в реестре проектов; дополнительно `owner`, `quarter`, `projectStatus`, `readiness`. |
| `direction` | `asc` | `asc` или `desc`. |
| `page` | `0` | Номер страницы с нуля. |
| `size` | `20` | Число строк 1…100. |

Неизвестный или повторённый параметр, недопустимая готовность/сортировка/направление,
отрицательная или нецелая страница, размер вне диапазона дают безопасный `400 BAD_REQUEST`.
Поиск, квартал и статус сначала задают общий набор проектов. Для него сервер рассчитывает
готовность по существующей формуле в одном снимке `readOnly`, `REPEATABLE_READ` и с одной
датой Europe/Moscow. Затем применяет `readiness`, сортировку и страницу. Равные значения
ключа сортируются по `projectId` по возрастанию при обоих направлениях; неизвестные
`health` и некорректные/пустые `deadline` всегда в конце.

## Счётчики и ответ

- `totalCount` — число проектов после `query/quarter/status`, до `readiness`.
- `readinessCounts` — четыре количества по этому же набору; сумма равна `totalCount`.
- `filteredCount` — число проектов после `readiness`, до страницы.
- `totalPages` — округлённое вверх `filteredCount / size`; для пустой выборки 0.
- `pageItemCount` — число элементов в текущем `items`; равно `items.length`, не больше `size`.
- Страница за пределами набора возвращает 200 с `items=[]`, сохраняя все счётчики.

В каждой строке находятся проект (`id`, `name`, `owner`, `quarter`, `projectStatus`,
`health`, `deadline`), наличие паспорта, архитектор, версия документа, количества
компонентов/интеграций/проверок/рисков и узкая `assessment`: `status`, `statusLabel`,
`reasonCount`, `upcomingCheckCount`, `acceptedHighRiskCount`, `officialGoLiveApproval`.
Идентификаторы дочерних записей, обоснования рисков, тексты проверок и другие детали
архитектуры/ИБ в этом ответе отсутствуют. Подробности доступны через существующую
`GET /api/projects/{id}/architecture`.

Готовность оценивается для всего общего набора, поскольку `readiness` вычисляется из
дочерних записей. Число SQL SELECT не зависит от количества проектов: один запрос
проектов, шесть узких наборов для формулы и один `GROUP BY` компонентов. В тесте на
501 проект зафиксированы восемь SELECT при любой странице и 20 или меньше элементов
HTTP-ответа. Время/память всё ещё растут с количеством кандидатов; эта версия не
содержит кэшированного статуса готовности или DB-пагинации до расчёта формулы.
