## Реализация удаления пустого паспорта

`DELETE /api/projects/{id}/architecture` требует одиночные query-параметры
expectedVersion, expectedPassportInstanceId и confirmed=true. Неизвестные/повторные/
невалидные параметры — 400, отсутствующие проект/паспорт — 404. Под locks проект →
паспорт проверяются instanceId, числовая версия и заново все шесть зависимостей:
компоненты, интеграции, проверки, риски, классы данных паспорта, среды.

При зависимостях — 409 PASSPORT_HAS_DEPENDENCIES с действительной версией и impact,
полностью совпадающим по формату/причинам со свежим deletion-impact. Записей нет,
классы/среды автоматически не очищаются: их пользователь удаляет явным PATCH.
При успехе удаляется только паспорт, flush, версия проекта +1 атомарно, refresh/flush,
cardAfterWrite/MANDATORY в той же write-транзакции. Ответ 200: passport=null, пустые
архитектурные коллекции, NOT_ASSESSED/PASSPORT_MISSING, officialGoLiveApproval=false.
Остальные поля проекта прежние. Повтор DELETE — 404. Ошибка после flush откатывает
паспорт, данные и версию проекта. Отдельного post-commit GET нет.

## Исправление экземпляра паспорта (согласовано пользователем)

POST паспорта генерирует новый серверный UUID instanceId. Он хранится в
project_architecture_passports.instance_id VARCHAR(36) NOT NULL, с UNIQUE
uq_arch_passport_instance и ORM updatable=false. Клиент не задаёт/не меняет instanceId.
DTO возвращает passport.instanceId. Техническая версия нового паспорта остаётся 0,
пользовательская documentVersion=1.0. UUID не зависит от Clock/версии проекта и не
теряется при перезапуске приложения.

expectedPassportInstanceId обязателен для **всех десяти защищённых операций**:

- PATCH/DELETE паспорта;
- POST компонентов, интеграций и рисков;
- POST checks/initialize;
- DELETE каждого из четырёх типов дочерних записей.

После locks: наличие/принадлежность ресурсов → instanceId → числовые версии → запись.
Неверный/отсутствующий UUID — 400, несовпадение — 409 PASSPORT_INSTANCE_CONFLICT с
реальной currentVersion и versionResource=PASSPORT, отсутствие ресурса — 404.
Нет автоматического получения нового токена для старой команды и повторов записи.
PATCH ребёнка сохраняет прежний контракт с UUID самой записи и expectedVersion;
новые записи получают новые серверные UUID, старые ID не переиспользуются.

Проверены все пути, потребляющие версию паспорта: ArchitecturePassportMutationService.patch,
ArchitecturePassportDeletionService.delete, ArchitectureChildMutationService.createComponent/
createIntegration, ArchitectureRiskMutationService.create, ArchitectureCheckMutationService.initialize,
ArchitectureChildDeletionService.delete для COMPONENT/INTEGRATION/CHECK/RISK.
POST самого паспорта сохраняет expectedProjectVersion и ProjectWriteLock.

Контракты B3.1/B3.2a/B3.2b/B3.2c/B3.3a и план PM-003 обновлены. Ранее выпущенные
V002/V003/V004 **не изменены**. Новый документ:
`docs/PM-003B3.3b-manual-V005.md`; API удаления — `docs/PM-003B3.3b-passport-deletion-api.md`.

## Ручная V005

`db/manual/V005__architecture_passport_instance.sql` остаётся вне ресурсов приложения.
Полная precondition схемы после V004 выполняется до первого DDL: старые таблицы,
архитектурные таблицы, маркер, столбцы/nullable/defaults, PK/FK/UNIQUE/CHECK/индексы/версии.
Несовместимая, частичная и повторно мигрированная схема отклоняется без DDL/изменения строк.
Существующим паспортам назначаются различные UUID, остальные значения/ID/даты/версии
сохраняются; затем NOT NULL, UNIQUE, маркер и полная postcondition новой схемы.

Инструкция требует остановить все записи и иметь проверенную резервную копию.
При частичном H2 DDL обычного ROLLBACK недостаточно — восстановить проверенную копию,
не продолжать/повторять скрипт вслепую. После возобновления записей откат к старой копии
может потерять новые данные и требует отдельного плана. Рабочие данные здесь не использовались.

### Подробности защиты и сохранности

1. Шесть воспроизведений: A создан через API с version=0; полная команда A сохранена;
   A удалён; B создан того же проекта с version=0 при том же фиксированном Clock.
   Старые PATCH/DELETE, POST компонента/интеграции/риска и initialize получают
   409 PASSPORT_INSTANCE_CONFLICT. Полный снимок 12 таблиц и B не меняются.
   Затем запрос с instanceId B для той же операции успешно выполняется.
2. Для всех десяти операций проверены отсутствие/неверный UUID и instance conflict
   до числовой версии (в запросе обе версии заведомо устаревшие). Данных не меняют.
   Проверены JSON null/число/boolean/array/object, повторные JSON/query-токены,
   запрет клиентского instanceId при POST/PATCH паспорта.
3. Для каждого типа ребёнка A создаётся и затем явно очищается через API, A удаляется,
   создаются B и его дети. UUID детей различаются. Сохранённые DELETE и PATCH ребёнка A
   возвращают 404, B/его строки не меняются. Контракт PATCH детей прежний.
4. Два DELETE, PATCH/DELETE в обоих порядках, создание компонента/интеграции/риска/
   initialize против DELETE в обоих порядках сохраняют правила B3.3b. При создании
   первым старая версия DELETE даёт 409; повтор с актуальной парой токенов даёт 409
   зависимостей с актуальным impact. При удалении первым создание получает 404.
5. Дополнительная гонка: одна транзакция удаляет A и создаёт B, удерживая lock;
   старый PATCH A фактически ожидает строку паспорта. После commit он даёт безопасный
   404 (H2 может вернуть отсутствие удалённой выбранной A) либо 409; B неизменен.
   Повтор после commit обязательно даёт 409 INSTANCE_CONFLICT. Это не автоматический
   повтор сервиса: отдельная проверка поведения уже существующего B.
6. Ожидание подтверждается CountDownLatch и реальными H2 sessions BLOCKED/BLOCKER_ID/
   SQL нужной таблицы, Future второго запроса ещё не завершён. Первая транзакция
   отпускается только после этого; случайных задержек для порядка нет.
7. Сбой после фактического удаления/flush и project.version+1 полностью восстанавливает
   паспорт, его instanceId, даты/версию и проект. Прежние тесты POST/PATCH/DELETE детей
   и паспорта подтверждают откаты и при новых токенах, независимость PATCH разных строк.
8. В заполненной схеме V002→V003→V004→V005 сравниваются все старые строки 13 таблиц
   (включая V004-маркер): единственные добавления — instance_id и V005-маркер.
   Проверены разные валидные UUID, физические NOT NULL/UNIQUE, индексы/FK и validate.
   Частичная колонка/маркер, повтор, неверные тип/FK/индекс/лишняя колонка/нет V004
   отклоняются; данные и SCRIPT NODATA до/после отказа идентичны.
9. Два последовательных Spring-контекста используют одну отдельную in-memory БД
   с DB_CLOSE_DELAY=-1 и ddl-auto=validate, без create-drop/пересоздания схемы:
   в первом A удаляется и создаётся B; во втором instanceId B сохранён, старая команда
   A запрещена, актуальный PATCH B успешен. Это перезапуск приложения, не рабочая БД.
10. GET карточки/портфеля/impact не создаёт паспорт/проверки и не меняет строки/даты/
    версии/UUID. Сохранены проекты, задачи, поезда, контрольные точки и данные другого
    проекта; нули/максимальный бюджет и все прежние ID/версии проверяются снимками.
    Ни формула B2, ни причины/UNVERIFIED/officialGoLiveApproval=false не менялись.
