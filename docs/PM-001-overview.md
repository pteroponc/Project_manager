## 2. Что уже работает и что требует изменения

| Область | Фактическое поведение |
|---|---|
| Источник проектов | `GET /api/projects`, данные из таблицы `projects`. |
| Сводка | `GET /api/portfolio`: количество, активные, рисковые, сумма бюджета, средний прогресс. |
| Активные | `status = active`. Другие статусы: `planned`, `paused`, `done`. |
| «С риском» в API | Все проекты, у которых `health` не равен `green`, включая неизвестные значения. |
| «Проблемные» в интерфейсе | Другая формула: красный/жёлтый `health`, просрочка, срок в пределах 14 дней или прогресс ниже 35%. Эти показатели могут расходиться. |
| Бюджет | Сумма `budget`. Расходов и финансового факта нет. Суммирование в Java использует `int`, возможен выход за диапазон. |
| Прогресс | Введённое пользователем поле. API отбрасывает дробную часть среднего; отдельный экран «Дашборды» округляет. |
| Контрольная точка | `milestone` — текст. Отдельной даты и признака выполнения нет. Рядом выводится `deadline` всего проекта. |
| Фильтры | Квартал и `health` поддержаны API и JavaScript, но соответствующие элементы отсутствуют в HTML. Список кварталов предполагается строить из уже отфильтрованных проектов — это сузит доступные варианты. |
| Переходы | Строки проектов на «Обзоре» не ведут к карточке. В разделе «Проекты» уже есть карточки, редактирование и переход к доскам. |
| Задачи | Есть `board_cards`, сроки, колонки и `blocked`, но достоверного портфельного показателя «проблемные задачи» нет. Единого признака завершения задачи также нет. |
| Загрузка | Проекты, сводка и релизные поезда загружаются общим `Promise.all`: ошибка поездов блокирует обновление портфеля. Начальные значения и некоторые подстановки показывают нули до получения данных. |
| Готовность релиза | Это состояние сборки самого приложения в GitHub, а не готовность проектов портфеля. |

Защиту PM-000 сохраняем: чтение ничего не создаёт и не исправляет, несопоставленные карточки остаются доступными.

## 3. Предлагаемое решение

### 3.1. Состав и расположение экрана

Порядок блоков:

1. Заголовок, фильтры, «Обновить», время последней успешной загрузки.
2. Сводка портфеля.
3. «Требуют внимания».
4. «Контрольные точки и сроки проектов».
5. Второстепенная ссылка или блок технической готовности приложения — размещение согласовать.

На широком экране сводка располагается в строку, ниже — «Требуют внимания» и контрольные точки. На узком экране — одна колонка, внимание выше сроков. Цвет дополняется текстовой причиной; названия проектов доступны как ссылки с клавиатуры.

### 3.2. Правила расчёта и примеры

Все показатели относятся к **одному набору проектов после применения фильтров**.

Для примеров используются условные данные, не рабочая БД. Расчётная дата — **19.09.2026**.

| Проект | Статус | Health | Срок проекта | Бюджет | Прогресс |
|---|---|---|---|---:|---:|
| A | active | green | 18.09.2026 | 2 млн ₽ | 20% |
| B | active | red | 25.09.2026 | 3 млн ₽ | 80% |
| C | planned | yellow | 20.10.2026 | 1 млн ₽ | 0% |
| D | done | green | 30.11.2026 | 0 ₽ | 100% |

Предлагаемый горизонт близких сроков — 14 календарных дней, требуется согласование.

| Показатель | Источник и формула | Отсутствующие данные | Пример |
|---|---|---|---|
| Всего проектов | `projects.id`: число уникальных проектов в выборке. | Успешная пустая выборка — `0`; ошибка загрузки — «Не удалось загрузить». | `4`. |
| Распределение по статусам | Группировка по `status`; доля = количество / общее число × 100%. Активные — группа `active`. | Неизвестный статус — отдельная группа, без исправления записи. При пустой выборке проценты не показывать. | Активные `2 из 4 — 50%`, запланированные `1`, завершённые `1`, на паузе `0`. |
| Указанный бюджет | Сумма корректных неотрицательных `budget`; агрегат — `long`. | Пустая выборка — «Нет проектов». Отсутствующие/некорректные значения не подменять нулём: показывать известную сумму с покрытием, например «по 3 из 4 проектов». Сохранённый `0` остаётся нулём. | `2 + 3 + 1 + 0 = 6 млн ₽`. |
| Средний указанный прогресс | Простое среднее корректных `progress` в диапазоне 0–100, округление до целого. Не взвешивать бюджетом. | Нет корректных значений — «Нет данных»; неполное покрытие явно обозначить. | `(20 + 80 + 0 + 100) / 4 = 50%`. |
| Требуют внимания | Уникальные проекты, у которых `health = red` или корректный `deadline < расчётной даты`. | При неизвестной дате/health отсутствие отклонения не означает благополучие: показать неполноту проверки. Красный health достаточен даже без даты. | A просрочен, B красный → `2`. При двух причинах у одного проекта считать его один раз. |
| Просроченные проекты | Число проектов с корректным `deadline < расчётной даты`. Это причина внимания, а не ещё одна обязательная KPI-карточка. | Некорректные/отсутствующие даты исключить из расчёта и отдельно обозначить. | A → `1`, просрочка `1 день`. |
| Близкие сроки | `0 ≤ deadline − расчётная дата ≤ 14` календарных дней. Показатель внутри контрольных точек. | Нет подходящих сроков — «В ближайшие 14 дней сроков нет»; неизвестные даты — отдельная группа. | B: до срока `6 дней` → `1`. Сам по себе близкий срок не включает проект в «Требуют внимания». |
| Контрольная точка проекта | Дословное `milestone`; рядом отдельное поле «Срок проекта» из `deadline`. | «Контрольная точка не указана» / «Срок проекта не указан». При некорректной дате показать исходное значение и пояснение. | Для B: «Согласование пилота»; срок проекта 25.09, осталось 6 дней. Дата самой точки неизвестна. |
| Проблемные задачи | В первой версии не рассчитывать: нет согласованной формулы и однозначной трактовки завершения для всех колонок. | «Нет достоверного расчёта» с пояснением, либо отсутствие числовой карточки. Никогда не `0` вместо неизвестного. | Даже при двух `blocked=true` можно утверждать только наличие двух заблокированных записей, а не точное число всех проблемных задач. |

Дополнительно показывать компактное сообщение о неполноте данных: например, «У 2 проектов не удалось определить срок». Не относить такие проекты автоматически к благополучным.

Не включать в PM-001:

- Освоение бюджета.
- Перерасход.
- Прогноз даты завершения.
- Выполнение контрольных точек.

Для этих показателей нет необходимых исходных данных. Низкий прогресс без планового графика также не доказывает отставание.

### 3.3. «Требуют внимания»

Строка содержит название, владельца, статус, `health`, срок и все установленные причины:

- «Срок просрочен на 3 дня».
- «Красное состояние».
- Обе причины одновременно.

Текст `risk` выводится как дополнительное описание, но сам факт наличия текста не делает проект проблемным. Убираем эвристику «прогресс ниже 35%».

Предлагаемая сортировка: сначала проекты с обеими причинами, затем с одной; внутри группы — просроченные по длительности просрочки, далее стабильная сортировка по названию/ID.

### 3.4. Фильтры и переходы

Предлагаются квартал, статус и `health`, плюс «Сбросить». Горизонт контрольных точек — отдельный переключатель, влияющий только на этот блок.

- Справочник кварталов строить из полного набора, а не текущей выборки.
- Сводка, внимание и сроки используют одинаковые общие фильтры.
- Везде явно писать «В выбранном срезе».
- Название проекта переводит в существующий раздел «Проекты», прокручивает и выделяет карточку по ID. Режим редактирования автоматически не открывается.
- Для полей, которых сейчас нет в карточке, добавить раскрываемые подробности в существующий шаблон.
- Возврат на «Обзор» сохраняет его фильтры.
- Кнопки «Редактировать» и «Показать доску» переиспользуются.

### 3.5. Загрузка и ошибки

- До получения ответа — индикатор загрузки или `—`, без фиктивных нулей.
- Нет проектов вообще — предложение создать проект.
- Нет совпадений с фильтрами — предложение сбросить фильтры.
- Нет выявленных отклонений — соответствующее сообщение с оговоркой о неполных данных, если они есть.
- Ошибка — сообщение и повторная загрузка. Старые данные можно оставить только с отметкой времени и предупреждением, что обновление не удалось.
- Ошибка GitHub или релизных поездов не блокирует портфель.
- При быстрой смене фильтров устаревший ответ не должен перезаписывать новый.

## 5. Спорные решения — согласовать до разработки

| Вопрос | Предложение |
|---|---|
| Жёлтый `health` | В базовую формулу внимания включить только красный и просрочку. Жёлтый оставить видимым состоянием и фильтром. Сейчас его подпись — «Требует внимания», поэтому потребуется согласовать более точное название, например «Предупреждение». |
| Завершённые проекты | Пока буквально применять правило просрочки и красного health ко всем проектам выборки. Исключать `done` из просрочки только после согласования: иначе это будет неоговорённое исключение. Фактической даты завершения нет. |
| Близкий срок | 14 дней включительно; сегодня — отдельная подпись «Сегодня». Возможно добавить переключатель 7/14/30 дней. |
| Расчётная дата | Единая серверная дата в согласованном часовом поясе; предлагается `Europe/Moscow`. Сравнение календарных дат без зависимости от времени браузера. |
| Контрольные точки | В PM-001 показывать текст точки и отдельно срок проекта. Настоящий календарь точек с собственными датами — отдельная задача с изменением модели. |
| Средний прогресс | Оставить второстепенным показателем под точным названием «Средний указанный прогресс». Он не измеряет выполненный объём работ портфеля. |
| Бюджет и валюта | Название «Указанный бюджет», валюта ₽ по текущему интерфейсу. Нужно подтвердить, что все бюджеты действительно рублёвые: поля валюты нет. |
| Проблемные задачи | Не выводить число в первой версии. Отдельный показатель «Заблокированные задачи» возможен позже после согласования обработки `blocked=null`, завершённых и несопоставленных карточек. |
| GitHub-блок | Сохранить функциональность, но перенести ниже и назвать «Сборка и релиз приложения» либо перенести в «Релизы». |
| Карточка проекта | Использовать существующую карточку в «Проектах», без отдельного нового экрана и дублирования формы. |

## 6. Критерии приёмки

- Все блоки отражают одну отфильтрованную выборку; сумма групп статусов равна числу проектов.
- Просрочка и красный `health` включают проект в «Требуют внимания»; две причины не удваивают счётчик.
- Близкий срок сам по себе отображается только в контрольных точках.
- Прогресс ниже 35% не становится самостоятельным признаком проблемы.
- Дата проекта нигде не выдаётся за дату выполнения контрольной точки.
- Отсутствие данных, ошибка и подтверждённый ноль различимы.
- Число проблемных задач не подменяется нулём.
- Не рассчитываются освоение, перерасход, прогноз завершения и выполнение точек.
- Неизвестные статусы, health и даты видны как неполные данные, записи автоматически не исправляются.
- Фильтры работают, варианты кварталов не исчезают после фильтрации; устаревшие ответы не меняют текущий срез.
- Переход открывает нужную существующую карточку, возврат сохраняет фильтры.
- Ошибка GitHub/поездов не мешает просмотру портфеля.
- Интерфейс доступен с клавиатуры и на узком экране; причины отклонений понятны без цвета.
- Чтение «Обзора» и карточек не изменяет БД; возможности проектов, досок и PM-000 сохраняются.
- Все автоматические проверки выполняются только на тестовой in-memory H2.

## Предлагаемый старт

Начать с **этапа 1 — согласования спорных правил и фиксации контракта показателей**.

До согласования реализацию и коммит не выполнять. Рабочую БД не изменять. Ветки `main`, `master` и `chatgpt-design` не затрагивать.
