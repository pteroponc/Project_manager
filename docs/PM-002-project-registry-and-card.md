## 0. Согласованный объём PM-002A

Первый этап выполняется без изменения JPA-модели и схемы БД и без frontend-работ. В PM-002A
входят только:

- characterization-тесты утверждённых правил PM-001;
- общий серверный assessment проекта;
- API реестра с поиском, фильтрами и сортировкой;
- API полной карточки на данных, которые уже существуют;
- реальный подсчёт задач проекта;
- read-only анализ последствий удаления;
- блокировка удаления проекта, если у него есть задачи.

Макеты реестра и карточки подготовлены и предварительно согласованы, но frontend нельзя начинать
до их окончательной проверки пользователем. В PM-002A также не входят дата начала, nullable
budget/progress, новая модель контрольных точек и optimistic locking: они требуют изменения
схемы и входят в PM-002B. Релизы и документы отложены.

Согласованная политика удаления PM-002A: автоматический cascade запрещён; `DELETE` проекта с
карточками доски возвращает 409 и не меняет ни проект, ни задачи. Проект без задач сохраняет
существующую возможность удаления.

### 0.1. Реализованный checkpoint PM-002A

## 1. Результат аудита

### 1.1. Технологический контекст

- Java 21, Spring Boot 3.5.6, Spring Web, Spring Data JPA и Jakarta Validation.
- H2: рабочий профиль использует файловую БД с `ddl-auto=validate`; demo и тесты используют
  отдельные in-memory БД.
- Интерфейс — один статический HTML, CSS и JavaScript без frontend-фреймворка и роутера.
- PM-000 запрещает изменения данных при чтении, автоматическое заполнение пользовательских
  записей и запуск тестов на рабочей БД.
- PM-001 уже содержит серверные правила состояния портфеля и расчётную дату в
  `Europe/Moscow`.

### 1.2. Текущий раздел «Проекты»

Раздел уже существует, но является списком крупных карточек и совмещённой формой, а не
реестром и отдельной карточкой проекта.

Текущее поведение:

- `GET /api/projects` загружает весь каталог при инициализации приложения;
- сервер фильтрует только по кварталу, статусу и состоянию, но интерфейс раздела «Проекты»
  эти фильтры не предоставляет;
- карточка в списке показывает название, техническую строку `deliveryModel/status/quarter`,
  состояние, описание, прогресс, владельца, бюджет, срок и KPI;
- действия «Показать доску», «Редактировать» и «Удалить» размещены в каждой карточке;
- отдельного режима просмотра проекта нет;
- переход с «Обзора» открывает раздел «Проекты», догружает проект и фокусирует его карточку;
- создание и редактирование используют одну HTML-форму и полный `POST`/`PUT`;
- форма не отслеживает несохранённые изменения;
- отмена сбрасывает форму локально и не отправляет запрос, что соответствует требованию;
- удаление использует только нативный `window.confirm` с названием проекта;
- ошибка загрузки каталога выводится через общий статус формы, отдельного повторного действия
  и явной маркировки устаревших данных нет;
- состояние фильтров PM-001 сохраняется при возврате с текущей карточки списка, но у самого
  реестра нет собственного набора фильтров.

### 1.3. Текущая модель проекта

`ProjectEntity` содержит:

| Поле | Тип и ограничение | Следствие для PM-002 |
|---|---|---|
| `id` | `String`, PK | Подходит. |
| `name`, `owner`, `status`, `health`, `quarter` | `String`, `nullable=false` | Отсутствие значения штатно не представимо. Допустимые значения status/health сервером не проверяются. |
| `deliveryModel` | nullable `String` | Сервис подменяет пустое значение на `kanban`. |
| `budget`, `progress` | примитивный `int`, `nullable=false` | Нельзя отличить «не указано» от достоверного нуля. |
| `deadline` | обязательный `String` | Формат и календарная корректность при записи не проверяются. |
| `milestone` | обязательный текст | Это одна подпись без собственной даты и признака выполнения; списка контрольных точек нет. |
| `risk`, `dependency`, `kpiName`, `kpiTarget`, `summary` | обязательные строки | API требует непустые значения, хотя часть полей не относится к минимальной карточке. |

Даты начала проекта нет. Версии записи, `updatedAt` и другого механизма обнаружения
конкурентного изменения нет.

### 1.4. DTO, валидация и ошибки

- `ProjectRequest` используется и для создания, и для полного обновления.
- Все строки в запросе, кроме фактически нормализуемой модели поставки, помечены
  `@NotBlank`; бюджет неотрицательный, прогресс ограничен 0–100.
- Сервер не проверяет допустимые status/health, корректность даты и взаимный порядок дат.
- `PUT` заново записывает все поля. Клиент, работающий со старым снимком, может перезаписать
  поля, изменённые другим запросом.
- Ответ использует примитивы `int`, поэтому неизвестное числовое значение невозможно.
- обработчик ошибок возвращает только первую ошибку в одном поле `error`; frontend не может
  надёжно привязать её к конкретному полю;
- любой `IllegalArgumentException`, включая ошибку значения, превращается в 404. Нужны
  раздельные ошибки 400, 404 и при необходимости 409.

### 1.5. Связи проекта

| Объект | Фактическая связь | Что можно достоверно показать |
|---|---|---|
| Доска | Отдельной сущности доски нет. Она строится из проекта, выбранной модели поставки и карточек. | Переход в вычисляемое представление доски. Нельзя утверждать, что отдельная доска создана или хранится. |
| Задачи | `board_cards.project_id` — обычная строковая колонка; JPA-связи и FK нет. | Реальное количество и список карточек можно запросить по `projectId`. |
| Контрольные точки | Только `projects.milestone`, без даты/статуса. | Можно показать «указанная контрольная точка» как текст, но нельзя вычислить ближайшую или разделить выполненные/предстоящие. |
| Релизные поезда | В `ReleaseTrainEntity` нет `projectId`, таблицы связи нет. | Ничего проектного показывать нельзя. Совпадение квартала не является связью. |
| Документы | Раздел HTML — статическая заглушка; сущности и API нет. | Ничего проектного показывать нельзя. |

`createdBoards` в `localStorage` — локальная UI-запись, не подтверждённая сервером. Её нельзя
использовать в полной карточке или последствиях удаления как достоверную связь.

### 1.6. Удаление и каскады

`ProjectService.deleteProject` удаляет только строку `projects`. Между `ProjectEntity` и
`BoardCardEntity` нет `@OneToMany`, `@ManyToOne`, cascade или orphan removal; в модели нет
и внешнего ключа. Поэтому карточки доски не удаляются каскадно и могут остаться
осиротевшими. После удаления проекта API доски не откроется, потому что сначала вызывает
`requireProject`, но строки `board_cards` сохранятся.

Релизные поезда и статические документы не связаны с проектом и удалением не затрагиваются.
Тестов жизненного цикла «проект с задачами → удаление проекта» нет.

До отдельного решения нельзя добавлять автоматическое каскадное удаление. Безопасный вариант
для PM-002 — предварительно показать реальные связи и блокировать удаление проекта с
карточками доски, возвращая 409. Сохранение текущего безусловного удаления является отдельным
спорным решением, перечисленным в разделе 13.

### 1.7. Существующие серверные расчёты

`PortfolioOverviewService` уже реализует утверждённые правила PM-001:

- единая дата по серверному `Clock` в `Europe/Moscow`;
- красное состояние незавершённого проекта требует внимания;
- просроченный срок незавершённого проекта требует внимания;
- жёлтое состояние, низкий прогресс и близкий срок сами по себе внимания не требуют;
- завершённый проект не считается просроченным;
- `done + red` является противоречием данных, но не причиной внимания;
- неизвестные статусы, состояния и даты остаются видимыми и не исправляются;
- чтение выполняется в read-only транзакции и покрыто тестом неизменности строк.

Эти правила сейчас находятся внутри сервиса дашборда. Копировать их в новый сервис или
JavaScript нельзя. Нужен общий серверный компонент оценки одного проекта.

### 1.8. Тестовое покрытие

Есть проверки:

- CRUD создания проекта и карточки доски на уровне API (частично);
- базовой Bean Validation;
- всех ключевых правил PM-001;
- отсутствия записей при чтении доски и портфеля;
- изоляции demo/test БД и сохранения неизвестных колонок доски;
- frontend-состояний PM-001, перехода с обзора и повторной загрузки.

Не покрыты:

- поиск и сортировка реестра;
- собственные фильтры реестра и их сохранение;
- полная карточка и 404;
- частичное обновление без потери чужих полей;
- допустимые status/health и корректность дат;
- ошибки по полям;
- несохранённая форма и отмена;
- последствия удаления проекта с задачами;
- конкурентное изменение;
- адаптивность раздела «Проекты».

## 3. Предлагаемая структура реестра

### 3.1. Компоновка

Визуальный язык наследуется от «Обзора»: существующая тёмно-зелёная навигация, фон
`#F4F7F6`, белые панели, граница `#DDE5E2`, компактные действия.

1. Заголовок «Проекты», количество найденных и кнопка «Создать проект».
2. Одна компактная панель:
   - поиск по названию и описанию;
   - квартал;
   - статус;
   - состояние;
   - toggle «Требуют внимания»;
   - сортировка;
   - вторичная кнопка «Сбросить».
3. Список результатов.
4. Состояние загрузки, пустой каталог, пустая выборка, ошибка с «Повторить».

### 3.2. Строка реестра

Desktop-строка содержит:

- название и короткое описание;
- статус и состояние с русскими подписями;
- квартал;
- прогресс или «Не указано» после перехода на nullable progress в PM-002B;
- плановую дату;
- серверный признак просрочки;
- ближайшую контрольную точку только после появления подтверждённых milestone-данных.

Вся строка открывает карточку. Вложенные действия не должны создавать конфликт клика.
Неизвестный status/health показывается как «Неизвестно: <исходное значение>».

Сортировка состояния выполняется в порядке `red → yellow → green → unknown` для ascending
«сначала требующие внимания».

### 3.3. Фильтры и возврат

Состояние хранится отдельно от фильтров «Обзора». Поиск, фильтры и сортировка синхронизируются с
query-параметрами, поэтому сохраняются при открытии карточки, возврате, browser back и прямой
ссылке. Позиция прокрутки хранится в состоянии интерфейса. Новый frontend-фреймворк не нужен.

Смена фильтра отменяет влияние позднего предыдущего ответа через request sequence/AbortController.
Запрос отправляется после debounce поиска 250–300 мс; select/toggle применяются сразу.

## 4. Предлагаемая карточка проекта

### 4.1. Режим просмотра

Карточка открывается в разделе «Проекты», но как отдельное представление:

- хлебная кнопка «Вернуться к проектам»;
- название, статус, состояние, прогресс;
- серверные признаки внимания/качества;
- основная кнопка «Редактировать»;
- вторичные переходы только к реально доступным разделам.

Разделы:

1. **Общая информация** — утверждённые поля проекта без бюджета. Пустые/nullable значения
   показываются как «Не указано», без подстановки нуля.
2. **Сроки и контрольные точки** — дата завершения и серверное число дней. До изменения схемы
   текущий `milestone` показывается как одиночный текст «Указанная контрольная точка» без
   вымышленной даты или статуса.
3. **Связанные элементы** — действие «Открыть доску» доступно каждому проекту и рядом показано
   реальное количество задач. Релизы и документы отсутствуют, пока нет связи.
4. **Качество данных** — результаты общего server-side assessment.

### 4.2. Расчёты карточки

Для расчётной даты `D`, нормализованного статуса `S`, состояния `H` и корректной плановой
даты `T`:

- `daysUntilDeadline = T - D` в календарных днях;
- `overdue = S != done && daysUntilDeadline < 0`;
- `attention = (S != done && H == red) || overdue`;
- `done + red` → quality issue, не attention;
- yellow, progress и срок 0–14 дней не включают attention;
- неизвестная/некорректная дата → `daysUntilDeadline = null` и предупреждение качества;
- вычисление выполняется один раз общим серверным компонентом с тем же `Clock`, что PM-001.

Дополнительные проверки качества:

- `done + red` — уже возможно и реализовано PM-001;
- deadline раньше start date — только после добавления start date;
- progress вне 0–100 — API уже запрещает, но проверка чтения нужна для старых/внешне
  изменённых строк;
- неизвестные status/health и пустые важные поля — проверять при чтении, не исправлять.

Существующий общий assessment продолжает защищать старые данные, включая некорректный бюджет,
но новые реестр, карточка, формы и макеты не выводят поле или значение бюджета.

## 5. API-контракты

Существующие `GET/POST/PUT/DELETE /api/projects` сохраняются для совместимости. Для PM-002
предлагаются специализированные контракты.

### 5.1. Реестр

`GET /api/projects/registry`

Параметры:

- `query` — необязательный поиск по `name` и `summary`;
- `quarter`, `status`, `health` — `all` или конкретное значение;
- `attention` — `all|only`;
- `sort` — `name|deadline|health`;
- `direction` — `asc|desc`.

Ответ:

```json
{
  "calculationDate": "2026-09-21",
  "timeZone": "Europe/Moscow",
  "totalCount": 12,
  "filteredCount": 3,
  "filterOptions": {
    "quarters": ["Q3 2026"],
    "statuses": ["active"],
    "healthValues": ["green", "red"]
  },
  "items": [
    {
      "id": "...",
      "name": "...",
      "summary": "...",
      "status": "active",
      "health": "red",
      "quarter": "Q3 2026",
      "progress": 40,
      "deadline": "2026-09-30",
      "assessment": {
        "daysUntilDeadline": 9,
        "overdue": false,
        "requiresAttention": true,
        "attentionReasons": ["Красное состояние"],
        "dataQualityIssues": []
      }
    }
  ]
}
```

Опции фильтров формируются по полному каталогу, а не текущему срезу. Неизвестные значения
сохраняются. Сортировка имеет `name,id` или соответствующее поле плюс `name,id` как устойчивый
tie-breaker. Для первой версии пагинация не требуется; при подтверждённом большом объёме она
добавляется в этот контракт без загрузки отдельных строк.

### 5.2. Полная карточка

`GET /api/projects/{id}/card`

Ответ содержит утверждённые сохранённые поля без бюджета, server assessment, `taskCount` и
доступность перехода к доске для каждого проекта. Не возвращает фиктивные `releaseCount`,
`documentCount` или milestone list. Отсутствующий проект — 404 в существующем совместимом
формате `{ "error": "..." }`.

Получение карточки — read-only операция. Снимок проекта и task count желательно читать в одной
read-only транзакции.

### 5.3. Создание и обновление

- `POST /api/projects` остаётся созданием и возвращает фактически сохранённый объект.
- Для изменения добавить `PATCH /api/projects/{id}` с
  `Content-Type: application/merge-patch+json`.
- Сервис применяет только ключи, присутствующие в JSON, к загруженной сущности; отсутствующие
  ключи не меняются.
- После merge сервер валидирует итоговую сущность целиком и возвращает фактически сохранённую
  карточку.
- Неподдерживаемые поля отклоняются 400, а не игнорируются.

`PUT` сохраняется для совместимости, но новый интерфейс его не использует.

Формат ошибки:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Исправьте отмеченные поля",
  "fieldErrors": {
    "progress": "Допустимо значение от 0 до 100"
  }
}
```

### 5.4. Последствия удаления

`GET /api/projects/{id}/deletion-impact`

Возвращает название, реальное количество `board_cards` и список поддержанных типов связей.
Поля для релизов/документов не добавляются, пока связей нет.

`DELETE /api/projects/{id}` будет вызываться frontend только после отдельного подтверждения UI.
Согласованная политика PM-002A: при `taskCount > 0` вернуть 409
`PROJECT_HAS_BOARD_CARDS`; автоматическое удаление карточек запрещено. Изменение этой политики
требует отдельного решения пользователя.

## 6. Общий серверный компонент правил

Выделить из `PortfolioOverviewService` чистый компонент, например `ProjectAssessmentService`,
который получает проект и расчётную дату и возвращает:

- нормализованные/известные status и health;
- корректную дату и `daysUntilDeadline`;
- `overdue`, `requiresAttention`, причины;
- проблемы качества данных.

`PortfolioOverviewService`, registry service и card service используют один компонент. Это
не меняет формулы PM-001. Хранилище не обновляется, нормализация существует только в ответе.

## 7. Создание и редактирование

### 7.1. UX

- просмотр открывается первым;
- «Редактировать» переводит карточку в форму с исходным серверным снимком;
- кнопки «Сохранить» и «Отмена» явные;
- изменение формы устанавливает dirty flag;
- закрытие карточки, переход в навигации и `beforeunload` при dirty требуют подтверждения;
- «Отмена» восстанавливает последний серверный снимок без API-запроса;
- во время сохранения кнопка блокируется от повторной отправки;
- после ответа форма и карточка строятся из ответа сервера;
- field errors отображаются рядом с полями, общий сетевой сбой — над действиями;
- ошибка не закрывает форму и не стирает ввод.

### 7.2. Серверная валидация

Без изменения схемы можно и нужно проверить:

- name, owner, quarter, deadline и другие текущие обязательные поля;
- status: `active|planned|paused|done`;
- health: `green|yellow|red`;
- deliveryModel: `kanban|scrum|waterfall`;
- progress 0–100, а в PM-002B также `null`;
- deadline — реальная ISO-дата.

Бюджет отсутствует в новых формах. Старый совместимый API сохраняет текущую проверку
`budget >= 0`. В PM-002B новый create/update-контракт разрешает отсутствие или `null` бюджета,
а переданное числовое значение по-прежнему не может быть отрицательным.

Правило `deadline >= startDate` возможно только после добавления start date. Нельзя временно
сравнивать deadline с другой датой.

## 12. Критерии приёмки

### Реестр

- Один запрос возвращает строки реестра; нет отдельного запроса на каждую строку.
- Поиск работает по name и summary без учёта регистра.
- Все фильтры пересекаются; reset восстанавливает полный список.
- Attention совпадает с PM-001 для red/overdue и исключений yellow/done.
- Сортировки name/deadline/health устойчивы и проверены.
- Health сортируется `red → yellow → green → unknown`.
- Unknown/null не превращаются в 0 или «в норме».
- Бюджет отсутствует в новом registry DTO и интерфейсе.
- Клик строки открывает правильную карточку; query-параметры сохраняют фильтры и сортировку,
  возврат восстанавливает scroll.

### Карточка

- Первично открывается read-only режим.
- Сохранённые поля и расчёты соответствуют API.
- Done не просрочен; done+red показан как качество данных.
- Показываются только подтверждённые связи.
- Бюджет отсутствует в новом card DTO и интерфейсе.
- «Открыть доску» доступно каждому проекту.
- 404, loading, error и retry различимы.

### Создание/редактирование

- Сохранение только по кнопке; cancel и уход после отказа не изменяют БД.
- Dirty form предупреждает при уходе.
- Сервер проверяет диапазоны, словари и даты.
- Ошибки отображаются у полей.
- PATCH одного поля не меняет остальные.
- Новая форма не показывает бюджет; PM-002B разрешает создать проект с `budget = null`.
- PM-002B разрешает создать проект с `progress = null`; интерфейс показывает «Не указано».
- `progress = 0` отображается как реальный нулевой прогресс, а не как отсутствие данных.
- Существующие значения бюджета и прогресса, включая нули, не преобразуются.
- `@Version` выявляет конкурентное изменение и возвращает 409.
- После успеха UI использует ответ сервера.

### Удаление

- До DELETE видны название и реальные последствия.
- Отмена не вызывает DELETE.
- Нет автоматического каскадного удаления пользовательских данных.
- Политика проекта с board cards явно согласована и покрыта тестом.

### Безопасность и регрессия

- Все GET registry/card/impact оставляют строки БД без изменений.
- PM-000 safety tests и PM-001 formulas проходят без изменений смысла.
- Demo/test используют только разрешённую in-memory H2, H2 Console отключена.
- Рабочая схема не создаётся и не изменяется автоматически.
- Ручная версионированная SQL-миграция PM-002B проверена сначала на новой test H2, затем на
  восстановленной копии; `ddl-auto=validate` принимает результат.
- После миграции новые проекты сохраняются с `budget = null` и `progress = null`, а существующие
  числовые значения, включая нули, остаются неизменными.
- Обзор, доски, релизы и документы продолжают открываться.

### Интерфейс

- 1440, 768 и 390 px не имеют горизонтального переполнения и наложений.
- Все действия доступны с клавиатуры и имеют понятные accessible names.
- Красный используется только для реальной проблемы, жёлтый — для предупреждения.
- Предыдущие данные после сбоя явно помечены как потенциально устаревшие.

## 13. Зафиксированные решения и отложенные функции

1. **Граница PM-002A — решено.** Выполняется только backend без изменения схемы и frontend.
2. **Nullable budget/progress — решено.** В новом реестре, карточке, формах и макетах бюджет не
   показывается. PM-002B переводит `budget` и `progress` в nullable и разрешает создавать проект
   с `budget = null` и `progress = null`; существующие значения, включая нули, не преобразуются.
3. **Контрольные точки — отложено.** Нужна отдельная сущность с name, plannedDate, completed и
   completedDate. Отложено до решения о схеме.
4. **Удаление с задачами — решено для PM-002A.** DELETE блокируется ответом 409; каскадного
   удаления и автоматического исправления данных нет.
5. **Доска — решено.** Действие «Открыть доску» доступно каждому проекту независимо от числа
   задач; это переход к вычисляемому представлению, а не утверждение о сохранённой сущности.
6. **Релизы и документы — отложено.** API и интерфейс не возвращают фиктивные
   counts или ссылки.
7. **Конкурентное редактирование — решено.** `@Version` и ответ 409 при конфликте входят в
   PM-002B и добавляются ручной миграцией.
8. **Порядок health-sort — решено.** `red → yellow → green → unknown`.
9. **URL-состояние — решено.** Поиск, фильтры и сортировка сохраняются в query-параметрах.
10. **Способ миграций — решено.** Изменение схемы оформляется отдельным ручным версионированным
    SQL после backup и успешной проверки восстановления на отдельной копии. Автоматическое
    изменение рабочей схемы запрещено.

## 14. Оценка необходимости изменения схемы

**Без изменения схемы** реализуются: реестр, поиск, фильтры, сортировка, attention PM-001,
read-only карточка текущих полей, корректный deadline, качество существующих данных, task count,
переход к доске, PATCH существующих полей, field errors, dirty guard, impact удаления и
безопасная блокировка удаления с задачами.

**Изменение схемы обязательно в PM-002B** для nullable budget/progress, даты начала, таблицы
