## Сделано

Добавлены четыре backend-маршрута:

| Метод | Путь | Успех |
|---|---|---|
| POST | `/api/projects/{id}/architecture/components` | 201, полный архитектурный агрегат |
| PATCH | `/api/projects/{id}/architecture/components/{recordId}` | 200, полный агрегат |
| POST | `/api/projects/{id}/architecture/integrations` | 201, полный агрегат с классификацией |
| PATCH | `/api/projects/{id}/architecture/integrations/{recordId}` | 200, полный агрегат с классификацией |

POST требует существующие проект/паспорт и expectedPassportVersion, берёт общий lock
проекта, затем lock паспорта. Новая UUID-запись получает техническую версию 0 через
Hibernate @Version; техническая версия паспорта увеличивается на 1 в той же транзакции.
Версия проекта и даты/реквизиты паспорта не меняются.

PATCH проверяет родителей и принадлежность записи проекту, блокирует только её строку,
проверяет expectedVersion и увеличивает только версию записи, включая прежние значения.
Версия паспорта не меняется. Разные записи могут завершать правки независимо.
Пропущенные поля сохраняются; null очищает только nullable-реквизиты.

Классификация интеграции обязательна при POST, минимум один класс. В PATCH переданный
массив заменяется целиком; отсутствие сохраняет набор; null/[]/дубликаты/неизвестные коды
отклоняются. Классы других интеграций не затрагиваются. Поля, классификация, версии,
flush и сборка полного DTO/оценки находятся в одной write-транзакции.

Валидация текста, NFC/trim, типов, каталогов и версий переиспользует B3.1.
Строгий bounded JSON parser выделен в общий компонент архитектурных write-маршрутов;
правила старых API не менялись. Добавлены безопасные 404 для записей и 409 с реальной
currentVersion и ресурсом PASSPORT/COMPONENT/INTEGRATION. Прямые JPA-ошибки также
преобразуются в безопасный DATABASE_ERROR; исходное исключение в ответ не попадает.

Пользовательская версия нового паспорта — **1.0**, отдельное read-only JSON-поле
`passport.documentVersion`. Это постоянные метаданные DTO на текущем этапе, без новой
колонки/миграции и без правил нумерации будущих редакций. Целочисленное `version`
остаётся техническим счётчиком конкурентных изменений и не преобразуется в номер документа.

Формула оценки не менялась. HIGH/CRITICAL-интеграции, LOW/MEDIUM-интеграции, принятые
HIGH/CRITICAL-риски и сохранение всех причин работают по актуальным согласованным правилам.
`officialGoLiveApproval=false`, принятые риски — UNVERIFIED. Бюджета в ответах нет.

Полный контракт и примеры запросов:
`docs/PM-003B3.2a-components-integrations-api.md`.

### Что проверено

1. POST/PATCH обоих типов, UUID, техническая версия новой записи 0, увеличение версии
   паспорта только на POST, неизменность версии проекта и дат паспорта. Полный ответ
   совпадает с GET после commit, включая все коллекции, версии и оценку.
2. Пользовательская documentVersion=1.0 сохранена при технических изменениях; клиент
   не может задать documentVersion, технические version, ID или вычисленные показатели.
3. Существование проекта/паспорта, отсутствующая и чужая запись: безопасные 404,
   без раскрытия версии чужой записи и без изменения строк.
4. Устаревшие версии POST/PATCH: реальные currentVersion и корректный versionResource;
   при 409 весь снимок данных остаётся прежним.
5. Nullable, сохранение пропущенных полей, очистка реквизитов; повторный PATCH прежних
   значений увеличивает версию ровно один раз. Непустая замена набора затрагивает только
   одну интеграцию, не меняет техническую версию паспорта.
6. Обязательные поля, enum, типы, null, строки/длины, NFC, многострочность, position=0
   и Integer.MAX_VALUE, boolean=false, полный каталог классов, дубликаты/пустые наборы.
   Строгий JSON: неизвестные/повторные поля, trailing JSON, неверный корень и размер тела.
   Некорректные/опасные входы не отражаются в ответе и не меняют строки.
7. Fault injection **после реального изменения и flush классификации**: PATCH откатывает
   имя/версию интеграции и весь набор; POST откатывает новую интеграцию, классификацию
   и уже увеличенную версию паспорта. Сравнение всех 12 таблиц до/после идентично.

### Конкурентность и удаление

| Сценарий | Результат |
|---|---|
| Два POST компонентов с одной версией паспорта | Один HTTP 201, один HTTP 409 PASSPORT_VERSION_CONFLICT, currentVersion=1; одна запись |
| Два POST интеграций с одной версией паспорта | Один 201, один 409; одна интеграция и корректные классы |
| POST компонента и POST интеграции с одной версией паспорта | Один 201, второй 409; используется общий протокол создания |
| Два PATCH одного компонента / одной интеграции | Второй ждёт lock; один 200, один 409 с версией записи 1; сохраняется Winner, версия паспорта прежняя |
| PATCH двух разных компонентов / двух разных интеграций | Второй завершается 200 **до** освобождения первой транзакции; обе версии записей +1, паспорт без изменений |
| POST компонента/интеграции первым, затем DELETE проекта | DELETE фактически ждёт lock проекта, затем 409 PROJECT_HAS_DEPENDENCIES; POST 201; данные сохранены |
| DELETE проекта первым, затем POST компонента/интеграции | POST фактически ждёт lock; DELETE получает 409 из-за уже существующего паспорта и откатывается; POST затем 201; данные сохранены |

В тестах разные транзакции/соединения, CountDownLatch и проверка реального состояния
H2 INFORMATION_SCHEMA.SESSIONS: BLOCKED, BLOCKER_ID, запрос к ожидаемой таблице и
`Future.isDone()==false` при удерживаемом lock. После подтверждения ожидания первая
транзакция отпускается. Цикл с коротким park только опрашивает состояние H2;
тест не полагается на случайную задержку запуска запроса.
В независимых PATCH проверяется завершение второй операции, пока первая ещё удерживает lock.
Проверено отсутствие сирот паспорта, компонентов, интеграций и классов интеграции.

Особенность текущего DELETE: создание ребёнка возможно только при существующем паспорте,
а паспорт уже является зависимостью проекта по FK NO ACTION. Поэтому успешное удаление
такого проекта не допускается в **обоих** порядках. Существующий DELETE не расширялся.
Дальнейший DELETE паспорта/дочерних строк обязан соблюдать общий протокол и повторные
проверки; его реализация сюда не включена.

В первом целевом прогоне обнаружено ручное присваивание version=0 перед persist для
сущностей с назначенным UUID: Hibernate считал их detached. Исправлено — начальную
техническую версию задаёт @Version при persist/flush. Затем 26 целевых тестов прошли;
полный финальный прогон включает ещё регрессию актуальной оценки, всего 27 новых тестов.
