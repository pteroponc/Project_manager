# PM-003B3.3c — impact и безопасное удаление проекта

## Совместимый контракт

`DELETE /api/projects/{id}` сохраняет прежний маршрут и успех **204 без тела**.
Версии, instanceId или новые query-параметры для DELETE проекта не добавляются.
Отсутствующий проект — структурированный 404 PROJECT_NOT_FOUND.

`GET /api/projects/{id}/deletion-impact` сохраняет все поля и отдельные счётчики:
id/name, taskCount, milestoneCount, architecturePassportCount, componentCount,
integrationCount, checkCount, securityRiskCount, deletionAllowed, blockers.
После B3.3c `architectureImpactPreliminary=false`.

GET — одна readOnly=true/REPEATABLE_READ транзакция. DELETE — одна write-транзакция:
общий ProjectWriteLock → повторный подсчёт семи зависимостей → отказ либо удаление
только проекта и flush. Обе операции используют ProjectDependencyService: семь
scalar COUNT, без загрузки полного архитектурного агрегата/текстов/детей.
GET дополнительно читает проект для существования и имени (всего восемь запросов).
DELETE использует уже заблокированный проект. При ненулевом счётчике записей нет.
Каскады, очистка зависимостей и автоматические повторы не добавляются.

| Зависимости | code |
|---|---|
| Только задачи | PROJECT_HAS_BOARD_CARDS |
| Только контрольные точки | PROJECT_HAS_MILESTONES |
| Задачи и точки вместе | PROJECT_HAS_DEPENDENCIES |
| Любые архитектурные или смешанные | PROJECT_HAS_DEPENDENCIES |

В 409 прежние `code` и `error` сохраняются, добавляется актуальный `impact`,
рассчитанный после получения lock в той же write-транзакции:

```json
{
  "code": "PROJECT_HAS_DEPENDENCIES",
  "error": "Project has dependent records and cannot be deleted: p",
  "impact": {
    "id": "p",
    "name": "Project",
    "taskCount": 0,
    "milestoneCount": 0,
    "deletionAllowed": false,
    "blockers": ["У проекта есть архитектурный паспорт"],
    "architecturePassportCount": 1,
    "componentCount": 0,
    "integrationCount": 0,
    "checkCount": 0,
    "securityRiskCount": 0,
    "architectureImpactPreliminary": false
  }
}
```

Причины/порядок такие же, как у GET. Отдельные дочерние архитектурные строки имеют
FK к паспорту: при их наличии паспорт также учитывается, а не заменяется одним
суммарным счётчиком. Классы данных/среды защищены наличием паспорта и его FK;
новых полей в project impact для них не добавляется.

## Протокол записи и конкурентность

- Карточки: оба createCard/updateCard overload, deleteCard — lock проекта до записи;
  transferCard — lock обеих строк проектов в сортированном порядке ID до изменения projectId.
- DemoDataInitializer не пишет карточки напрямую: транзакционный run вызывает BoardService.
- Контрольные точки: create/patch/delete теперь явно берут ProjectWriteLock до CAS
  версии проекта и записи. API и expectedVersion проекта прежние. Ранее CAS сам
  блокировал UPDATE проекта до commit и обнаруживал удалённый проект, но общий
  явный lock делает порядок существования/версии/записи единым с DELETE.
- Паспорт POST/DELETE, POST детей/initialize и DELETE детей уже используют проект →
  паспорт (→ ребёнок), удерживая lock до commit. Они не ослаблены этим этапом.
- PATCH паспорта/наборов и существующих детей не создаёт/переносит владельца:
  существующий паспорт всегда блокирует DELETE проекта. Их независимые locks,
  версии и instanceId-протокол сохранены.

Создание первым → DELETE ждёт, затем возвращает 409 с актуальным impact.
DELETE первым → создание ждёт, затем получает безопасный 404 без сироты/HTTP 500.
Перенос первым → удаление исходного проекта разрешено, целевого запрещено;
удаление пустого целевого первым → перенос отклонён без потери исходной карточки.
Исходный проект с ещё не перенесённой карточкой удалить нельзя.
Два DELETE пустого проекта → один 204, второй после ожидания 404.

FK V003 NO ACTION/NOT NULL/индекс проверяются напрямую на отдельной памяти,
мигрированной V002→V003→V004→V005 и запущенной с ddl-auto=validate. Один FK сам
не заменяет общий протокол на H2 2.3.232. Прямые SQL/внешние писатели вне протокола
не входят в гарантию сериализации; все писатели должны соблюдать его.

Искусственный сбой после DELETE/flush откатывает транзакцию полностью. Техническая
ошибка БД возвращает безопасный DATABASE_ERROR без SQL/stack trace/пути/класса;
не превращается в выдуманный impact. Известные зависимости отклоняются до удаления,
а не за счёт перехвата FK-ошибки. Нового логирования содержимого нет.

Frontend, схема, миграции, datasource-профили и формула B2 не изменены. Рабочая
файловая БД и её копии не открываются. Коммит/push — после отдельного ревью.
