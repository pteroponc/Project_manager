## Реализация

В строках компонентов, интеграций, проверок и рисков добавлено «Удалить».
В разделе паспорта — «Удалить паспорт». Выбор записи выполняется по UUID,
а не индексу массива. В подтверждении показаны проект, тип и название записи;
у проверки название берётся из действующего каталога checkType.
Технические версии и UUID не выводятся в пользовательский текст.

Подтверждение использует общую оболочку редактора и отдельный неотмеченный флаг.
Без явного выбора флага DELETE не отправляется. Отмена не вызывает DELETE.
Для интеграции указано удаление выбранной интеграции и только её классификации;
классы других интеграций и паспорта сохраняются. Для проверки указаны неполнота
набора и отсутствие автоматического восстановления/дополнения непустого набора.

### Неизменяемое намерение удаления

При открытии фиксируются исходные projectId, UUID записи, версия записи,
версия и instanceId паспорта. Эти значения хранятся отдельно от редактируемых
полей и не обновляются из impact, ошибок или сверки. Даже изменение объекта
исходного снимка не меняет адрес/параметры уже открытого подтверждения.

После попытки отправки DELETE исходный объект агрегата помечается использованным
в WeakSet, без изменения его строк/полей. Простое закрытие ошибочного подтверждения
и открытие нового из старого снимка не разрешает повторное удаление — ни той же,
ни другой записи. Требуется явная загрузка актуального агрегата, его открытие
и новое подтверждение с неотмеченным флагом. Один impact не заменяет агрегат
и не восстанавливает пригодность старых токенов. Успешный DELETE возвращает новый
полный агрегат, который становится текущим снимком.

## Точные DELETE-контракты

Четыре явных пути:

```text
/api/projects/{projectId}/architecture/components/{recordId}
/api/projects/{projectId}/architecture/integrations/{recordId}
/api/projects/{projectId}/architecture/checks/{recordId}
/api/projects/{projectId}/architecture/risks/{recordId}
```

Метод DELETE, без JSON-тела. Ровно четыре одиночных query-параметра:

```text
?expectedVersion=981240&expectedPassportVersion=981238&expectedPassportInstanceId=f071002a-3da5-4bc6-b472-6ba147514ea2&confirmed=true
```

expectedVersion относится к выбранной записи. expectedPassportVersion и instanceId —
к исходному паспорту. Значения выше — пример из изолированных фикстур. Путь и UUID
кодируются через encodeURIComponent. Версии сериализуются как неотрицательные
десятичные целые; значения вне безопасного целочисленного диапазона JavaScript
не отправляются. confirmed передаётся только точной строкой `true`.

Удаление паспорта:

```text
DELETE /api/projects/{projectId}/architecture?expectedVersion=981238&expectedPassportInstanceId=f071002a-3da5-4bc6-b472-6ba147514ea2&confirmed=true
```

Ровно три query-параметра, без тела. expectedVersion здесь относится к паспорту;
expectedPassportVersion не добавляется. Версии, принадлежность и окончательный
запрет по зависимостям по-прежнему проверяет существующий backend под блокировками.

## Impact паспорта

До разрешения подтверждения выполняется
`GET /api/projects/{projectId}/architecture/deletion-impact`.
Показаны passportPresent, все серверные blockers и все шесть счётчиков:

| Поле | Подпись |
|---|---|
| componentCount | Компоненты |
| integrationCount | Интеграции |
| checkCount | Проверки |
| securityRiskCount | Риски ИБ |
| dataClassCount | Классы данных паспорта |
| environmentCount | Среды |

При deletionAllowed=false, отсутствии паспорта, ошибке чтения или непригодном
ответе флаг и кнопка удаления отключены. Проверяется принадлежность impact
исходному проекту и пригодность всех шести счётчиков; противоречивое разрешение
с ненулевыми зависимостями не принимается. Разрешение не вычисляется из текущего
снимка карточки: нужен пригодный серверный impact с deletionAllowed=true.

При ошибке impact предлагается явный повтор только GET; DELETE не отправляется.
При разрешении поясняется: удаляется только пустой паспорт, проект сохраняется;
проверка предварительная, окончательное решение принимает DELETE. Классы/среды
не очищаются автоматически — нужны отдельные явные действия пользователя.
Ответ impact не меняет версии, instanceId или сам снимок агрегата.

## Полный ответ и ошибки

- При 200 используется только полный агрегат ответа. Нет дополнительного GET
  после успеха и нет ручного удаления элементов из снимка в браузере.
- Для удаления паспорта ожидаются passport=null, пустые архитектурные коллекции
  и серверная NOT_ASSESSED с PASSPORT_MISSING. Показываются отсутствие паспорта
  и действие создания, при сохранённом проекте. Новое создание использует версию
  проекта из возвращённого агрегата; старый instanceId не переносится в POST.
- Для дочерней записи проверяется пригодность полного ответа, сохранение исходного
  экземпляра паспорта и отсутствие выбранного UUID в соответствующей коллекции.
  Неполные/чужие/непригодные ответы, включая сломанные коллекции/оценку, не применяются.
- При 409 показана безопасная причина: устаревшие сведения, новый экземпляр
  паспорта или зависимости. Если сервер вернул impact при отказе удаления паспорта,
  отображаются его актуальные счётчики и причины. Исходные токены не меняются.
- Для передачи impact из настоящего ответа ошибки fetchJson дополнен свойством
  error.impact. Содержимое ошибок и обоснований не логируется.
- При 404 сообщается отсутствие ресурса и явно указано, что собственный DELETE
  не подтверждён как успешный. Никакого удаления строки из старого снимка нет.
- Сеть, 5xx, 204 вместо полного агрегата, непригодный 200 — неизвестный результат:
  сервер мог выполнить удаление. Нет автоматических повторов; предлагается явная сверка.
- При 400/404/409/неизвестном результате старое подтверждение блокируется.
  Попытка обойти блокировку закрытием формы и повторным открытием из прежнего
  снимка также заблокирована. Новый DELETE — только из нового актуального агрегата
  с новым явным подтверждением.

Сверка выполняет явный GET архитектурного агрегата. Она отличает удалённую запись
от нового instanceId паспорта и показывает название в подтверждении рядом
с актуальным названием ресурса. Флаг подтверждения не выдаётся за поле сервера.
Сверка сама ничего не удаляет и не заменяет токены старого намерения.

## Навигация и сохранность

- Двойное нажатие отправляет один DELETE. Флаг блокируется на время запроса.
- При уходе во время DELETE или после неизвестного результата объясняется,
  что закрытие не отменяет запрос удаления.
- Переход из изменённого редактора к удалению требует отдельного подтверждения
  потери ввода. Отказ сохраняет ввод редактора и не открывает удаление.
- Активен один редактор/подтверждение. Переходы по проектам, разделам и истории
  браузера, а также beforeunload используют общий механизм C.3a–C.3d.
- Поздние impact/DELETE success/error/comparison/finally не меняют другую форму,
  другой проект или более актуальный снимок. Используются идентичность формы
  и существующий счётчик запросов архитектурного представления.
- Названия и серверные blockers экранируются. SQL, пути, Java-классы и stack trace
  из ошибок не выводятся. Нового логирования содержимого нет.
- Уровни рисков, готовность и все причины по-прежнему берутся с сервера.
  Удалённая проверка не восстанавливается, непустой набор не дополняется.

### Ограничения

Браузер использовал HTTP-фикстуры, не запущенный Java backend. Конфликт зависимости
между impact и DELETE — принудительный ответ фикстуры для проверки клиента,
не доказательство конкурентных транзакций БД. В штатном backend создание зависимости
также меняет версию паспорта: первым отказом может быть конфликт версии.
Транзакции, locks, FK и атомарность backend в этом frontend-этапе не менялись
и повторно не доказывались. Maven не запускался. Рабочая БД и её совместимость
не проверялись. Версии за пределами безопасного диапазона JavaScript не отправляются.
Схема, миграции, каскады и операции удаления проекта не изменены.
