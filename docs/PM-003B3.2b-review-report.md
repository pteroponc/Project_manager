## Реализация

| Метод | Маршрут | Успех |
|---|---|---|
| POST | `/api/projects/{id}/architecture/checks/initialize` | 201, полный архитектурный агрегат |
| PATCH | `/api/projects/{id}/architecture/checks/{recordId}` | 200, полный агрегат |

Инициализация требует проект/паспорт и expectedPassportVersion. Общий lock проекта,
затем lock паспорта, проверка актуальной технической версии и полного отсутствия проверок.
Создаются ровно десять типов из каталога оценщика, UUID выдаёт сервер;
required=true, status=NOT_STARTED, owner/plannedDate/actualDate/comment=null.
Hibernate задаёт новым записям version=0. Версия паспорта увеличивается **один раз за набор**.
Любой непустой набор, включая неполный, не дополняется: безопасный 409 без записи.
При устаревшей версии сначала возвращается PASSPORT_VERSION_CONFLICT с актуальной версией;
при актуальной версии непустого набора — CHECKS_ALREADY_EXIST.

PATCH требует expectedVersion самой проверки, существующие родители и принадлежность.
Разрешены только required/status/owner/plannedDate/actualDate/comment. Пропущенные поля
сохраняются, null очищает nullable-реквизит. Сначала строится отдельное итоговое состояние
и проверяются все сочетания, только затем изменяется managed-сущность:

- обязательная проверка не допускает NOT_REQUIRED;
- PASSED требует actualDate; у любого другого статуса actualDate должна быть null;
- required=false требует NOT_REQUIRED и непустой comment.

Противоречие даёт 400 целиком. Только версия проверки увеличивается ровно на 1,
включая прежние значения; версии паспорта/проекта не меняются. Lock относится к одной
проверке, разные проверки редактируются независимо. Даты паспорта не меняются.
Пользовательская documentVersion остаётся **1.0**, технические версии отдельные.

Строгий bounded JSON parser, version/text/NFC/date validators, формат ошибок и полный
DTO переиспользуют B3.1/B3.2a. Проверки/запись/flush/DTO/пересчёт — в одной сервисной
write-транзакции через существующий cardAfterWrite/Propagation.MANDATORY.
Формула и согласованные правила B2 не менялись. Ответ сохраняет все причины и принятые
высокие риски, officialGoLiveApproval=false, UNVERIFIED; бюджет не возвращается.
Отдельного GET после завершения записи нет. Существующие GET остаются read-only.

Полный контракт, каталоги, матрица допустимых состояний и примеры:
`docs/PM-003B3.2b-checks-api.md`. План PM-003 исправлен: формулировка о «недостающем наборе»
и разрешённом поштучном POST для восстановления типов больше не применяется.

### Покрытие

1. Инициализация ровно десяти уникальных типов и UUID, правильный порядок каталога в DTO,
   начальные поля/null/версии. Полный ответ совпадает с GET после commit.
   Версия паспорта +1, версия проекта и даты паспорта прежние, documentVersion=1.0.
2. Повтор при актуальной версии и частичный существующий набор из одной проверки —
   CHECKS_ALREADY_EXIST; при устаревшей версии — PASSPORT_VERSION_CONFLICT.
   Полные снимки 12 таблиц идентичны до/после отказа; частичный набор не исправляется.
3. Strict JSON и разрешённые поля инициализации, неверные типы/версии, дубликаты,
   trailing JSON, максимальный размер тела. Поштучный POST и DELETE не реализованы.
4. Частичный PATCH, сохранение owner/дат/status/required, очистка nullable-полей,
   NFC и многострочность, повторение прежних значений: версия проверки +1 каждый раз.
5. Противоречивые объединённые состояния, включая переход из PASSED без очистки
   actualDate и очистку обоснования уже необязательной проверки; все дают 400 без записи.
   Проверены корректные переходы с одновременным изменением связанных полей.
6. Неизменяемые поля, enum, strict JSON/types, пустые/опасные строки, длины 255/2000,
   запрет null для required/status, реальные ISO-даты, 2026-02-29/30 отклоняются,
   2024-02-29 принимается. Ошибки не отражают исходные значения или внутренние детали.
7. Отсутствующие родители, отсутствующая/чужая проверка и устаревшие версии.
   409 содержит реальную currentVersion и PASSPORT/CHECK; чужая версия не раскрывается.
8. После flush инициализации fault injection на этапе загрузки DTO подтверждает внутри
   write-транзакции наличие десяти строк и passport.version=1, затем бросает JPA-ошибку.
   После 500 все строки и версия паспорта откатываются; повторная инициализация успешна.
9. Ошибка после flush PATCH подтверждает новую версию и PASSED в той же транзакции,
   затем DataAccess-ошибка: поля, даты и версия полностью откатываются. Оба вида ошибок
   дают безопасный DATABASE_ERROR без SQL/пути/Java-класса/исходного исключения в ответе.
10. PASSED всех десяти → READY; одна NOT_REQUIRED с обоснованием при девяти PASSED → READY;
    обязательная BLOCKED → BLOCKED; обычная CHANGES_REQUIRED → ATTENTION_REQUIRED;
    PRODUCTION_ADMISSION/CHANGES_REQUIRED → BLOCKED, с сохранением причин меньших приоритетов.
11. plannedDate вчера даёт CHECK_OVERDUE, сегодня/+14 попадают в upcomingChecks,
    +15 — нет; calculationDate/timeZone соответствуют единому московскому контексту.
12. DTO внутри write-транзакции видит незакоммиченные десять строк и версию паспорта;
    параллельный GET из другого соединения их ещё не видит. После commit полный JSON равен DTO.
13. Повторные GET до и после записи не создают проверки, не меняют строки/даты/версии.
    Сравниваются все поля 12 таблиц, упорядоченные по стабильным ключам. Остальные сущности
    сохранены полностью: проекты с нулями и максимальным бюджетом, задачи, поезда,
    контрольные точки, компоненты, интеграции/классы, риск, классы/среды паспорта.
    В паспорте единственная разница после инициализации — техническая версия +1.
14. Полный прежний Maven-набор, включая B3.1/B3.2a/B2/B1/PM-001/PM-002, прошёл без регрессий.

### Конкурентность

| Сценарий | Подтверждённый результат |
|---|---|
| Две инициализации expectedPassportVersion=0 | Один 201 с десятью записями, второй ждёт project lock и получает 409 PASSPORT_VERSION_CONFLICT/currentVersion=1; дубликатов нет |
| Initialize первым, POST компонента вторым | 201 initialize, второй после ожидания 409 версии паспорта; компонент не создаётся |
| POST компонента первым, initialize вторым | 201 component, initialize после ожидания 409; проверки не создаются |
| Initialize первым, POST интеграции вторым | 201 initialize, второй после ожидания 409; интеграция/классы не создаются |
| POST интеграции первым, initialize вторым | 201 integration, initialize после ожидания 409; проверки не создаются |
| Два PATCH одной версии одной проверки | Второй фактически ждёт lock строки; один 200, один 409 CHECK_VERSION_CONFLICT/currentVersion=1; сохраняется Winner |
| PATCH разных проверок | Второй завершает 200 до освобождения первой транзакции; обе проверки version=1, passport.version не меняется |

Используются отдельные соединения/транзакции и CountDownLatch. До освобождения первой
транзакции проверяется H2 INFORMATION_SCHEMA.SESSIONS: реальный BLOCKED, BLOCKER_ID,
запрос к ожидаемой таблице, одновременно Future.isDone()==false. Только затем отпускается
барьер и проверяется результат. Короткий park опрашивает состояние, не задаёт случайный
порядок запуска. Подтверждено отсутствие сирот проверок/паспорта.

Первый целевой прогон выявил два тестовых ожидания: отсутствующий маршрут в текущей
конфигурации может дать 404 вместо 405; изменение версии влияло на прежнюю сортировку
снимка через строковое представление всей строки. Исправлены тесты: проверяется отсутствие
маршрута, снимки упорядочиваются по стабильным ключам. Новые операции и конкурентные
сценарии проходили уже в первом прогоне; финальный полный набор прошёл полностью.
