# PM-003B2.2 — контракт API чтения

База этапа: `codex-dev`, `60aebc890a2f4464503796c3e7fbd9560cfc3775`.
Формула `ArchitectureReadinessAssessmentService` остаётся из PM-003B2.1.

## Маршруты и снимок

| GET | Ответ 200 |
|---|---|
| `/api/projects/{id}/architecture` | `project`, `passport`, `dataClasses`, `environments`, `components`, `integrations`, `checks`, `risks`, `assessment` |
| `/api/architecture/portfolio` | `calculationDate`, `timeZone`, `totalCount`, `page`, `size`, `totalPages`, `summary`, `items` |
| `/api/projects/{id}/architecture/deletion-impact` | Наличие паспорта, шесть отдельных счётчиков, `deletionAllowed`, `blockers` |
| `/api/projects/{id}/deletion-impact` | Старые поля `id`, `name`, `taskCount`, `milestoneCount`, `deletionAllowed`, `blockers`; пять архитектурных счётчиков и `architectureImpactPreliminary=true` |

`project` содержит только `id`, `name`, `owner`, `quarter`, `projectStatus`, `version`.
Бюджет не включён в новые ответы. Дочерние записи содержат `projectId` и собственную
`version`; паспорт — `projectId`, `version`, `createdAt`, `updatedAt` и поля модели.
Наборы классов данных и сред возвращаются отсортированными массивами кодов; у них нет
собственной версии в модели хранения. `integrations[].dataClasses` содержит классификацию
конкретной интеграции. Компоненты упорядочены по `position`, затем ID; проверки — по каталогу
десяти типов, затем ID; интеграции и риски — по ID. Nullable-поля остаются JSON `null`.

Риск получает вычисленный `level`; у `ACCEPTED` — `acceptanceVerification=UNVERIFIED`.
Оценка возвращается целиком: статус, подпись, все причины всех приоритетов, ближайшие
проверки, принятые высокие риски с обоснованием, дата, часовой пояс и
`officialGoLiveApproval=false`. Никакой повторной формулы в API нет.

Отсутствующий проект во всех трёх маршрутах проекта даёт 404:

```json
{"code":"PROJECT_NOT_FOUND","error":"Project not found"}
```

Для существующего проекта без паспорта карточка даёт 200: `passport=null`, шесть пустых
архитектурных коллекций, оценка `NOT_ASSESSED` с `PASSPORT_MISSING` и остальными причинами,
которые вернул расчёт (например, отсутствующие типы проверок). GET ничего не создаёт.
Проект без паспорта включён в портфель; `passportPresent=false`, `criticality=null`.

Загрузка скалярных проекций, сборка DTO и расчёт находятся внутри одной сервисной
транзакции `@Transactional(readOnly=true, isolation=REPEATABLE_READ)`.
Open-in-view не требуется. JPA-сущности не передаются клиенту и не загружаются этими
проекциями. Чтение не вызывает сохранение и не получает блокировок на изменение.
Карточка и портфель переиспользуют сборщик `ArchitectureReadinessSnapshot` и неизменённый
оценщик. Один `ArchitectureAssessmentContext`, полученный от внедряемого Clock, используется
для всех оценок запроса; зона — `Europe/Moscow`.

## Параметры портфеля

Все фильтры пересекаются; параметры и допустимые значения приведены ниже.
Значения строковых фильтров и сортировок обрезаются по краям и сравниваются без учёта регистра.
Имена параметров чувствительны к регистру.
Для сохранённых `quarter` и `projectStatus` SQL-фильтры используют `lower(trim(...))`.
Список допустимых кварталов получен тем же SQL-выражением `lower(trim(p.quarter))`,
поэтому проверка квартала и фильтрация согласованы. Это нормализация сравнения:
значения в БД и возвращаемые поля проекта сохраняют исходный регистр и крайние пробелы.

| Параметр | Значения и умолчание |
|---|---|
| `query` | Умолчание — пустая строка. Поиск подстроки по названию **или владельцу**, без учёта регистра. Summary не участвует; `%` и `_` — обычные символы, не маски SQL. |
| `quarter` | `all` по умолчанию либо квартал, который есть в текущем снимке проектов. Неизвестный квартал — 400. |
| `projectStatus` | `all` (умолчание), `planned`, `active`, `paused`, `done` |
| `readiness` | `all` (умолчание), `BLOCKED`, `ATTENTION_REQUIRED`, `NOT_ASSESSED`, `READY` |
| `criticality` | `all` (умолчание), `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`, `unspecified` — критичность не указана, включая проекты без паспорта |
| `sort` | `name` (умолчание), `owner`, `quarter`, `projectStatus`, `readiness`, `criticality` |
| `direction` | `asc` (умолчание), `desc` |
| `page` | Целое число от 0; умолчание 0 |
| `size` | Целое число 1…100; умолчание 20 |

При `asc` готовность упорядочена `BLOCKED → ATTENTION_REQUIRED → NOT_ASSESSED → READY`,
критичность — `LOW → MEDIUM → HIGH → CRITICAL`. Остальные ключи — строковые,
без учёта регистра. `desc` обращает порядок известного ключа.
При равенстве ключей ID всегда идёт по возрастанию; отсутствующие/пустые значения остаются
в конце в обоих направлениях. Строки неизвестной критичности также идут в конце.

Неизвестное имя параметра, неизвестный фильтр/сортировка/направление, повтор одного
параметра и некорректная пагинация дают безопасный 400:

```json
{"code":"BAD_REQUEST","error":"Invalid architecture portfolio parameters"}
```

Пустой результат и страница за пределами набора дают 200 с `items=[]`.
`totalCount` и `summary` относятся ко всему отфильтрованному набору **до пагинации**;
`totalPages=ceil(totalCount/size)` (для пустого набора 0).
`summary` содержит `readinessCounts` по четырём статусам, `acceptedHighRiskCount`,
`passportPresentCount`, `passportMissingCount`. Каждый принятый HIGH/CRITICAL-риск считается
отдельно; численность не ограничивается количеством строк текущей страницы.

Пример: `/api/architecture/portfolio?query=alice&quarter=q1&projectStatus=active&readiness=READY&criticality=HIGH&sort=name&page=0&size=20`.

## Пакетная загрузка и объём

Поиск, квартал и статус проекта отбирают кандидатов одним SQL-запросом.
Все необходимые архитектурные строки загружаются JPQL-проекциями для пакетов до 500 ID.
Для портфеля не запрашиваются компоненты и классификация интеграций: формуле они не нужны.
Для одного непустого пакета — 7 запросов: проекты и 6 наборов расчёта.
Каждый следующий пакет добавляет 6 запросов. Явный фильтр квартала добавляет один запрос
списка существующих кварталов для валидации. Пустой набор без фильтра квартала — 1 запрос.
Карточка и паспортный impact — 9 запросов, проектный impact — 11, включая два старых счётчика.
Дочерние таблицы не запрашиваются по отдельности для каждого проекта.

Readiness/criticality, сортировка, агрегаты и пагинация выполняются в памяти внутри того же
снимка. Загружается весь набор кандидатов и его данные оценки, а не только текущая страница.
`size<=100` ограничивает ответ, но не общий объём загрузки. Время, память и длительность
транзакции растут с количеством кандидатов и их дочерних строк; общего лимита сейчас нет.
Для большого портфеля понадобится отдельное решение для объёма/производительности;
нельзя молча обрезать данные, иначе агрегаты и фильтры станут неверными.

## Анализ удаления

Паспортный impact содержит `projectId`, `passportPresent`, `componentCount`,
`integrationCount`, `checkCount`, `securityRiskCount`, `dataClassCount`, `environmentCount`,
`deletionAllowed`, `blockers`. Классы интеграции не подменяют классы паспорта.
При отсутствии паспорта все счётчики равны 0, `deletionAllowed=false`,
`blockers=["Паспорт отсутствует"]`: удалить несуществующий ресурс нельзя.
Существующий паспорт допускается к будущему удалению только при нулевых шести счётчиках.

Проектный impact сохраняет старые поля и причины по задачам/контрольным точкам,
дополнительно учитывает наличие паспорта, компонентов, интеграций, проверок и рисков.
Это предварительная информация: `architectureImpactPreliminary=true`.
Текущий DELETE проекта не расширен. Операции удаления и повторные проверки новых
зависимостей под общей блокировкой проекта относятся к PM-003B3.
Read-only impact не гарантирует, что данные останутся такими до будущего DELETE.

## Безопасность и границы

Ошибки БД используют существующий безопасный 500 `DATABASE_ERROR` / `Database operation failed`;
ответ не содержит SQL, stack trace, путей и Java-классов. Новое логирование содержимого
паспорта и обоснований рисков не добавлено. Обоснования доступны только как данные API,
предусмотренные контрактом. Существующий контур доступа приложения не расширяется этим этапом.

Frontend, операции записи, формула, схема, V002/V003/V004 и datasource-профили не изменяются.
Рабочая файловая БД и её копии не открываются. Проверки используют только отдельные
одноразовые in-memory H2 с защитой PM-000; приложение с рабочим datasource не запускалось.
