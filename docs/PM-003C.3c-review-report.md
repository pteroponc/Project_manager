## Явная инициализация

Кнопка «Создать набор проверок» появляется только при наличии паспорта
и полностью пустом массиве checks. Для любого непустого набора, включая
одну проверку, кнопки нет; дополнительная проверка есть и в модели редактора.
GET и переходы по разделам ничего не создают.

Кнопка открывает подтверждение в общей оболочке редактора. В нём указаны проект,
десять типов и последствия: обязательные проверки, статус «Не начата»,
отсутствие владельцев, дат и комментариев. Нужен явный выбор
«Подтверждаю создание десяти проверок для этого паспорта», затем нажатие
«Создать десять проверок». Сами записи создаёт сервер; браузер их не синтезирует.

POST `/api/projects/{id}/architecture/checks/initialize`:

```json
{
  "expectedPassportVersion": 981238,
  "expectedPassportInstanceId": "f071002a-3da5-4bc6-b472-6ba147514ea2"
}
```

Пример использует токены тестовой фикстуры. В рабочем интерфейсе projectId,
instanceId и техническая версия фиксируются из исходного агрегата при открытии
подтверждения. Флаг подтверждения в JSON не отправляется: контракт содержит
ровно два поля. Переход к другому проекту или новому экземпляру паспорта не
переносит подтверждение: требуется новая форма с неотмеченным флагом.
Технические значения не показываются пользователю.

Двойное нажатие отправляет один POST. При конфликте версии/instanceId или
CHECKS_ALREADY_EXIST автоматического повтора нет. Сверка показывает текущий
размер набора, но не заменяет исходные токены и не дополняет неполный набор.

## Редактирование проверки

«Редактировать» передаёт UUID записи, поиск не зависит от позиции в массиве.
Заголовок содержит тип выбранной проверки. Тип также показан в тексте формы,
но не является редактируемым полем и не отправляется на сервер.

Доступны шесть полей: required, status, owner, plannedDate, actualDate, comment.
Owner — до 255, многострочный comment — до 2000 символов по API. Текст
обрезается по краям, нормализуется NFC, переводы строк приводятся к LF.
Исходный ввод остаётся в форме при ошибке. Секреты и небезопасный текст
окончательно проверяет существующий backend; его ошибки показываются безопасно.

PATCH `/api/projects/{id}/architecture/checks/{recordId}`:

```json
{
  "expectedVersion": 981241,
  "required": false,
  "status": "NOT_REQUIRED",
  "owner": null,
  "plannedDate": null,
  "actualDate": null,
  "comment": "Проверка неприменима к согласованному объёму решения."
}
```

Это пример перехода из PASSED с заполненными владельцем и датами.
Отправляются только изменённые поля и исходная версия самой проверки.
Версия и instanceId паспорта в PATCH не добавляются. ID и checkType в тело
не входят. `false` сохраняется как значение; пустое nullable-поле становится
null. Без изменений запрос не отправляется. Разные записи используют свои версии.

### Валидация итогового состояния

Проверяется объединение исходных полей и ввода:

| Итог | Требование |
|---|---|
| required=true | status не NOT_REQUIRED |
| required=false | status=NOT_REQUIRED и непустой comment |
| status=PASSED | actualDate обязательна |
| status не PASSED | actualDate отсутствует |

Например, PASSED → BLOCKED требует явной очистки actualDate.
Один флаг required=false не меняет статус автоматически. Очистка обоснования
у необязательной NOT_REQUIRED без изменения итогового состояния запрещена.
Ошибки размещаются рядом со status, actualDate, comment и другими полями.

Даты вводятся в обычные текстовые поля с подсказкой ГГГГ-ММ-ДД. Это сохраняет
некорректно введённую дату для исправления вместо скрытого сброса браузером.
Проверяются точный формат и существование календарной даты, включая високосные
годы. Нет ограничений относительно сегодняшнего дня или порядка двух дат.
Четырёхзначный год 0000 допускается, как в фактическом LocalDate-валидаторе API.

Статусы, даты и комментарии автоматически не исправляются и не заполняются.
После успешного POST/PATCH применяется полный агрегат ответа без дополнительного
GET. Готовность, причины, принятые риски и officialGoLiveApproval берутся с сервера.
Завершение проверки не объявляется официальным допуском. Пользовательская версия
паспорта по-прежнему отображается из documentVersion.

## Ошибки и сохранение ввода

- 400: весь ввод сохраняется, безопасные сообщения возле полей; исправление
  и новая отправка возможны только по явному действию пользователя.
- 409 версии проверки/паспорта: форма сохраняется, повторная отправка блокируется.
  Явная сверка показывает серверные сведения и ввод без подмены исходных токенов.
- CHECKS_ALREADY_EXIST объясняет запрет инициализации непустого набора.
- CHECK_NOT_FOUND объясняет удаление выбранной записи; другие 404 — отсутствие
  проекта или паспорта. Чужие данные/версии в сообщениях не раскрываются.
- PASSPORT_INSTANCE_CONFLICT при initialize объясняет удаление и повторное
  создание паспорта. При PATCH старой удалённой проверки backend возвращает 404;
  сверка отдельно отличает новый instanceId от изменения прежнего паспорта.
- Сеть, 5xx или непригодный успешный ответ — неизвестный результат: сервер мог
  выполнить запись. Ввод сохраняется, автоматического retry нет.
- Закрытие, переключение редакторов и проектов, история браузера и beforeunload
  используют общую защиту C.3a/C.3b. Активен один редактор.
- Ответ прежней формы, записи, сверки или GET не заменяет новую форму,
  другой проект или более актуальный снимок того же проекта.
- Текст формы и сравнения экранируется; технические идентификаторы и счётчики
  не выводятся в пользовательский текст. Логирование содержимого не добавлялось.
