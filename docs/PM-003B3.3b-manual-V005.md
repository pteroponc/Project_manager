# B3.3b — instanceId и ручная V005

## Хранение и контракт

`project_architecture_passports.instance_id VARCHAR(36) NOT NULL`, UNIQUE
`uq_arch_passport_instance`; сервер назначает новый UUID при каждом POST паспорта.
Значение неизменяемо (`updatable=false`) и возвращается как `passport.instanceId`.
Технический @Version нового паспорта остаётся 0, пользовательская documentVersion=1.0.
Время создания и версия проекта не используются как идентификатор экземпляра.

Защищённые операции требуют пару instanceId + техническая версия:

| Операция | Токен |
|---|---|
| PATCH паспорта | JSON expectedPassportInstanceId + expectedVersion |
| DELETE паспорта | Query expectedPassportInstanceId + expectedVersion + confirmed=true |
| POST компонента/интеграции/риска | JSON expectedPassportInstanceId + expectedPassportVersion |
| POST checks/initialize | JSON expectedPassportInstanceId + expectedPassportVersion |
| DELETE компонента/интеграции/проверки/риска | Query expectedPassportInstanceId + expectedVersion + expectedPassportVersion + confirmed=true |

POST самого паспорта сохраняет expectedProjectVersion; instanceId от клиента
запрещён. PATCH ребёнка сохраняет UUID самой записи и её версию; UUID удалённых
записей не переиспользуются сервером. Отсутствие или неверный тип/формат UUID — 400.
Принимается полная каноническая форма 8-4-4-4-12, регистр hex нормализуется.
Повторное query/JSON-поле запрещено, неизвестные поля по-прежнему запрещены.

После блокировок проверяются наличие и принадлежность, затем instanceId, затем
числовые версии, до первой записи. Не найден ресурс — 404. UUID не совпал —
409 PASSPORT_INSTANCE_CONFLICT с действительной currentVersion и
versionResource=PASSPORT. Нельзя автоматически заменить старый токен новым и
повторить запрос. Клиент получает текущую карточку и заново подтверждает намерение.

Схема locks прежняя: проект → паспорт для POST/initialize/DELETE паспорта;
проект → паспорт → запись для DELETE ребёнка; паспорт для PATCH паспорта.
UUID сравнивается с актуально заблокированной строкой после ожидания, не с кэшем.
В БД он переживает перезапуск приложения и доступен всем экземплярам приложения.
Шесть запретов удаления, версия проекта +1 при удалении, полный откат и DTO в той
же write-транзакции сохраняются. Формула B2 и read-only GET не меняются.

## Порядок ручного применения

Файл: `db/manual/V005__architecture_passport_instance.sql`, H2 2.3.232.
Вне src/main/resources, автоматического мигратора/startup SQL нет.
V002/V003/V004 не изменяются. Рабочая БД и её копии в этой разработке не открывались.
Ниже инструкция для отдельно согласованного эксплуатационного применения.

1. Остановить **все записи** на всё время проверки, DDL, backfill и postcondition.
2. Создать резервную копию согласованным способом и заранее проверить восстановление
   в изолированном окружении; сохранить исходную версию приложения и конфигурацию.
3. Использовать исполнитель SQL, который останавливается при **первой ошибке**.
   Не включать continue-on-error, не выполнять части вручную и не пропускать precondition.
4. Precondition до первого DDL проверяет полную схему после V004: четыре прежние
   таблицы, восемь архитектурных, маркер, столбцы/типы/nullable/defaults, ключи,
   ограничения значений, индексы/FK NO ACTION и версии. Колонка/ограничение instanceId
   и маркер V005 должны отсутствовать; частичная/повторная схема отклоняется.
5. Добавляется nullable-колонка, каждому существующему паспорту назначается RANDOM_UUID,
   затем NOT NULL и UNIQUE, маркер V005. Другие данные, ID, даты и версии не меняются.
6. Postcondition проверяет полную новую схему, UUID/различие значений, NOT NULL/UNIQUE,
   старые ограничения/FK/индексы и оба маркера. Только после успеха разрешать запуск
   новой версии с ddl-auto=validate и обновлённых клиентов.

## Остановка и восстановление

Precondition отказал — остановиться, не исправлять несовместимость скриптом и не
повторять вслепую. H2 DDL имеет неатомарные границы commit: при ошибке после первого
DDL обычного ROLLBACK недостаточно. Записи остаются остановленными; восстановить
**проверенную резервную копию** в согласованном окружении и сверить все данные,
версии/даты, схему и маркеры. Не продолжать частичный backfill/ALTER вручную.

До возобновления записей откат приложения возможен вместе с восстановлением базы
до V005. После новых записей восстановление старой копии теряет последующие данные:
это отдельный план восстановления, не автоматический down-скрипт. Старый клиент
без токена не должен получать совместимый обход защиты. Успешный validate сам по
себе не доказывает UNIQUE/FK: в тестах проверяются метаданные и реальные нарушения.
