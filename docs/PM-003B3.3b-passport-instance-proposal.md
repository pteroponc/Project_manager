# B3.3b — защита экземпляра паспорта: предложение на согласование

Статус: **согласовано пользователем и реализовано в B3.3b**. Этот документ сохраняет историю решения; актуальные результаты — в review-report и manual-V005. Коммита/push нет.
Рабочая файловая БД и её копии не открываются. Предыдущий отчёт/ZIP B3.3b описывают
состояние до этой найденной регрессии и не подтверждают её исправление.

## Причина

Паспорт идентифицируется project_id, а POST всегда создаёт техническую version=0.
После удаления и повторного создания прежние числовые версии снова допустимы.
Это ABA: одной проверки @Version недостаточно для различения экземпляров.
Прирост projects.version при DELETE сам по себе не помогает, поскольку команды
паспорта и его коллекций этот счётчик не проверяют. createdAt также не подходит:
фиксированный Clock и точность хранилища допускают одинаковое время A и B.
Пользовательская documentVersion=1.0 остаётся метаданными документа.

## Предлагаемое решение

Добавить **неизменяемый серверный UUID instanceId** у каждого нового экземпляра
паспорта. Сохранить project_id как нынешний PK и все существующие связи.
Техническая version нового паспорта остаётся 0 и по-прежнему увеличивается на 1.
Оптимистический токен паспорта становится парой `(instanceId, version)`.

UUID генерируется сервером один раз при POST; клиент не может задать или изменить
его. UUID хранится в БД, не вычисляется из времени/версий и не кэшируется как
источник истины: проверка работает после перезапуска приложения и между экземплярами
приложения. documentVersion не участвует в проверках.

### Изменение хранения — только после согласования

- Новая колонка `project_architecture_passports.instance_id VARCHAR(36) NOT NULL`.
- Именованное UNIQUE-ограничение на instance_id; ORM-поле без публичного изменяемого
  API-реквизита, значение не меняется при PATCH/создании/удалении дочерних записей.
- Отдельная ручная `db/manual/V005__architecture_passport_instance.sql` вне ресурсов.
  V002/V003/V004 не изменяются, автоматический запуск не добавляется.
- Предварительная проверка полной ожидаемой схемы после V004, отсутствия новых
  объектов/маркера, остановка при частичном/повторном применении до первого DDL.
- При ручной миграции существующим паспортам назначаются UUID; остальные поля,
  версии и даты остаются прежними. Затем NOT NULL/UNIQUE и postcondition.
- Записи остановлены на время ручной миграции; при частичном DDL восстановление
  проверенной резервной копии. Здесь ни рабочая БД, ни её копии не используются.

### Изменение API — обязательное поле, без совместимого обхода

В полном read/write DTO добавить `passport.instanceId` (read-only). Текущая карточка,
портфельный расчёт, snapshot B2 и формула готовности не меняют смысла.
Портфель не становится источником токена записи: актуальный токен берётся из карточки.

| Маршрут | Новое требование |
|---|---|
| POST `/api/projects/{id}/architecture` | Прежний expectedProjectVersion; новый instanceId выдаёт сервер, клиент его не передаёт |
| PATCH `/api/projects/{id}/architecture` | JSON expectedPassportInstanceId + прежний expectedVersion паспорта |
| DELETE `/api/projects/{id}/architecture` | Query expectedPassportInstanceId + прежние expectedVersion и confirmed=true |
| POST `.../components`, `.../integrations`, `.../risks` | JSON expectedPassportInstanceId + прежний expectedPassportVersion |
| POST `.../checks/initialize` | JSON expectedPassportInstanceId + прежний expectedPassportVersion |
| DELETE `.../{components,integrations,checks,risks}/{recordId}` | Query expectedPassportInstanceId + прежние expectedVersion, expectedPassportVersion, confirmed=true |
| PATCH дочерней записи | Контракт прежний: собственные server UUID recordId и expectedVersion; запись не переносится, UUID нового ребёнка не берётся из старой команды |
| GET и deletion-impact | По-прежнему ничего не создают/меняют; паспорт в карточке содержит новый instanceId |

Без нового поля защищённые команды отклоняются с 400; не выводить его автоматически
из текущего паспорта для старых клиентов. Неизвестные/повторные JSON/query-поля и
неверный UUID — безопасный 400. Это намеренное изменение контракта, требующее обновления
клиентов/контрактных тестов. Frontend в этой работе не реализуется.

Отсутствующие ресурсы сохраняют 404. Несовпадение instanceId — безопасный
409 `PASSPORT_INSTANCE_CONFLICT`, реальная currentVersion и versionResource=PASSPORT.
Никаких автоматических повторов и подстановки нового instanceId в старую команду.
Клиент должен получить актуальную карточку и заново подтвердить намерение.
Обычное несовпадение версии при совпавшем instanceId — прежний PASSPORT_VERSION_CONFLICT.

### Блокировки и атомарность

- Создание паспорта остаётся под ProjectWriteLock и проверкой expectedProjectVersion.
- POST детей/initialize: проект → паспорт, затем сравнение instanceId и версии до записей.
- DELETE паспорта: проект → паспорт, сравнение instanceId/версии → повторные шесть
  счётчиков → прежний запрет либо атомарное удаление/проект +1.
- PATCH паспорта: его row lock, затем сравнение instanceId/версии перед изменениями.
- DELETE ребёнка: проект → паспорт → целевой ребёнок/принадлежность, затем токен
  экземпляра и обе версии до первой записи. Чужой/отсутствующий ребёнок остаётся 404.
- PATCH разных детей остаётся независимым: собственные UUID, locks и @Version;
  принадлежность проекту и существование родителей проверяются как сейчас.

При ожидании блокировки токен сравнивается с фактически заблокированным актуальным
паспортом, а не с ранее прочитанным экземпляром. Все проверки/записи/flush/DTO в одной
транзакции. Никаких изменений формулы B2, каскадов, неявной очистки или ослабления
шести запретов B3.3b.

## Регрессионные проверки

До исправления добавлены шесть параметризованных воспроизводящих тестов в
ArchitecturePassportDeletionIntegrationTest: A создаётся через API с version=0,
команда сохраняется, A удаляется через API, B создаётся в том же проекте с version=0,
команда A должна быть отвергнута без изменения полного снимка 12 таблиц.
Clock фиксированный для обоих экземпляров, так что временная метка не маскирует дефект.
Ожидаемая безопасность выражена проверкой отказа, а не утверждением успешной атаки.

Выполнен целевой прогон этих шести сценариев на изолированной in-memory H2:
**6 тестов, 6 failures, 0 errors, 0 skipped** — регрессия воспроизведена во всех
шести маршрутах. Старые PATCH/DELETE приняты с 200, POST/initialize — с 201.
Это не подтверждение безопасности: новые тесты сейчас красные и должны стать
зелёными только после исправления. Лог — игнорируемый
`tmp/PM-003B3.3b-incarnation-reproduction.log`. `git diff --check` пройден.

В согласованной реализации тесты сохраняют instanceId A и требуют 409 PASSPORT_INSTANCE_CONFLICT;
обновить все защищённые команды и добавить старые DELETE детей, потерянный/неверный
токен, конкурентные POST, ожидающий запрос A через границу DELETE/recreate, перезапуск
контекста приложения с той же in-memory БД, сохранность UUID и полные откаты.
Для дочерних PATCH проверить безопасный 404 старого recordId после удаления A/B,
без блокировки независимых правок разных строк.

V002 → V003 → V004 → V005 проверять только на изолированной in-memory H2: совпадение
старых строк/дат/версий (кроме нового instance_id), условия остановки, метаданные,
NOT NULL/UNIQUE, ddl-auto=validate. Затем полный Maven, существующие JS, diff check,
обновлённый итоговый отчёт и новый ZIP для ревью. Согласование получено, изменения API и схемы реализованы; актуальный итог — в review-report.
