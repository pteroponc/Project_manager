# PM-003B3.2b — явная инициализация и PATCH архитектурных/ИБ-проверок

## Обязательное уточнение B3.3b: экземпляр паспорта

Паспорт возвращает серверный неизменяемый `instanceId` (UUID), техническая версия
нового паспорта остаётся 0, documentVersion=1.0. После удаления новый паспорт того
же проекта получает другой instanceId. Клиент не задаёт instanceId при POST и не
может менять его при PATCH.

**expectedPassportInstanceId обязателен** в JSON PATCH паспорта, POST компонента,
интеграции, риска и checks/initialize; в query DELETE паспорта и всех четырёх типов
дочерних записей. Он передаётся вместе с прежними числовыми версиями/confirmed.
POST самого паспорта сохраняет expectedProjectVersion; PATCH дочерней записи сохраняет
собственный UUID recordId и expectedVersion, без токена паспорта.

Отсутствующий/невалидный UUID — 400; после блокировок сначала проверяются наличие
и принадлежность ресурсов, затем instanceId, затем числовые версии. Несовпадение —
409 PASSPORT_INSTANCE_CONFLICT с реальной currentVersion и versionResource=PASSPORT,
без записей. Ресурс отсутствует — 404. Никакой подстановки токена текущего паспорта
для старой команды или автоматического повтора. Клиенту нужна новая карточка и
повторное подтверждение намерения. Числовые параметры и closed-list JSON/query
дополнены только этим полем. Это изменение контракта обязательно для клиентов.

Пример query дополнительно содержит
`expectedPassportInstanceId=11111111-1111-4111-8111-111111111111`;
в JSON-команде добавляется одноимённое строковое поле с UUID из актуального DTO.
Полная спецификация и ручная миграция: `docs/PM-003B3.3b-manual-V005.md`.

База: `codex-dev`, `7aa0bd13246e33c128a01df27b2ec1a5a14a572e`.
Схема B1b, полный DTO B2.2, согласованный оценщик B2 и валидаторы/JSON B3.1/B3.2a сохранены.

## Маршруты

| Метод | Путь | Успех |
|---|---|---|
| POST | `/api/projects/{id}/architecture/checks/initialize` | 201, полный архитектурный агрегат |
| PATCH | `/api/projects/{id}/architecture/checks/{recordId}` | 200, полный агрегат |

Content-Type `application/json`. Поштучного POST проверок нет; явный DELETE добавлен в B3.3a.
В ответе project/passport/классы/среды/компоненты/интеграции/проверки/риски и assessment.
Все причины и принятые высокие риски сохраняются, `officialGoLiveApproval=false`,
принятие риска — UNVERIFIED, бюджета нет. Формула готовности не изменялась.
Пользовательская `passport.documentVersion` остаётся **"1.0"**; `version` — технический счётчик.

## Инициализация

Тело содержит ожидаемые instanceId и **техническую** версию паспорта:

```json
{"expectedPassportVersion":0,"expectedPassportInstanceId":"11111111-1111-4111-8111-111111111111"}
```

Нужны существующие проект и паспорт. Locks берутся в порядке **проект → паспорт**.
Под lock проверяются текущая версия паспорта и полное отсутствие проверок.
Устаревшая версия даёт PASSPORT_VERSION_CONFLICT с реальной currentVersion.
Если версия актуальна, любой непустой набор даёт CHECKS_ALREADY_EXIST, в том числе
набор из одного типа. Неполный набор не дополняется и не исправляется.
Ни строки, ни версии при 409 не меняются.

В полностью пустом наборе создаются ровно десять уникальных типов из единого каталога оценщика:

1. ARCHITECTURE_APPROVAL
2. SECURITY_REQUIREMENTS
3. DATA_CLASSIFICATION
4. THREAT_MODEL
5. SECURITY_ASSESSMENT
6. ACCESS_CONTROL
7. LOGGING_MONITORING
8. BACKUP_RECOVERY
9. LOAD_TESTING
10. PRODUCTION_ADMISSION

Каждой записи сервер назначает UUID; `required=true`, `status=NOT_STARTED`,
`owner=plannedDate=actualDate=comment=null`. Начальную техническую версию **0** задаёт
Hibernate @Version на persist/flush, вручную она не присваивается.
Техническая версия паспорта увеличивается **один раз за весь набор**, версия проекта,
даты/реквизиты паспорта и пользовательская версия не меняются.

Пример: паспорт version=0 → initialize → десять проверок version=0, паспорт version=1.
Повтор с expectedPassportVersion=0 даёт 409 версии; повтор с 1 — CHECKS_ALREADY_EXIST.
Инициализация не происходит при GET, PATCH или создании паспорта/компонента/интеграции.

## PATCH

Нужны expectedVersion **самой проверки**, её принадлежность проекту и минимум одно
изменяемое поле. Чужая запись даёт тот же 404, что отсутствующая, её версия не раскрывается.

| Поле | Тип / ограничения | null |
|---|---|---|
| `required` | JSON boolean | Запрещён |
| `status` | NOT_REQUIRED, NOT_STARTED, IN_PROGRESS, IN_REVIEW, PASSED, CHANGES_REQUIRED, BLOCKED | Запрещён |
| `owner` | Однострочный текст, максимум 255 после NFC | Очищает |
| `plannedDate` | Строка реальной даты YYYY-MM-DD | Очищает |
| `actualDate` | Строка реальной даты YYYY-MM-DD | Очищает, если допускает итоговый статус |
| `comment` | Многострочный управленческий текст, максимум 2000 после NFC | Очищает, если допускает итоговое состояние |

Отсутствие поля сохраняет прежнее значение. ID, projectId, checkType, version,
documentVersion и другие поля неизменяемы. Только expectedVersion без изменений — 400.

### Проверяется объединённое состояние

До изменения managed-сущности строится итог из прежних значений и переданных полей:

| Итог | Правило |
|---|---|
| required=true | status не может быть NOT_REQUIRED |
| status=PASSED | actualDate обязательна |
| status != PASSED | actualDate должна быть null |
| required=false | status=NOT_REQUIRED и непустой comment |

Любое противоречие — 400 целиком, без изменения строки, дат и версий. Например,
PASSED → BLOCKED требует явного `actualDate:null`; `required:false` само по себе
не переводит статус автоматически. Никаких автоматических дат или комментариев нет.
Если в PASSED уже есть actualDate, PATCH только owner сохраняет её и разрешён.
Очистка comment у NOT_REQUIRED/required=false без другого исправления состояния запрещена.

Завершение обязательной проверки:

```json
{"expectedVersion":0,"status":"PASSED","actualDate":"2026-10-14"}
```

Явная неприменимость:

```json
{"expectedVersion":1,"required":false,"status":"NOT_REQUIRED","actualDate":null,"comment":"Проверка неприменима к согласованному объёму решения."}
```

Возврат к обязательной заблокированной проверке:

```json
{"expectedVersion":2,"required":true,"status":"BLOCKED","actualDate":null,"comment":null}
```

Успешный PATCH увеличивает только техническую версию проверки **ровно на 1**, в том числе
при прежних значениях. Версии паспорта/проекта, даты паспорта и documentVersion не меняются.
Для изменённой строки используется @Version, для полностью прежних полей — CAS и refresh.

### Даты и готовность

Проверяется формат и существование календарной даты, без новых ограничений на порядок
plannedDate/actualDate или «не позже сегодня». Согласованные правила B2 остаются:
PASSED с actualDate завершает обязательную проверку; NOT_REQUIRED с обоснованием завершает
необязательную; BLOCKED блокирует обязательную проверку; CHANGES_REQUIRED требует внимания,
а для обязательной PRODUCTION_ADMISSION блокирует. Все причины меньших приоритетов сохранены.
Просрочка — строго plannedDate < единой calculationDate Europe/Moscow для незавершённой
обязательной проверки. Ближайшие даты сегодня…+14 включительно сами статус не ухудшают.

## Транзакции и конкурентность

Инициализация: validate → общий ProjectWriteLock → lock паспорта → версия → пустота →
persist десяти записей → flush → CAS версии паспорта → refresh/flush → полный DTO и
пересчёт через `cardAfterWrite`/MANDATORY → commit. Всё входит в одну write-транзакцию.
Инициализация согласована с созданием компонентов/интеграций B3.2a: при общей ожидаемой
версии состава одна операция завершается успешно, другая после ожидания получает 409.

PATCH: validate полей → родители → lock строки с условием принадлежности → версия →
объединение и валидация итогового состояния → запись полей → flush/@Version либо CAS →
полный DTO/пересчёт в той же write-транзакции → commit. Общее состояние проекта/паспорта
PATCH не блокирует на запись: разные проверки редактируются независимо.
Два PATCH одной версии одной проверки дают один успех и один 409 с её актуальной версией.

Любой сбой после flush откатывает набор/изменения и все версии. Отдельного GET после
commit нет, ответ видит свои незакоммиченные изменения. Он не обещает видеть ещё не
зафиксированную правку другой проверки. GET остаются read-only REPEATABLE_READ и не
создают/изменяют записи. Старые FK NO ACTION и общий протокол проекта сохранены;
каскады, orphanRemoval и операции удаления не добавляются.

## JSON, текст и ошибки

Общий строгий parser архитектурных write-маршрутов: объект в корне, неизвестные и повторные
поля, trailing JSON, неверные типы — 400. Тело максимум 32 KiB, bounded-чтение 32769 байт,
глубина 4, строка парсера 10000 символов, число 20 символов; поля ограничены строже.
Версии — JSON integer 0…9223372036854775806, не строки/дроби/boolean.

Переиспользуются B3.1: trim/NFC, длина после нормализации в UTF-16 единицах, запрет пустого
текста/недопустимых управляющих и FORMAT-символов/HTML/исполняемых фрагментов/явных
секретов/URL/IP. Comment сохраняет многострочность, CRLF/CR приводятся к LF; для очистки
используется null, не пустая строка. Коды статусов принимаются в каноническом верхнем регистре.
Фильтр явных шаблонов не заменяет контроль содержания и будущие авторизацию/экранирование.
Правила старых API не меняются.

| HTTP | code |
|---|---|
| 400 | BAD_REQUEST / VALIDATION_ERROR, безопасные сообщения B3.1 и fieldErrors известного поля |
| 404 | PROJECT_NOT_FOUND / PASSPORT_NOT_FOUND / CHECK_NOT_FOUND |
| 409 | CHECKS_ALREADY_EXIST, PASSPORT_VERSION_CONFLICT или CHECK_VERSION_CONFLICT |
| 500 | DATABASE_ERROR / Database operation failed |

409 версии содержит реальную currentVersion и versionResource PASSPORT либо CHECK:

```json
{"code":"CHECK_VERSION_CONFLICT","error":"Version does not match","currentVersion":1,"versionResource":"CHECK"}
```

Для непустого набора при актуальной версии:

```json
{"code":"CHECKS_ALREADY_EXIST","error":"Checks already exist"}
```

Исходные значения, SQL, пути, Java-классы и stack trace в ошибку не попадают;
новое логирование содержимого не добавлено.

## Границы

Поштучный POST проверок, DELETE, операции рисков и frontend не реализованы.
Схема/сущности, миграции, datasource-профили и startup SQL не изменяются.
Рабочая файловая БД и копии не открываются; тесты только на отдельных in-memory H2,
с сохранением защиты PM-000. Коммит и push выполняются только после отдельного разрешения.
