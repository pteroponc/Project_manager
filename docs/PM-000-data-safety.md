а не подтверждение совместимости фактической базы. Её открытие по-прежнему не разрешено.

## Резервное копирование: процедура для отдельного согласования

1. Установить фактический абсолютный путь БД по параметрам запуска и рабочему каталогу процесса.
   Относительный `./data/project_manager` сам по себе не доказывает расположение используемой БД.
2. Зафиксировать версию приложения, H2 из используемого JAR и параметры подключения без секретов.
3. Выбрать новый каталог резервных копий вне репозитория, target и автоматической очистки.
4. Получить разрешение на создание копии и при необходимости штатную остановку приложения.
5. Не перезаписывать предыдущие копии. Ограничить доступ к архиву как к исходным данным.

### Остановленное приложение — предпочтительно

- Не запускать старую сборку ради резервного копирования.
- Убедиться, что все процессы, использующие БД, штатно завершены. Не удалять lock-файлы для обхода блокировки.
- Скопировать закрытый `project_manager.mv.db` в новый каталог. Для этой MVStore-базы это файл данных;
  если обнаружены дополнительные файлы хранения, сначала уточнить формат и версию.
- Альтернатива — `org.h2.tools.Backup` той же версии H2, только для закрытой базы.
- Записать имя, размер и SHA-256 копии. Контрольная сумма подтверждает целостность копирования,
  но не заменяет проверку восстановления.

### Уже работающее приложение

Использовать административное подключение к той же открытой БД внутри её процесса:

```sql
BACKUP TO '<новый абсолютный путь>/project-manager-YYYYMMDD-HHMMSS.zip';
```

Возможный канал — встроенная H2 Console уже работающего приложения. Указать тот же JDBC URL
с защитой IFEXISTS, проверить, что подключение относится к нужной существующей базе.
Не открывать embedded-файл отдельным процессом, не включать AUTO_SERVER и не отключать FILE_LOCK.
Если безопасный канал недоступен — согласовать остановку и холодное копирование.
Обычное копирование открытого `.mv.db` и offline-инструмент Backup для online-копии не подходят.

Перед применением сборки остановить пользовательские изменения и сделать финальную копию.
Online-архив отражает состояние на момент backup; последующие изменения в него не попадают.

Источники: https://h2database.com/html/commands.html#backup
и https://h2database.com/html/tutorial.html#backup

## Проверка восстановления и совместимости схемы

Выполнять после отдельного согласования доступа к копии, не к рабочему файлу.

1. Сохранить резервный архив неизменным, распаковать его в новый отдельный каталог.
2. Проверить список файлов архива; отклонить пути, выходящие за каталог восстановления.
3. Подключить совместимую версию H2 напрямую, с `IFEXISTS=TRUE;ACCESS_MODE_DATA=r`.
   Снять перечень таблиц, колонок, всех ID и полный логический снимок прикладных записей.
   Не запускать старые Spring-инициализаторы для инспекции.
4. На ещё одной восстановленной копии запустить исправленную сборку с явно указанными
   абсолютным URL, отдельным портом, `spring.jpa.hibernate.ddl-auto=validate`,
   `spring.sql.init.mode=never`, без demo. Не использовать рабочие пути и не выполнять CRUD.
5. Проверить успешную валидацию схемы, чтение проектов и всех моделей досок, повторный старт.
   Сравнить все поля и ID до/после. Бинарный хеш после работы H2 может изменяться из-за
   служебных структур; это не равнозначно изменению прикладных записей.
6. При несовместимости остановиться, составить отчёт. Не применять update/create и не мигрировать схему автоматически.
7. Только после успешной проверки отдельно согласовать рабочий запуск. Сохранить уже установленные
   `validate`, `IFEXISTS=TRUE` и запрет автоматической SQL-инициализации.

Проверка синтетической схемы тестами не доказывает совместимость существующей рабочей схемы.

## Новая пустая БД: безопасная инициализация структуры

Проверено на новой in-memory H2: `validate` отказывает с `Schema-validation: missing table`,
в PUBLIC не появляется ни одной таблицы. Для отсутствующего файлового хранилища IFEXISTS
также запрещает его создание обычным подключением; файловый сценарий сейчас не запускался.

Предлагаемая отдельная процедура (пока не реализована как команда и не выполнялась на файловой БД):

1. Подготовить SQL создания только трёх прикладных таблиц, ограничений и индексов из текущих JPA-моделей
   на новой in-memory H2. Проверить его просмотром и применением к другой пустой in-memory H2.
   Не включать DROP, TRUNCATE, DELETE, MERGE, изменение пользователей и автоматическое наполнение.
2. Выбрать совершенно новый абсолютный путь, отличный от рабочего и от резервных копий.
   До открытия проверить отсутствие файлов базы; отказаться от операции, если цель уже существует.
   На время создания исключить другие процессы и пользователей, способных создать цель.
3. После отдельного согласования создать только новую БД. Проверить, что пользовательская схема
   не содержит объектов; при любом существующем объекте остановиться без применения SQL.
4. Применить проверенный CREATE-only SQL без IF NOT EXISTS: конфликт должен останавливать процедуру,
   а не маскироваться. DDL H2 не следует считать полностью откатываемым: при частичной ошибке
   оставить новый экземпляр для диагностики, не повторять автоматически и не переключать приложение.
5. Проверить новую структуру текущей сборкой с `validate` и отсутствие прикладных записей.
   После этого отдельно согласовать подключение приложения к новой БД с IFEXISTS=TRUE.

Существующие пользовательские базы этой процедурой не обрабатываются. Для них — backup,
проверка копии и отдельное решение по обнаруженным несовместимостям. Не использовать
`ddl-auto=create`, `create-drop` или `update` как обход ошибки валидации рабочей базы.
Автотест отдельно подтверждает цепочку явного создания новой in-memory структуры →
повторного запуска с validate без demo-данных.
