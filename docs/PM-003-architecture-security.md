## 1. Фактическое состояние и границы переиспользования

Стек: Java 21, Spring Boot 3.5.6, Spring MVC, Spring Data JPA/Hibernate, Bean Validation,
H2; интерфейс — статические HTML/CSS/JavaScript без frontend-фреймворка. Автоматического
мигратора нет. `ProjectEntity` хранится в `projects`, идентификатор — строка; обязательны
`name`, `owner`, `status`, `health`, `quarter`, строковый `deadline`, прежние текстовые поля
`milestone`, `risk`, `dependency`, KPI и `summary`. `deliveryModel`, `startDate`, `budget` и
`progress` допускают `null`; `progress = 0` отличается от неизвестного прогресса.
`budget` остаётся в старой модели и совместимом API, хотя в новом интерфейсе PM-002C его нет.
Новый архитектурный паспорт не должен изменять эти значения или подменять старое текстовое поле
`risk` структурированными ИБ-рисками без отдельного решения о переносе данных.

`BoardCardEntity` хранится в `board_cards` со строковым `projectId`; JPA-связи нет,
FK на projects с NO ACTION, NOT NULL и индексом добавляется ручной V003 и проверен напрямую на тестовой памяти. `ProjectMilestoneEntity` хранится в `project_milestones`, имеет
обязательный внешний ключ `project_id → projects.id` без каскада; чтение сортирует по
`position`, затем `id`. `ProjectEntity.version` — `@Version`. Версионный `PATCH` проекта
проверяет `expectedVersion`; операции с контрольными точками используют ожидаемую **версию
проекта** и атомарный compare-and-swap. Чтение версию не увеличивает. Старый совместимый
`PUT /api/projects/{id}` остаётся, но не требует клиентскую ожидаемую версию, поэтому нельзя
переносить его контракт на новый модуль.

`GET /api/projects/registry` предоставляет поиск, фильтры, сортировку, серверную оценку
PM-001 и варианты фильтров. `GET /api/projects/{id}/card` возвращает реальные сведения,
количество задач и контрольные точки, без бюджета. `GET /api/projects/{id}/deletion-impact`
считает задачи, контрольные точки, паспорт, компоненты, интеграции, проверки и ИБ-риски;
DELETE запрещает удаление при любой зависимости (409 с актуальным impact). Read API реестра, карточки и impact используют
`@Transactional(readOnly = true, isolation = REPEATABLE_READ)`; удаление и версионные
изменения проекта/точек — транзакционные. У доски и старых CRUD есть собственные прежние
границы транзакций; их нельзя считать образцом для нового агрегата. Удаление проекта
повторно проверяет все семь зависимостей в write-транзакции после ProjectWriteLock.
Операции контрольных точек тоже явно берут этот lock перед CAS и записью.
В PM-003B1a `ProjectWriteLock` блокирует строку проекта до создания/переноса карточки и до
DELETE; DELETE повторно считает зависимости после блокировки. Один FK на H2 2.3.232
не закрывает гонку незавершённой вставки с удалением проекта. При переносе двух проектов
блокировки берутся по возрастанию ID. GET не получает write-блокировку.

`ProjectMutationError` имеет поля `code`, `error`, необязательные `fieldErrors` и
`currentVersion`. `ProjectMutationException` уже даёт 404/409 и валидируемые ошибки. При этом
старые обработчики `IllegalArgumentException`, `BadRequestException` и Bean Validation
возвращают неодинаковые формы; новый модуль должен унифицировать **свои** ответы, не ломая
совместимые старые API. Новый сервис изменения должен возвращать агрегат в границе **одной**
транзакции после flush, а не выполнять изменение и отдельное чтение двумя сервисными вызовами:
при конкурентной записи второе чтение может показать чужое состояние.

PM-001 рассчитывает здоровье и сроки в `ProjectAssessmentService`: одна дата
`Europe/Moscow`, красный health или просроченный незавершённый проект требуют внимания,
жёлтый health сам по себе нет, `done + red` — противоречие данных. `PortfolioOverviewService`
агрегирует эти результаты в read-only транзакции. Архитектурная готовность — **другой**
показатель; можно переиспользовать часовой пояс/внедряемый `Clock`, шаблон оценки и понятие
списка причин, но нельзя связывать готовность с `health`, `deadline`, статусом `done` или
формулами PM-001. Релизные поезда и GitHub-проверки также не являются ИБ-проверками.

Ручной `db/manual/V002__project_model_and_milestones.sql` проверяет ожидаемую старую схему
до DDL, добавляет поля проекта/таблицу контрольных точек, проверяет результат; Spring его не
запускает. Обычный профиль использует файловую H2 с `IFEXISTS=TRUE`,
`ddl-auto=validate`, `spring.sql.init.mode=never`. Явный `demo` и `smoke` ограничены
`IsolatedDatabaseGuard` разрешёнными in-memory H2; тестовая защита также требует отдельную
in-memory базу. PM-003 не должен ослаблять эти ограничения или запускать рабочую базу.

После PM-002C sidebar и секции `overview`, `projects`, `project-card`, `dashboards`, `boards`,
`release`, `docs` живут в `index.html`; общая навигация и обзор — в `app.js`, реестр и карточка
— в `projects-ui.js`, стили — в `styles.css`. Клиент хранит фильтры реестра в query-параметрах,
обрабатывает 409 и экранирует текст перед HTML-вставкой. Новый интерфейс следует добавить
позднее отдельными PM-003C/D, сохранив маршруты и разделы. Известный долг PM-002C:
`projects-ui.js` после реестра вызывает `/card` для каждой строки ради `startDate` и числа
задач, а сортировку прогресса делает в браузере. Это N+1 запросов; PM-003A его не исправляет.
Новый портфельный API должен сразу возвращать все **свои** показатели без N+1 на клиенте.

## 2. Предлагаемая предметная модель

Все новые строки привязаны к существующему `projects.id`. Паспорт имеет ровно одну строку на
проект (`project_id` — PK и FK). Дочерние записи ссылаются на паспорт через тот же
`project_id`; пока паспорта нет, их создавать нельзя. Везде `ON DELETE NO ACTION`, без JPA
`CascadeType.REMOVE` и `orphanRemoval`. Строковые идентификаторы дочерних записей — UUID
(`VARCHAR(36)`); старые идентификаторы проектов остаются прежними (`VARCHAR(255)`).

Каталоги, валидируемые сервером (в SQL — строковые коды с CHECK или эквивалентной проверкой
на стороне БД после уточнения совместимости H2):

- Критичность, вероятность, влияние: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
- Стадия паспорта: `NOT_STARTED`, `IN_DESIGN`, `IN_REVIEW`, `APPROVED`,
  `CHANGES_REQUIRED`; тип решения: `NEW_SOLUTION`, `EXISTING_SOLUTION_CHANGE`,
  `INTEGRATION`, `MIGRATION`.
- Классы данных: `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `PERSONAL`, `PAYMENT`,
  `COMMERCIAL_SECRET`. Среды: `DEV`, `TEST`, `PREPROD`, `PROD`, `OTHER`; это ярлыки,
  не реальные контуры или адреса.
- Тип компонента: `FRONTEND`, `BACKEND`, `DATABASE`, `QUEUE`, `EXTERNAL_SERVICE`,
  `INFRASTRUCTURE`; тип взаимодействия: `API`, `EVENT`, `FILE_EXCHANGE`, `BATCH`,
  `OTHER`; направление: `INBOUND`, `OUTBOUND`, `BIDIRECTIONAL`; категория
  аутентификации: `NONE`, `SERVICE_ACCOUNT`, `OAUTH2`, `MTLS`, `CERTIFICATE`,
  `OTHER`; готовность интеграции: `PLANNED`, `IN_PROGRESS`, `READY`, `BLOCKED`.
- Типы проверок (порядок фиксирован): `ARCHITECTURE_APPROVAL`, `SECURITY_REQUIREMENTS`,
  `DATA_CLASSIFICATION`, `THREAT_MODEL`, `SECURITY_ASSESSMENT`, `ACCESS_CONTROL`,
  `LOGGING_MONITORING`, `BACKUP_RECOVERY`, `LOAD_TESTING`, `PRODUCTION_ADMISSION`.
  Статусы: `NOT_REQUIRED`, `NOT_STARTED`, `IN_PROGRESS`, `IN_REVIEW`, `PASSED`,
  `CHANGES_REQUIRED`, `BLOCKED`. Только `PRODUCTION_ADMISSION` предлагается считать
  блокирующей проверкой **перед запуском**; дата проекта не служит заменой этому признаку.
- Категории риска: `ACCESS`, `DATA`, `AVAILABILITY`, `INTEGRATION`, `PROCESS`,
  `OTHER`; статусы: `OPEN`, `IN_PROGRESS`, `ACCEPTED`, `MITIGATED`, `CLOSED`.

`created_at`/`updated_at` паспорта — UTC-моменты, изменяемые только при явной записи;
`last_review_date` — указанная пользователем локальная дата. Отсутствующие поля черновика
хранятся как SQL `NULL`; пустая строка не равна «не оценено». Для `READY` необходимы:
ответственный архитектор, краткое описание, тип и стадия, критичность, хотя бы один класс
данных и одна целевая среда, требования доступности и восстановления, дата пересмотра.
Пока эти сведения отсутствуют, паспорт можно сохранить как черновик, но готовность будет
`NOT_ASSESSED`. Даты `created_at`/`updated_at` сами по себе оценку не заменяют.

### Итоговый уровень риска

Рекомендация: клиент передаёт только `probability` и `impact`; сервер возвращает вычисленный
`level`. Не хранить третий редактируемый показатель, способный разойтись с исходными.
Предлагаемая симметричная матрица (строки — вероятность, столбцы — влияние):

|  | LOW | MEDIUM | HIGH | CRITICAL |
|---|---|---|---|---|
| LOW | LOW | LOW | MEDIUM | HIGH |
| MEDIUM | LOW | MEDIUM | HIGH | CRITICAL |
| HIGH | MEDIUM | HIGH | CRITICAL | CRITICAL |
| CRITICAL | HIGH | CRITICAL | CRITICAL | CRITICAL |

Это явная политика, покрываемая 16 тестами; в частности, редкое критическое воздействие не
становится «низким» риском. Изменение матрицы — отдельное версионируемое бизнес-решение, так
как оно меняет портфельные статусы без записи в БД.

## 3. Серверный расчёт готовности

`ArchitectureReadinessAssessmentService` принимает неизменяемый `ArchitectureReadinessSnapshot`:
паспорт, наборы классов/сред, проверки, интеграции и риски. Вход не содержит JPA-сущностей,
health, прогресс, сроки или статус проекта. Компоненты в формуле не участвуют. Сервис не
обращается к репозиториям и не изменяет вход. Внедряемый `Clock` используется только в
`newContext()`: будущий обработчик запроса снимает **одну** дату `Europe/Moscow` и передаёт
один `ArchitectureAssessmentContext` всем оценкам. `assess(snapshot, context)` часы не читает.
Возвращает
`status`, `statusLabel`, `reasons` (все причины с машинным кодом, сущностью/id и безопасным
сообщением), `upcomingChecks`, `acceptedHighRisks`, `calculationDate`, `timeZone`,
`officialGoLiveApproval: false`. Порядок причин стабилен:
уровень приоритета, тип сущности, тип проверки из каталога/уровень риска, дата (NULL в конце),
id, код и безопасное сообщение. Ближайшие проверки сортируются по дате, типу, id и статусу;
принятые риски — по убыванию уровня, id и обоснованию. Статус — максимальный
приоритет найденных причин: `BLOCKED → ATTENTION_REQUIRED → NOT_ASSESSED → READY`. Причины
нижнего приоритета **не отбрасываются**.

| Статус/причина | Точное условие |
|---|---|
| `BLOCKED` — «Заблокировано» | Открытый/обрабатываемый `CRITICAL`-риск; обязательная проверка `BLOCKED`; обязательная `PRODUCTION_ADMISSION` в `CHANGES_REQUIRED`; интеграция `HIGH`/`CRITICAL` в `BLOCKED`. |
| `ATTENTION_REQUIRED` — «Требует внимания» | Открытый/обрабатываемый `HIGH`-риск; принятый `HIGH`/`CRITICAL`-риск; просроченная обязательная незавершённая проверка; стадия `CHANGES_REQUIRED`; обязательная проверка кроме `PRODUCTION_ADMISSION` в `CHANGES_REQUIRED`. |
| `NOT_ASSESSED` — «Оценка не завершена» | Нет паспорта (`PASSPORT_MISSING`); сведения неполны (`REQUIRED_INFORMATION_INCOMPLETE`); стадия не `APPROVED` (`ARCHITECTURE_NOT_APPROVED`); отсутствует хотя бы один из десяти типов проверок или есть незавершённая/противоречивая проверка (`CHECKS_INCOMPLETE` и причины отдельных записей); интеграция `HIGH`/`CRITICAL` в `PLANNED`/`IN_PROGRESS`. Все причины сохраняются даже при более сильном итоговом статусе. |
| `READY` — «Архитектура и ИБ: проверки завершены» | Полный утверждённый паспорт; все десять типов представлены по одному и корректно завершены либо явно неприменимы; причин других статусов нет. `officialGoLiveApproval=false`: это не официальный допуск. |

Полнота паспорта следует разделу 2; неизвестные коды каталогов и пробельные обязательные
строки не считаются заполненными. Отсутствие паспорта, неполнота сведений, неутверждённая
архитектура и незавершённые проверки имеют отдельные причины. Отсутствующие типы проверок
дают `CHECK_TYPE_MISSING`, дубликаты — `CHECK_TYPE_DUPLICATE`; ID отсутствующей записи — NULL,
не выдуманный идентификатор. Неизвестный тип/статус, отсутствующий ID или противоречие полей
дают `CHECK_DATA_INVALID`; сообщения не отражают исходные подозрительные значения.

`required=true` завершён только при `PASSED` с `actualDate`; `required=false` требует
`NOT_REQUIRED` с непустым `comment` и без `actualDate`. Для остальных статусов `actualDate`
должен отсутствовать. Противоречие не даёт READY. Обязательная проверка с некорректным PASSED
также считается незавершённой. Просрочка строго `plannedDate < calculationDate`; отсутствие
срока не просрочка, но даёт `CHECK_PLANNED_DATE_MISSING` для обязательной незавершённой проверки.
Незавершённые обязательные проверки с датой сегодня…+14 включительно возвращаются в
`upcomingChecks`, даже когда итоговый статус вызван другой причиной. +15 вне горизонта.
Сам горизонт статус не ухудшает; корректно завершённые и неприменимые проверки туда не входят.

Матрица 4×4 раздела 2 согласована и вычисляется без сохранения `level`. `ACCEPTED` с уровнем
HIGH/CRITICAL **всегда** даёт ATTENTION_REQUIRED и отдельную запись `acceptedHighRisks` с
обоснованием и `acceptanceVerification=UNVERIFIED`. Эта отметка не позволяет получить READY
и не удостоверяет полномочия. Отсутствующее обоснование добавляет отдельную причину неполноты;
сам риск остаётся в списке. LOW/MEDIUM-риски и статусы MITIGATED/CLOSED сами проблемной причины
не создают. Неизвестные вероятность, влияние или статус дают `RISK_DATA_INVALID`.

HIGH/CRITICAL-интеграции оцениваются по таблице выше; READY у такой интеграции причин не даёт.
LOW/MEDIUM-интеграции статус не меняют. Неизвестная критичность или готовность значимой
интеграции даёт `INTEGRATION_DATA_INVALID`. Критичность компонентов информативна и в расчёт
не передаётся. Свободное обоснование принятого риска возвращается как текст: будущий API/UI
должен применять контекстное экранирование. Причины имеют фиксированные безопасные сообщения.

PM-003B3.2b: десять записей проверок создаёт только явное `POST .../checks/initialize` по проекту с уже
созданным паспортом и ожидаемой технической версией паспорта. Операция атомарна, создаёт
**ровно десять типов только при полностью пустом наборе**: `required=true`,
`status=NOT_STARTED`, owner/plannedDate/actualDate/comment равны null; версии задаёт Hibernate.
Любой непустой набор, включая неполный, отклоняется с 409 без изменения строк и версий.
Дополнения «недостающих типов» нет. Общий порядок locks: проект → паспорт; версия паспорта
увеличивается ровно на 1 за весь набор. GET ничего не инициализирует.
Неприменимость специалист устанавливает явным versioned PATCH (`required=false`,
`status=NOT_REQUIRED`, непустой `comment`). Изменение обратно требует нового решения.

## 4. Проект API и конкурентных изменений

Согласованное уточнение B3.3b: `passport.instanceId` — неизменяемый UUID каждого
экземпляра, хранится в V005 и переживает перезапуск. Новый паспорт того же проекта
получает другой UUID, даже при technical version=0 и documentVersion=1.0.
`expectedPassportInstanceId` обязателен в PATCH/DELETE паспорта, POST компонента/
интеграции/риска, initialize, DELETE всех четырёх дочерних типов. Для JSON это поле
тела, для DELETE — одиночный query-параметр. POST самого паспорта по-прежнему требует
expectedProjectVersion; PATCH ребёнка — его UUID и expectedVersion без токена паспорта.
Под locks: существование/принадлежность → instanceId → числовые версии → запись.
Неверный/отсутствующий UUID — 400; несовпадение — 409 PASSPORT_INSTANCE_CONFLICT,
реальная currentVersion и versionResource=PASSPORT; отсутствующий ресурс — 404.
Не подставлять актуальный токен в старый запрос и не повторять автоматически.
Полный контракт и ручная V005: `docs/PM-003B3.3b-manual-V005.md`.

Все GET только читают и возвращают снимок; отсутствующий проект — 404 `PROJECT_NOT_FOUND`.
`GET /api/projects/{id}/architecture` для существующего проекта **без** паспорта возвращает
200 с `passport: null`, пустыми списками, `NOT_ASSESSED`, пользовательским названием
«Оценка не завершена» и причиной `PASSPORT_MISSING`, а не создаёт паспорт/проверки.
Портфельный API принимает только перечисленные фильтры с валидацией, поддерживает пагинацию
и детерминированный порядок. Не отдаёт бюджеты, сетевые сведения и секреты.
Контракт PM-003B2.2 описан в `docs/PM-003B2.2-read-api.md`: поиск по названию/владельцу
без учёта регистра, пересечение фильтров, шесть сортировок, ID как дополнительный ключ,
отсутствующие значения в конце в обоих направлениях, `page=0`, `size=20` (максимум 100).
Неизвестные параметры и значения, повтор параметра и неверная пагинация дают безопасный 400.
`criticality=unspecified` включает проекты без паспорта. Все строки портфеля используют один
контекст оценки. Загрузка, DTO и расчёт выполняются внутри одной `readOnly=true`,
`REPEATABLE_READ` сервисной транзакции, пакетно, без write-блокировок и сохранений.
В каждом ответе с оценкой `READY` обозначено как расчёт по введённым сведениям,
`officialGoLiveApproval=false`; принятые риски имеют `acceptanceVerification=UNVERIFIED`.
Портфель и карточка не должны выдавать отметку `ACCEPTED` за подтверждённое решение
уполномоченного лица.

`collection` — закрытый список реальных маршрутов, не произвольный path. В B3.2b для `checks`
реализованы явная инициализация и PATCH существующих строк; DELETE добавлен в B3.3a.
Поштучного POST нет, неполный набор автоматически не дополняется. Версии включены в каждую запись и полный ответ. Изменение любой записи
выполняется в одной сервисной `@Transactional`-операции: validate → проверка проекта и
владения записью → compare-and-swap → запись → flush → пересчёт → ответ. Никаких автоматических
повторных сохранений при 409. Результат чтения внутри той же транзакции не должен вызвать
dirty checking; отсутствие частичных изменений проверяется тестом.

Контракт создания/PATCH паспорта PM-003B3.1 закреплён в `docs/PM-003B3.1-passport-write-api.md`.
Новые маршруты имеют собственный строгий JSON-разбор: неизвестные/повторяющиеся поля и
неверные типы отклоняются; тело максимум 32 KiB, классов максимум 6, сред максимум 5,
дубликатов нет. Даты/длины/NFC/управленческий текст валидируются до изменений.
`createdAt` и `updatedAt` задаются сервером в UTC через Clock; PATCH сохраняет `createdAt`.
409 версии содержит реальную `currentVersion` и `versionResource=PROJECT|PASSPORT`.
Старые коды отказа DELETE для задач/точек сохранены, в 409 добавлен impact. Расширение DELETE проекта реализовано в B3.3c; инициализация/PATCH проверок — B3.2b, POST/PATCH рисков — B3.2c,
DELETE дочерних записей — B3.3a, DELETE пустого паспорта — B3.3b.

Пользовательская версия нового паспорта — **1.0** (`passport.documentVersion`, read-only).
Это метаданные документа, не счётчик конкурентных изменений. `passport.version` и версии
дочерних строк — отдельные технические `@Version`; нумерация редакций документа в этом
этапе не вводится и от технического счётчика не вычисляется.

PM-003B3.2a реализует только POST/PATCH компонентов и интеграций. Контракт:
`docs/PM-003B3.2a-components-integrations-api.md`. Создание требует
`expectedPassportVersion` и locks в порядке проект → паспорт; увеличивает только
техническую версию паспорта, новая запись получает техническую версию 0 от Hibernate.
PATCH требует `expectedVersion` записи, проверяет принадлежность и блокирует только
её строку; разные записи редактируются независимо, версия паспорта не увеличивается.
Передаваемые классы интеграции обязательны при POST, при PATCH заменяются целиком,
не могут быть null/пустыми и не содержат дубликатов. Свойства/набор/версии/flush и полный
DTO с оценкой входят в одну write-транзакцию. GET остаются read-only.
DELETE, проверки, риски и frontend в B3.2a не включены.

Контракт проверок B3.2b: `docs/PM-003B3.2b-checks-api.md`. PATCH сохраняет пропущенные поля,
null очищает только nullable-реквизиты. Итоговое состояние проверяется после объединения:
обязательная проверка не может быть NOT_REQUIRED; PASSED требует actualDate, в остальных
статусах actualDate отсутствует; required=false требует NOT_REQUIRED и непустой comment.
Противоречие даёт 400 целиком. Locks и версии PATCH относятся только к проверке;
прежние значения тоже увеличивают её техническую версию ровно один раз. Пользовательская
версия паспорта остаётся 1.0; формула B2 не меняется.

Контракт рисков B3.2c: `docs/PM-003B3.2c-risks-api.md`. POST использует общий порядок locks
проект → паспорт и увеличивает техническую версию паспорта на 1. PATCH проверяет принадлежность,
блокирует только строку риска и увеличивает только её техническую версию, включая прежние значения.
Объединённое состояние проверяется до изменения managed-сущности: ACCEPTED требует непустое
acceptanceJustification, CLOSED требует closedDate, у остальных статусов closedDate=null.
Обоснование допускается и сохраняется при других статусах; автоматической очистки нет.
level вычисляется существующим оценщиком, ACCEPTED имеет UNVERIFIED, согласование не удостоверяется.
Весь ответ собирается после flush в той же write-транзакции, формула B2 не меняется.

Контракт удаления B3.3a: `docs/PM-003B3.3a-child-deletion-api.md`. Чужая/отсутствующая
запись — одинаковый безопасный 404 без версии, в том числе при устаревшей версии паспорта.
Версии сравниваются после lock записи; при двух несовпадениях сначала возвращается
PASSPORT_VERSION_CONFLICT, иначе конфликт соответствующей записи. Повтор DELETE — 404.
Удалённая проверка не восстанавливается GET; неполный набор не даёт READY, initialize
при любом оставшемся наборе даёт 409. Даты паспорта, версия проекта и documentVersion
не меняются. FK NO ACTION сохранены, каскадов нет; ошибки после flush откатывают всё.

Контракт удаления пустого паспорта B3.3b: `docs/PM-003B3.3b-passport-deletion-api.md`.
Удаляются только паспорт и его принадлежность проекту; техническая версия проекта
атомарно увеличивается на 1. При зависимостях никаких записей: пользователь сначала
явно удаляет дочерние записи и очищает классы/среды PATCH. При конфликте зависимости
ответ содержит тот же формат impact и причины, что GET deletion-impact; версии
проверяются раньше зависимостей. Ошибка после flush откатывает паспорт и версию проекта.

Рекомендация по версиям: паспорт и каждая компонентная/интеграционная/проверочная/рисковая
строка имеют **свою** `@Version`. Редактирование двух разных строк разными специалистами не
конфликтует. Версия паспорта защищает его поля, наборы классов/сред и членство коллекций:
создание/удаление дочерней записи требует `expectedPassportVersion` и атомарно увеличивает её;
редактирование существующей дочерней записи требует только её `expectedVersion` и не увеличивает
версию паспорта. Удаление дочерней записи проверяет обе версии. Это даёт осознанные конфликты
при конкурентном изменении состава, но не сериализует все правки разных специалистов.
Удаление интеграции следует тому же правилу: проверить принадлежность и обе версии до записи,
атомарно увеличить версию паспорта, явно удалить классификацию **только этой** интеграции,
затем её строку, сделать flush и вернуть новый агрегат. Любой конфликт/ошибка откатывает
классификацию, интеграцию и увеличение версии целиком; FK остаётся `NO ACTION`, каскадов нет.
При исчезновении проекта/паспорта между проверкой и записью вернуть 404, при изменении версии
— 409 с реальной `currentVersion`; не подставлять фиктивное число. Ограничения FK и UNIQUE
страхуют гонки и преобразуются в структурированный 409 без SQL/stack trace.

Формат ошибок нового API: `{ "code": "...", "error": "Безопасное общее сообщение",
"fieldErrors": { "field": "..." }, "currentVersion": 3 }`; опциональные поля отсутствуют,
а не заполняются выдуманными значениями. 400 — валидация, 404 — отсутствующий ресурс,
409 — версия/зависимость/уникальность. Технические исключения логируются только на сервере
с контролем содержания, клиент получает общий код. Для портфеля ошибки фильтра и неизвестного
enum не раскрывают внутренние классы или SQL.

## 5. Удаление и сохранность данных

Проект нельзя удалить при наличии хотя бы одной задачи, контрольной точки, архитектурного
паспорта, компонента, интеграции, проверки или ИБ-риска. `deletion-impact` показывает
**отдельный** счётчик для каждого вида и причины блокировки; `deletionAllowed=false` при любом
ненулевом. Этот GET read-only. В DELETE сначала блокируется строка проекта общим
`ProjectWriteLock`, затем счётчики перепроверяются в той же write-транзакции перед первой
записью. Обязательная предпосылка — отдельная ручная миграция FK
`board_cards.project_id → projects.id ON DELETE NO ACTION` с индексом по `project_id`.
Её precondition проверяет фактические тип/nullable/PK `board_cards` и считает все строки,
у которых `project_id IS NULL` или не найден в `projects`. При наличии хотя бы одной такой
карточки миграция прекращается **до первого DDL**; карточки не удаляются и не изменяются,
а разбор конкретных данных и способ разрешения требуют отдельного согласования. В PM-003B1
это самостоятельный первый шаг, до миграции архитектурных таблиц; расширение DELETE в
PM-003B3 требует подтверждённого FK и общего протокола блокировки; это проверено B3.3c на изолированной мигрированной памяти. На H2 2.3.232
одного FK недостаточно для гонки с незавершённой вставкой. Любой runtime-путь создания или
переноса зависимости проекта должен удерживать блокировку этой же строки до коммита;
существование проекта проверяется после получения блокировки. При двух проектах блокировки
берутся в стабильном порядке ID. Если карточка удерживает lock первой, DELETE после её коммита
видит задачу и получает 409. Если DELETE удерживает lock первым, последующая вставка после
его коммита получает 404. Барьерные тесты наблюдают второй запрос в состоянии BLOCKED до
освобождения первой транзакции и требуют отсутствия сирот. Прямые SQL-записи вне протокола
остаются отдельным ограничением. FK — дополнительная защита целостности; технические ошибки
не отражаются клиенту. Существующие задачи и точки не удаляются.

Паспорт нельзя удалить, пока есть дочерние строки, включая классы данных и среды. Явный
versioned DELETE интеграции после подтверждения удаляет её строки классификации и интеграцию
атомарно; строки других интеграций и паспорт не затрагиваются. Это специальная операция над
составом одной интеграции, **не** каскад удаления паспорта или проекта. При 404/409/сбое
состояние строк и версий до/после совпадает, сирот не остаётся.
После появления пользовательских данных rollback схемы не должен удалять таблицы.

## 6. Ограничения безопасности и валидация

Полей для паролей, токенов, закрытых ключей, содержимого сертификатов, строк подключения,
секретов окружений, IP/хостов, портов, эксплуатационных конфигураций и подробностей
уязвимостей нет. В интеграции хранится только **категория** аутентификации. Все свободные
описания — управленческие формулировки, а не технические инструкции. До появления
аутентификации и ролей вводить/публиковать чувствительные технические сведения в модуле
нельзя; развёртывание должно быть ограничено доверенной внутренней средой. Ввод явных
секретоподобных шаблонов/URL/IP отклонять серверной валидацией, но фильтр не считать
достаточной защитой от произвольного текста; нужен процесс ручного контроля содержания.

Длины всех строк заданы в таблице выше; `class_code`, enums, id и FK допускают только
предписанный формат/каталог, пустые или пробельные значения не допускаются. `name`,
`source_system`, `target_system` обязательны и непусты. `architect`, описания, требования,
платформа, владелец, сторона и комментарий могут быть SQL `NULL` в черновике, но не пустой
строкой. Входные свободные строки обрезать по краям, нормализовать Unicode NFC, ограничить
длину после нормализации, отклонять управляющие символы; коды enum принимать только в
каноническом верхнем регистре, неизвестные — 400. Не сворачивать внутренние пробелы внутри
названий без решения пользователя. Нельзя превращать пропущенное PATCH-поле в `null`.
В текстовых полях не допускаются HTML-теги/исполняемые фрагменты; при выводе независимо
от валидации использовать `textContent` или контекстное HTML/attribute escaping, никогда
`innerHTML` с сырым пользовательским текстом. Сервер не отражает исходное подозрительное
значение в ошибке. Ограничить размеры тела и массивов на уровне API; каталог типов
предотвращает невалидируемый JSON. Проверить безопасность экспорта/логирования при будущем
расширении; сейчас вложения и документы не проектируются.

## 7. Ручная миграция следующей версии и откат

Дополнение B3.3b: после выпущенной V004 применяется отдельная ручная V005
`db/manual/V005__architecture_passport_instance.sql` с полной precondition схемы V004,
уникальными UUID существующих паспортов, NOT NULL/UNIQUE и postcondition/маркером.
V002/V003/V004 не изменяются. Автозапуска нет; записи остановлены на весь скрипт,
при частичном DDL — восстановление проверенной резервной копии. Рабочая БД в этом
этапе не открывается. Инструкция: `docs/PM-003B3.3b-manual-V005.md`.

В PM-003B1 подготовить **два последовательных ручных скрипта** вне
`src/main/resources`: `db/manual/V003__board_cards_project_fk.sql` и
`db/manual/V004__architecture_security.sql`. Никаких startup SQL, Flyway/Liquibase или
изменения обычного `ddl-auto=validate`. Это две отдельные контрольные точки: успех V003
обязателен до V004 и до выпуска расширенного DELETE проекта.

V003 до первого DDL проверяет точную исходную схему `board_cards`/`projects` PM-002C,
отсутствие FK и отсутствие карточек с `board_cards.project_id IS NULL` либо с
`board_cards.project_id`, которого нет в `projects.id`. При несовместимой схеме или хотя бы
одной такой карточке скрипт останавливается без автоматического удаления или исправления строк;
нельзя использовать `IF NOT EXISTS`. После отдельного решения по данным и повторной проверки
V003 создаёт индекс `board_cards(project_id)` и FK `ON DELETE NO ACTION`, а если исходная схема
допускает `NULL` — также ограничение `NOT NULL` для `board_cards.project_id`; postcondition
проверяет индекс, ссылку, правило удаления, `NOT NULL` и
неизменность старых строк. Повторное применение отклоняется до DDL. При необходимости
JPA-описание и создание *новой* тестовой/demo-схемы должны также обеспечивать этот FK;
`ddl-auto=validate` само по себе не доказывает наличие ограничения, поэтому нужна прямая
проверка метаданных и конкурентная проверка. Перед применением миграции к согласованной
восстановленной копии остановить все записи в неё на время precondition и DDL, чтобы
проверка сирот и добавление FK видели один стабильный набор строк. Рабочую БД в PM-003B1
не открывать.

V004 сначала проверяет **полную ожидаемую исходную схему после V003**: состав/типы/nullable
критичных столбцов `projects`, `board_cards`, `release_trains`, `project_milestones`,
PK/FK/индексы (включая новый FK задач) и `projects.version`, а также отсутствие всех восьми
архитектурных таблиц и маркера V004. Несовместимость — понятная ошибка **до первого DDL**;
не использовать `IF NOT EXISTS`, которое скрыло бы частичную миграцию. Затем создать таблицы
и ограничения из раздела 2, индексы, запись о версии миграции и проверить postcondition:
состав/типы/nullable/PK/FK `NO ACTION`/индексы/значение `version` и маркер. Повторное
применение обязано отказаться до DDL. Если вводится таблица маркеров миграций, её структура
и отсутствие/ожидаемое содержимое входят в precondition каждого скрипта; V002 задним числом
не изменять.

Порядок проверки: (1) одноразовая отдельная in-memory H2 с точной предыдущей схемой и
сохранёнными строками проектов, задач, релизных поездов и точек; V003, затем V004;
сравнить все старые строки, ID, бюджет/прогресс/версии до и после каждого шага; отдельно
создать сироту в памяти и убедиться, что V003 отказывает до DDL без изменения строк;
проверить повторное применение, FK, конкурентную гонку и `ddl-auto=validate`; (2) **только
после отдельного согласования** —
backup рабочей БД по PM-000, проверенное восстановление в другой путь и пробный запуск
новой версии **только на восстановленной копии**; (3) отдельное решение о рабочей миграции.
Если на восстановленной копии обнаружатся сироты, остановиться и запросить отдельное решение;
V003/V004 не применять к рабочей базе автоматически.
Ни PM-003A, ни автоматические тесты не открывают рабочую файловую БД или её копии.

Для работающего H2 использовать согласованную команду `BACKUP TO` на новой абсолютной
локации; для остановленного — копирование после подтверждения полной остановки всех
подключений. Проверить архив, восстановить **в отдельный путь**, снять логические снимки до
и после, хранить backup вне Git с ограниченным доступом. Не копировать открытый `.mv.db`
обычным файловым копированием. H2 DDL нельзя считать полностью транзакционным: при сбое
не «доприменять» скрипт к частично изменённой базе, а остановить приложение и восстановить
подтверждённый backup в новый каталог. Если после миграции появились новые пользовательские
данные, переключение на старую копию без сверки/переноса приведёт к потере этих изменений;
удаление новых таблиц не является безопасным откатом. План переключения и переноса данных
согласуется отдельно.

## 8. План проверок

Автоматические тесты — только новые отдельные in-memory H2 под защитой PM-000; никакого
теста на файловой рабочей базе. На каждом шаге сравнивать записи до/после там, где
проверяется неизменность.

| Группа | Проверяемый результат |
|---|---|
| Миграция | Исходная схема V002 → V003 (FK задач) → V004 (архитектурные таблицы); все поля старых строк `projects`, `board_cards`, `release_trains`, `project_milestones` идентичны; нули бюджета/прогресса и максимум существующего бюджета не меняются. Осиротевшие карточки, несовместимая и частично мигрированная схема отклоняются до DDL без автоматической «починки»; повторный запуск отклоняется; FK `board_cards.project_id` с `NO ACTION`, остальные FK/индексы/version/default проверены напрямую; `ddl-auto=validate` запускается на мигрированной памяти. |
| Чтение | Повторные GET портфеля, паспорта и обоих deletion-impact не создают паспорт/десять проверок, не меняют строки или версии. Пустой проект даёт `NOT_ASSESSED`/«Оценка не завершена»/`PASSPORT_MISSING`; существующий неполный паспорт даёт отдельные `REQUIRED_INFORMATION_INCOMPLETE` и `CHECKS_INCOMPLETE`; отсутствующий проект — 404. |
| Формула | Все четыре статуса, 16 клеток матрицы, все причины и приоритет; принятые HIGH/CRITICAL дают ATTENTION_REQUIRED и список UNVERIFIED, MITIGATED/CLOSED сами причин не дают; HIGH/CRITICAL-интеграции BLOCKED блокируют, PLANNED/IN_PROGRESS дают NOT_ASSESSED, LOW/MEDIUM не влияют. Противоречивые PASSED/NOT_REQUIRED, неполнота и незавершённые проверки не дают READY. Подпись READY — «Архитектура и ИБ: проверки завершены», `officialGoLiveApproval=false`. Снимок не изменяется; единый контекст запроса и порядок входа не меняют результат. |
| Даты | Просрочка строго до расчётной даты; ближайшие сроки `today..today+14` включительно, `today+15` вне горизонта; одна дата `Europe/Moscow` для всего ответа, включая границу суток и несколько проектов. |
| Конкурентность/атомарность | Две одновременные правки одной строки → одна 409 с реальной версией; правки разных строк не конфликтуют; create/delete состава проверяет версию паспорта; удалённый проект/паспорт → 404 без 500; ошибки FK/UNIQUE и сбой посреди записи не оставляют частичных строк или увеличенных версий. Для интеграции отдельный тест: неверная версия строки/паспорта или сбой между удалением классификации и интеграции оставляет обе таблицы и обе версии без изменений. |
| Удаление | Все семь видов зависимостей в impact и 409; задачи и точки сохраняются; паспорт с дочерними строками не удаляется. Явный DELETE интеграции атомарно удаляет только её классификацию и строку, не оставляет сирот, другие интеграции не меняет; нет каскада паспорта/проекта. Параллельные создание задачи и DELETE проекта в обоих порядках дают либо сохранённый проект с задачей и 409 DELETE, либо удалённый проект и отказ создания задачи без сироты/500. Расширенный DELETE проекта не включать до V003. |
| Валидация и безопасность | Длины, обязательность, пустые строки, enum, даты, диапазоны, недопустимые статусы, обоснование принятого высокого/критического риска; XSS-строки отображаются текстом; API и ошибки не содержат секретов, SQL, stack trace, путей и имён Java-классов. |
| Портфель | Фильтры/поиск/сортировка/пагинация согласованы с totalCount, нет N+1 на клиенте, причины и принятые риски не теряются; существующие PM-001/PM-002 тесты и маршруты проходят регрессию. |

После добавления интерфейса — ручная проверка 1440/768/390 px, клавиатуры и screen reader,
пустых/частичных данных, ошибки загрузки/повтора, 409 без автоматической перезаписи, перехода
из архитектурного портфеля в проект и обратно с сохранением query-параметров. Подписи:
`NOT_ASSESSED` — «Оценка не завершена», `READY` — «Архитектура и ИБ: проверки завершены», рядом
«Расчётный показатель; не является официальным допуском к промышленной эксплуатации»;
`ACCEPTED` — «Отмечен как принятый; полномочия не проверены». Не показывать начатую оценку
как «не проводилась», а причины отсутствия паспорта, неполноты и незавершённых проверок —
раздельно.

## 10. Согласованные правила расчёта и дальнейшие решения

1. **Полнота проверок согласована.** Нужны все десять типов по одному; обязательная завершается
   PASSED с actualDate, неприменимая — NOT_REQUIRED с обоснованием. Противоречия не дают READY.
2. **Незавершённые проверки согласованы.** До просрочки — NOT_ASSESSED; при просрочке
   обязательной — ATTENTION_REQUIRED. Сроки сегодня…+14 сами статус не меняют.
3. **Проверка перед запуском согласована.** Обязательная PRODUCTION_ADMISSION в
   CHANGES_REQUIRED блокирует; другие обязательные CHANGES_REQUIRED требуют внимания.
4. **Риски и интеграции согласованы.** Матрица 4×4 фиксирована, level не хранится. Принятые
   HIGH/CRITICAL всегда дают ATTENTION_REQUIRED и UNVERIFIED, поэтому READY невозможен.
   HIGH/CRITICAL-интеграция BLOCKED блокирует, PLANNED/IN_PROGRESS не завершает оценку;
   LOW/MEDIUM-интеграции и критичность компонентов итоговый статус не меняют.
5. **Конкурентность.** Рекомендуются версии каждой строки и паспорта для изменения состава,
   а не одна версия проекта на все правки специалистов. Создание паспорта однократно
   использует ожидаемую версию проекта; старый PUT остаётся совместимым, но не становится
   версионным контрактом нового модуля.
6. **Удаление задач при гонке.** Нужны V003 с FK `NO ACTION` и проверкой
   осиротевших карточек **до** V004 и до расширенного DELETE. При сиротах — остановка и
   отдельное решение по каждой группе данных без автоматического удаления/исправления.
   До подтверждённого FK и тестов общего протокола блокировки проекта расширенный DELETE
   не выпускать. Один FK или read-only impact не закрывает гонку на H2 2.3.232.
7. **Справочники и экспозиция.** Закрытые коды закреплены моделью PM-003B1b и расчётом.
   Для будущего API отдельно определить ограничение доступа к приложению до появления
   аутентификации/ролей. Технические секреты и адреса не вводить даже в «комментарий».
8. **Макеты.** PM-003C/D требуют отдельного согласования структуры экранов. PM-003A не
   меняет frontend и не исправляет N+1 запросы PM-002C.
